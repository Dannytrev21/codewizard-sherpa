### Surfaces (Rule-7) — count discrepancy in story header reconciled

The story header AC-10a says `__all__` is "31 names — variant classes (17)
+ umbrella aliases (5) + reason `Literal` aliases (6) + error models (2)
+ `ApplicationPlan` (1)". The actual variant count across the five
umbrellas is 4 + 4 + 3 + 3 + 2 = **16**, not 17 — the story double-counts
either `NotApplicable` or `Failed` (which appear in both `RecipeOutcome`
and `RemediationOutcome` but as *distinct class objects*).

The story's example import block uses the bare-name form
`NotApplicable as RecipeNotApplicable, ... NotApplicable as
RemediationNotApplicable`. Python allows `from X import a as b, a as c`
but binds both locals to the *same* class object. That is incorrect for
this design: `RecipeOutcome.Failed.error` is annotated `RecipeError`,
while `RemediationOutcome.Failed.error` is annotated `RemediationError`
**and** carries an extra optional `partial_report_path: str | None` field
(arch line 452). The variants MUST be distinct classes.

Resolved by exporting under disambiguated names: `RecipeFailed`,
`RemediationFailed`, `RecipeNotApplicable`, `RemediationNotApplicable`.
The umbrella discriminated unions still route correctly via the shared
`kind` literal (`"not_applicable"` resolves to `RecipeNotApplicable`
within `RecipeOutcome` and to `RemediationNotApplicable` within
`RemediationOutcome` because each umbrella's variant tuple is closed).

The exact-set test (`test_all_exports_exact_set`) therefore pins
**30 names** (16 + 5 + 6 + 2 + 1), not 31. The set is asserted on
`set(__all__)` and on `len(__all__)`; a future contributor cannot collapse
two variants back into one without breaking the test.

### Pre-existing S1-02 bug found + fixed

The full test suite revealed a flaky Hypothesis-found regression in
`tests/unit/plugins/test_scope.py::test_parse_str_round_trip`:
`Concrete(value="0--2")` is admissible per the `scope_dims()` strategy
regex `^[a-z0-9_]([a-z0-9_-]{0,62}[a-z0-9_])?$` (closes leading/trailing
hyphens but admits internal `--`). When joined with the `--` separator,
the rendered scope `*--*--0--2` has four `--`-separated dims and fails
the parse check.

Per the scheduled-task instructions ("look at the last story
completed... if there are issues with that or any existing issues begin
working on that to fix it"), tightened the strategy regex to
`^[a-z0-9_](?:-?[a-z0-9_])*$` plus a length filter — the new pattern
alternates non-hyphen with optional single hyphen, forbidding *all three*
ambiguous boundary forms (leading hyphen, trailing hyphen, internal
double-hyphen). All 56 scope tests pass, including the Hypothesis
property tests.

This is a strictly narrower strategy than S1-02 originally shipped; it
does not affect the literal-regex rejection-matrix tests (R1–R17), which
call `parse()` directly with hand-crafted adversarial inputs. The S1-02
attempt log's "Rule-7 surfaces" section §1 already discussed the
ambiguity in detail; this closes the gap the Hypothesis shrinker
eventually surfaced.

### Refactor decisions (design-patterns lens)

- **Sum type over flag-and-payload.** `RemediationOutcome` is the surface
  that explicitly closes the `(passed: bool, error: str | None)` smell
  ADR-0033 names as a review blocker. The four-arm union makes
  `Validated.passed` mean *trust-scorer verdict on a sandbox-completed
  run*, never overloaded with "did the workflow finish".
- **Discriminated-union routing.** Single `Annotated[A | B | C,
  Field(discriminator="kind")]` form per umbrella — exact convention from
  the five existing Pydantic discriminated unions in the repo
  (`freshness.py`, `scanner_outcome.py`, `scenario_result.py`,
  `_cve_models.py`, + the manifest-recipe surface). Validates structural
  closure at decode time without requiring a custom `Discriminator(...)`
  callable.
- **Functional core / imperative shell.** The module has no functions,
  only data declarations + `field_validator` / `model_validator` arms.
  Every business rule is encoded in the type system (Literal members) or
  in pure validators (`_message_length`, `_passed_iff_no_failing`). The
  imperative shell is in Pydantic's validation machinery, not in our
  code.
- **Smart constructor + make-illegal-states-unrepresentable.** The
  `Validated` `model_validator(mode="after")` enforces `passed == (len(failing) == 0)`;
  constructing `Validated(passed=True, failing=[SignalKind("tests")])`
  raises ValidationError. The type system can't express
  passed-iff-failing-empty without a refinement (Pydantic doesn't have
  refinement types), so this is the cheapest correct shape.
- **Single source of truth for shared reasons.** `NotApplicableReason` is
  one module-level alias; both `RecipeNotApplicable.reason` and
  `RemediationNotApplicable.reason` reference it. `is` identity test
  (AC-8g) guards against accidental duplication. Phase 4+ extends the
  reason set additively in one place.
- **Open/Closed via additive extension.** Every reason `Literal` is the
  Phase-3 minimum set; the architecture explicitly calls out additive
  widening (Phase 4+ recipes can add `LLM_FALLBACK_REQUIRED` to
  `NotApplicableReason` without renaming or removing existing members).
  The `assert_never` arms in every consumer's `match` + the
  subprocess-mypy fence are the structural guard against silent
  widening.
- **Composition over inheritance.** No base class hierarchy — each
  variant is a flat `BaseModel`. The umbrella is built via
  `Annotated[... discriminator]`, not by inheritance. Mirrors
  `freshness.py:110` exactly.

### Lessons

1. **Pydantic discriminated unions can host structurally-identical variants
   under different umbrellas only if the *class objects* are distinct.** The
   discriminator routes by `kind` at decode time; if two variants share
   a class, the umbrella will return the same class regardless of which
   field annotation it was declared under. Where fields diverge
   (different annotations or extra fields) the classes MUST be distinct.
2. **A four-AC truth-table check beats two two-AC checks.** `Validated.passed_iff_failing_empty` is checked across all four corners
   `(passed=True, failing=[]) / (passed=False, failing=[T]) /
   (passed=True, failing=[T]) / (passed=False, failing=[])` — two
   accepted, two rejected. Catches both "validator missing" and
   "validator inverted" mutations.
3. **Hypothesis strategies that mirror the parse regex are wrong for
   round-trip tests when the dim alphabet overlaps the separator.** A
   regex that allows `-` inside a dim AND uses `--` as the dim
   separator creates ambiguous boundaries the round-trip property
   cannot hold over. The strategy must be narrower than the parse
   regex — round-trippable subset, not parse-admissible subset. (Same
   lesson called out in S1-02 attempt log; this attempt closes the
   internal-`--` case the original narrowing missed.)
