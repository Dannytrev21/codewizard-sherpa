### Refactor decisions (design-patterns lens)

- **Plugin architecture / Registry pattern.** `RecipeRegistry` mirrors `PluginRegistry` (S2-01) — small stable kernel + per-instance state + `default_*` singleton + `register_*(..., registry=...)` DI seam. Adding the 5th decorator-registry in the codebase; rule-of-N=5 documented in module docstring; kernel-extract still deferred per Rule 2 (five hand-written dispatch shapes diverge enough that a shared base would leave most LOC untouched).
- **Strategy pattern (GoF).** `RecipeEngine` (worker) + `RecipeProtocol` (matcher) — one engine serves many recipes; `plugin.transforms()[recipe.kind].apply(...)` is the dispatch site. Two implementations day-1 (S5-02 `NpmLockfileRecipeEngine`, S5-03 `OpenRewriteRecipeEngine`) earn the abstraction.
- **Newtype identifiers.** `PluginId`, `RecipeId`, `TransformKind` — no raw `str` in public signatures. `_validate_recipe_id` is the smart constructor at the registration boundary.
- **Sum type (`MatchedRecipe | RecipeNotApplicable`).** Walker return is a closed union; mypy --strict pins exhaustiveness. `RecipeNotApplicable.reason ∈ {"ALL_RECIPES_NOT_APPLICABLE", "NO_RECIPES_REGISTERED"}` is the disambiguation between two structurally-distinct failure modes.
- **Functional core / imperative shell.** `match_recipes` is pure over registry + cve + bundle. `RecipeRegistry.register` is the single mutation site; reads are pure (sort + filter).
- **Open/Closed at the file boundary.** Adding a new recipe = new module + `@register_recipe(plugin_id)` line. Adding a new engine = new module + `Plugin.transforms()` map entry. No edits to kernel modules.
- **Smart constructor (`_validate_recipe_id`).** Recipe-id strings can ONLY enter the typed `RecipeId` newtype via the regex-validated lifter at register-time — invalid ids fail loud at import, never silently at first walker call.
- **Composition over inheritance.** `RegisteredRecipe(plugin_id, recipe)` is a frozen-slots dataclass holding a `RecipeProtocol` instance; no recipe class inherits from the registry or vice-versa.
- **Re-export via class identity (not duplication).** `plugins/protocols.py` does `from codegenie.transforms.recipe_engine import RecipeEngine` — class identity verified by `assert P is T`. Eliminates the "two declarations drift" failure mode S2-01 explicitly deferred.

### Trade-offs deliberately taken

1. **`plugins/__init__.py` NOT extended with re-exports.** The story §Files-to-touch said to add `RecipeRegistry`, `register_recipe`, etc. to `__all__` in `plugins/__init__.py`. But `plugins/__init__.py` is intentionally empty (cold-start hygiene — "no eager re-exports — consumers import the specific submodule directly so the kernel stays cold-start friendly and the import-linter contracts in S1-05 can pin the public surface explicitly"). Surfaced the conflict per Rule 7; chose the more-recent, more-tested convention (Rule 11). Tests import directly from `codegenie.plugins.recipe_registry`. `transforms/__init__.py` DOES re-export the new symbols (its own existing convention).
2. **`Callable[[type], type]` return on `register_recipe`.** Originally untyped; mypy --strict required a return annotation. `Callable[[type], type]` is the minimal accurate type — the decorator takes a recipe class and returns it unchanged (`recipe_cls`). A tighter `TypeVar("R", bound=type)`-style annotation would let mypy preserve the concrete subclass; deferred because no test in this story exercises subclass-preservation through the decorator (a future Phase 4+ story can promote it if a real need surfaces).
3. **Subprocess test extracts last line of stdout.** First implementation compared full stdout; structlog/initialization log lines drift by timestamp across runs (`2026-05-19 13:29:51` vs `13:29:52`). Fix: `result.stdout.strip().splitlines()[-1]` extracts only the script's `print` output. The determinism contract is about ordering of `reg.all(PID)`, not about silencing package import side-effects — the script is short and the last-line extraction is the more honest assertion.
4. **`RecipeRegistry.all()` returns sorted tuple, NOT registration order.** S2-01's `PluginRegistry.all()` preserves registration order. This divergence is intentional and documented in `recipe_registry.py`'s docstring — the orchestrator's first-Applies-wins walker depends on `(-precedence, name)` order. Consistency with S2-01 was rejected because the recipe registry's primary consumer (the walker) needs ordering semantics S2-01's consumers do not.
5. **`RecipeNotFound` ships alongside `RecipeAlreadyRegistered` / `RecipeNameCollision`.** The story's AC-4 specifies `get()` semantics implicitly (typed `.recipe_id`); shipping `RecipeNotFound` makes the contract explicit and mirrors S2-01's `PluginNotRegistered` precedent. Out-of-scope for AC strictly, but in-scope for ADR-0002 lineage and the "fail loud" convention.
