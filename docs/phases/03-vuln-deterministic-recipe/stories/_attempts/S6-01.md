### As-built drift resolutions

1. **Chain convention pinned to "prev_hash = the new head folding this
   record" (Convention 2).** AC-GEN, AC-4, AC-CORE, AC-CHAIN and the TDD
   walker all describe `prev_hash = _chain_step(prior_head, body)`. AC-INTERIM's
   prose "its `prev_hash` is `GENESIS_CHAIN_HEAD` on the first run" is
   imprecise — it contradicts AC-GEN. Resolved in favour of the AC-GEN /
   walker form: the chain head *input* on the first run is `GENESIS_CHAIN_HEAD`;
   the first record's `prev_hash` is `_chain_step(GENESIS, body) != GENESIS`.
   The `test_cache_prune_event_chains_from_genesis` test asserts exactly that
   (recomputes `_chain_step(GENESIS, body)` and matches the on-disk value).

2. **`CacheGcCompleted` is chained at the on-disk envelope level, not via a
   model field.** AC-7 says "every spanning variant carries `prev_hash`", but
   AC-CG forbids redefining the re-imported `CacheGcCompletedEvent` (S3-05) —
   which has no `prev_hash` (nor `event_id` / `timestamp`) field. Resolution:
   the eight *native* spanning variants declare `prev_hash: BlobDigest`;
   `CacheGcCompleted`'s `prev_hash` lives as a top-level JSON key written by
   `emit_spanning` and stripped by `replay()` before Pydantic validation
   (`extra="forbid"` would otherwise reject it). The chain itself is verified
   at the JSON-dict level for *all* nine variants, so `CacheGcCompleted`
   participates fully. `emit_spanning` returns the per-record chain head as a
   synthetic `EventId` for the id-less `CacheGcCompleted` (the CLI ignores the
   return value).

3. **`emit` stamps `timestamp` from the injected clock.** Variants carrying a
   `timestamp` field have it overwritten from `EventLog`'s `clock()` at emit
   time — mirroring the story's own "writer rewrites `prev_hash`" design and
   making `clock` load-bearing (AC-CLOCK). `CacheGcCompleted` (no `timestamp`
   field) is emitted unchanged.

4. **The `sink` parameter overrides the *spanning* sink.** AC-2's signature
   takes a single `sink: EventStreamSink | None`, but there are two streams.
   The spanning stream (chain + flock) is the interesting one for
   deterministic byte assertions, so the injected sink targets it; the
   internal stream always uses `ZstdAppendingFileSink`. `InMemorySink.lock()`
   is a no-op context manager (single-process tests); the file sink's `lock()`
   does the real `fcntl.flock`. AC-FLOCK exercises the real file sink across
   two spawned processes.

5. **On-disk format = concatenated independent zstd frames; truncation is
   detected by per-frame one-shot decode.** `zstandard` 0.25's
   `decompress(..., read_across_frames=True)` is unimplemented, and both
   `stream_reader` and `decompressobj` decode a *truncated* trailing frame
   silently. `read_all` walks frames via `decompressobj().unused_data` (the
   frame-boundary primitive) and decodes each frame with a one-shot
   `decompress`, which *does* raise `ZstdError` on truncation — translated to
   `EventLogCorrupted(reason="truncated_frame")` (AC-TORN, fail-loud).

6. **`capture_spanning_events` test fixture swapped to `EventLog.replay()`.**
   The S3-05 conftest decoded the interim uncompressed `append.jsonl`; the
   S3-05 docstring promised "decoder swap only" when S6-01 lands. Honoured —
   the fixture now reads `append.jsonl.zst` via the canonical chain-verifying
   reader.

7. **`uv.lock` + pre-commit `mypy` hook updated for `zstandard`.** Adding
   `zstandard>=0.22` to `[project].dependencies` required `uv lock` (the
   lockstep fence) and a matching `additional_dependencies` entry on the
   isolated pre-commit `mypy` hook (it ships inline type hints).
