# Phase 7.5 — Multi-language foundations + Python: Devil's-advocate critique

**Reviewed by:** Devil's-advocate critic subagent
**Date:** 2026-05-20

## Method
I read all three designs and attacked each on its own terms. I do not propose alternatives.

## Attacks on the performance-first design

### Concrete problems (be specific — name components, decisions, numbers)

1. **Problem:** The whole design conflates "node" with the grammar `SupportedLanguage` `Literal`, and that `Literal` does not contain `"node"`. **Why it matters:** `src/codegenie/grammars/lock.py:51` is `SupportedLanguage = Literal["typescript", "tsx", "javascript"]` — there is no `"node"` member. The performance design's `LanguageDetectionPrepass` "returns `frozenset[SupportedLanguage]`" and its data-flow §3 says `Registry.sorted_for_dispatch` is "filtered to probes whose `applies_to_languages` intersects `{node, python}`". `{node, python}` is not a subset of `SupportedLanguage`, and `applies_to_languages` on the probe ABC is a separate `list[str]` axis, not the grammar `Literal`. The design has silently invented a fourth identifier ("node" the ecosystem) and typed its detection pre-pass against the wrong one. The "registry-cost proof" test that "registers N synthetic `LanguagePack`s" cannot even be written until this is resolved. **Where:** `LanguageDetectionPrepass` component; Data flow steps 2–3; Goal "Registry dispatch".

2. **Problem:** The headline goal — "Node/TypeScript cold gather p50/p95 unchanged within ±3% measured against the Phase 7 baseline" — has no baseline that exists. **Why it matters:** there is no committed Phase-7 cold-gather wall-clock number anywhere in the repo; the design's own Open Question 5 admits "Where do these baselines live, who re-baselines them." A ±3% gate against a number that doesn't exist is not a goal, it is a deferred decision dressed as a measurable. Worse, the design then calls this canary "the single most important test in this design" — the most important test is undefined. CI cold-gather wall-clock on shared GitHub runners has variance far exceeding ±3% (noisy-neighbour scheduling routinely swings 10–30%); a hard ±3% gate would be chronically flaky and a warn-only gate enforces nothing. **Where:** Goals ("Zero-regression gather"); Test plan ("Performance regression canary"); Open question 5.

3. **Problem:** The `LanguageDetectionPrepass` claims to "reuse the *existing* `language_detection` probe's marker logic" and read `enriched_snapshot.detected_languages` — a field it asserts "`cache/keys.py` and the coordinator already reference." **Why it matters:** the design never verified this field exists. The Phase 0/1 `LanguageDetection` is a *probe* that runs *inside* the coordinator's wave; its output lands in `ProbeOutput.schema_slice`, not on the `RepoSnapshot`. A pre-pass that runs *before wave construction* (the design is explicit: "before the wave is even built") cannot read a probe output that has not been produced yet. The design has a temporal ordering bug: it wants probe-derived data at a point in the lifecycle before any probe has run. Either it duplicates the marker walk (contradicting "does not add a second filesystem walk") or it reorders the coordinator (a silent edit to shipped Phase 0–2 code, ADR-0043-forbidden). **Where:** `LanguageDetectionPrepass` "Internal design"; Data flow step 2.

4. **Problem:** The "language #2 is free on language-#1 repos" thesis is contradicted by the design's own filter mechanism. **Why it matters:** if the coordinator must `filter` `sorted_for_dispatch` by an `eligible_packs` set, that filter is *new code on the dispatch path the coordinator runs on every gather* — including pure-Node gathers. The design claims the hot path is "the *existing* registry machinery, untouched," but a per-gather set-intersection over the probe list is not untouched; it is an added O(probes) pass. It is cheap, yes — but the design's own framing ("zero added latency on any repo that does not use that language") is then false by construction. The honest claim is "negligible," not "zero," and the design picks the unverifiable absolute. **Where:** Architecture ("the hot path is the *existing* registry machinery, untouched"); Data flow step 3.

5. **Problem:** The conformance-tier performance design (session-scoped fixtures, "run the per-language gathers in parallel via the session fixture warming concurrently — asyncio gather of the fixture builds") fights pytest's execution model. **Why it matters:** pytest session-scoped fixtures are lazily instantiated on first request and are not a place you `asyncio.gather` N independent builds — fixtures are pulled per-test, synchronously, in collection order. To "warm concurrently" you need a `conftest`-level session hook or `pytest-xdist` (which the codebase explicitly bans — CLAUDE.md: "No `pytest-xdist`"). The 90 s budget rests on a parallelism mechanism the test framework does not give you for free and the project forbids the obvious workaround for. The design asserts sub-linear growth from a parallelism it has not shown is achievable. **Where:** `tests/conformance/` component "Internal design (the performance-critical part)"; Goal "Conformance CI budget".

### Hidden assumptions

1. **Assumption:** The coordinator's single bounded `asyncio.Semaphore` budget is a tuning constant that scales cleanly to "both languages' worth of probes" on a polyglot repo. **What breaks if it's wrong:** the design's own "Acknowledged blind spots" admits it "did not model whether the bound itself needs a per-gather adjustment." If a polyglot repo doubles the eligible-probe count and the bound stays fixed, polyglot gather wall-clock degrades — directly violating the "Python gather parity ≤ Node-cold-p95 × 1.15" goal for the exact repos the phase exists to prove (polyglot).

2. **Assumption:** Python Layer A/B "is a smaller probe set than Node's full A–G," so the 1.15× ceiling is "generous." **What breaks if it's wrong:** the roadmap scopes Python as "new probes (Python Layer A/B)" — Layer A *and* B. Node's Phase 1 was Layer A only and Phase 2 added B–G. The design has no probe inventory for Python and no LOC estimate; it has assumed smallness. If Python Layer B (import-graph, reflection) is as heavy as Node's, the 1.15× ceiling is wrong and the headline parity goal fails silently — there is no test that would catch a 1.4× Python gather because the ceiling was a guess.

3. **Assumption:** `register_language` and `@register_probe` being "two registration paths that must agree" is acceptable, policed by "a conformance assertion." **What breaks if it's wrong:** the pack's `layer_a_probes` tuple is a *manifest* used to build the eligibility memo, while the probes self-register via decorator. If a probe is in the decorator path but absent from the manifest, the detection pre-pass *filters it out of the wave* — the probe is registered but never dispatched, silently. The "conformance assertion that the two agree" runs in CI, not at gather time; a production gather with a drifted pack silently under-analyzes. This is exactly the "honest confidence / silent staleness is the worst failure mode" violation (design.md §2 commitment 3) the project most fears, introduced by a performance optimization (the memo).

### Things this design missed that a different lens caught

- **`setup.py` as arbitrary executable code.** The performance design's Python dep-graph section lists "parse lockfiles, never invoke a resolver subprocess" but never mentions `setup.py`/`setup.cfg`. The security design correctly identifies `setup.py` is RCE-on-execution. The performance design's "uv.lock and poetry.lock are already-resolved graphs" framing ignores that a huge fraction of real Python repos ship *only* a `setup.py` or `requirements.txt` — its parity benchmark is built on the easy case.
- **`scip-python` as a security surface.** Performance treats SCIP purely as a latency rung ("slow and can be stale"). It is also a large, network-capable, pyright-based binary running on the gather host — a supply-chain and jail-escape concern the performance design is blind to.
- **Idempotence / two-phase atomicity of `register_language`.** Performance says `register_language` "is idempotent" in one sentence but its fan-out is "a straight-line sequence of calls" with no rollback. A mid-fan-out failure leaves registries half-written — the security design caught this; performance did not.

## Attacks on the security-first design

### Concrete problems

1. **Problem:** The design mandates `AdapterConfidence = Trusted | Degraded | Unavailable` as a sum type and explicitly calls out "Not a `float` confidence ... the ADR-0033 amendment to ADR-0032's `confidence() -> float`." **Why it matters:** ADR-0032 as written (read directly from `docs/production/adrs/0032-language-search-adapters.md`) declares the adapter Protocols with `def confidence(self) -> float`. There is no "ADR-0033 amendment" to ADR-0032 in the repo — the security design has invented an amendment to justify its sum type. Either the design is silently editing the ADR-0032 Protocol contract (which every Phase 1–7 adapter implements — a cross-cutting break to shipped code, exactly the silent edit ADR-0043 forbids) or it is asserting an amendment that does not exist. A Phase 7.5 design cannot unilaterally change a Phase-pre-7 frozen Protocol; that needs its own ADR and a *migration*, which the design never scopes. **Where:** "Python search adapter" component "Isolation"; Design-patterns table row 3.

2. **Problem:** "Total registration" Goal 1 says `register_language()` "validates the whole pack, then commits to all three registries inside one operation; any failure rolls back" — but the registries it fans into have no rollback API. **Why it matters:** `@register_probe` and `@register_dep_graph_strategy` (`src/codegenie/depgraph/registry.py:116`) are append-only registries whose `register` raises `DepGraphRegistryError`/`ProbeError` on duplicate and has *no unregister*. A "two-phase commit" over three append-only registries with no delete operation cannot "roll back" — the design would have to add an `unregister` to each shipped registry (a silent behavior edit to Phase 1–3 kernel code) or build a staging shadow-registry the real registries are swapped from. The design names neither. The atomicity goal is unbacked by the substrate. **Where:** Goal 1; `register_language()` component "Isolation" ("stage all writes, then commit-all or rollback-all").

3. **Problem:** The threat model's framing — "the gather pipeline reading a hostile repository ... a `requirements.txt` engineered to trigger a network fetch" — is a threat that the *existing* deterministic-pipeline architecture already forecloses, and the design spends its largest section re-proving it. **Why it matters:** The `fence` job + `import-linter` + `ALLOWED_BINARIES` already make network-at-gather-time structurally impossible repo-wide; the design's `tests/fence/test_depgraph_purity.py` is a *narrower* re-statement of a contract `import-linter` already enforces. Meanwhile the design under-invests in the genuinely new threat: the `LanguagePack` *module itself* is trusted code, and the design's own Risk #1 and Acknowledged-blind-spot #1 admit "the design controls *what `register_language()` does* but not *what a pack module does before it is called*" — i.e. the one genuinely new privileged surface in the phase is the one it explicitly does not defend. The effort allocation is inverted: heavy armor on a solved problem, an admitted gap on the new one.

4. **Problem:** The design adds `cgroup memory cap on the jailed process` as a recommendation (Open Question 2, blind spot 5) for `scip-python`, on the premise that gather runs `scip-python` and a memory-bomb repo "could pressure the host." **Why it matters:** this contradicts the phase's own scope and the codebase. `scip-python` is invoked through `run_external_cli` per ADR-0032 — but more importantly, the security design *itself* recommends in Open Question 3 shipping the Python search adapter "tree-sitter-first and treat the `scip-python` adapter as a fast-follow ... keeping it out of the phase's critical path." The design simultaneously (a) builds an elaborate TB-4 trust boundary, jail, env-scrub, degrade-ladder, and memory-cap proposal around `scip-python` and (b) recommends `scip-python` not be in the phase at all. That is a self-contradiction: half the security architecture defends a component the design recommends deferring. One of the two positions is dead weight.

5. **Problem:** The design treats over-detection ("a repo with one stray `.py` is flagged Python") as strictly safe — "Over-detection ... is preferred to under-detection. Over-detection costs a few wasted probe runs; under-detection silently skips analysis." **Why it matters:** over-detection is not free in a security frame the design otherwise prizes. A planted `pyproject.toml`/`setup.py` in a Node repo causes the Python dep-graph strategies and `scip-python` to *run over attacker-controlled Python files that the repo's real maintainers never intended as Python* — the design *expands* the attacker's reachable parser surface by being eager. The design's own "monotone accumulation / never demote" detector guarantees an attacker can *always* add the Python verdict to any Node repo and force the Python parsers to execute. The design calls its eager detector tamper-resistant; it is actually tamper-*inviting* for the parsers it spent the whole document hardening.

### Hidden assumptions

1. **Assumption:** The `tests/golden/languages/` goldens being "covered by the repo's existing dirty-tree guard (the goldens-not-dirtied protection from `ac1b5c5`)" makes golden-regeneration a safe, non-launderable surface. **What breaks if it's wrong:** the dirty-tree guard from commit `ac1b5c5` stops the *test suite* from dirtying *tracked* goldens during a run — it does not, and cannot, distinguish a *legitimate deliberate* golden regeneration in a PR from an *attacker's* golden regeneration in a PR. Both appear as a committed golden diff. The design's own Risk #3 admits "is this migration's golden regeneration legitimate? is ultimately a judgement call." The design leans on `ac1b5c5` as a control it is not; the laundering channel it identifies remains open.

2. **Assumption:** `import-linter` contracts "over the new Python pack sub-packages" can forbid a malicious pack module from reading `~/.aws/` at import. **What breaks if it's wrong:** `import-linter` checks the *import graph* — it forbids module `X` from importing module `Y`. Reading `~/.aws/` needs only `open()` / `pathlib` / `os` — all stdlib, all already importable everywhere in the codebase, none forbiddable by `import-linter` without breaking every file. The design's stated structural backstop for its #1 risk does not have the power the design assigns it; the real control collapses to "PR review," which the design itself calls "neither airtight."

3. **Assumption:** Symlink escape is a Python-probe-specific concern the Python probes must newly defend ("Symlinks are resolved and rejected if they escape the snapshot root"). **What breaks if it's wrong:** symlink containment is a property of the `RepoSnapshot` construction (Phase 0/1), not of any individual probe. If the snapshot already contains only in-root paths, the Python probes inherit safety for free; if it does *not*, then every Phase 1–7 Node probe is *already* vulnerable and Phase 7.5 is not the place to fix it. The design has assigned a cross-cutting Phase-0 responsibility to a new Phase-7.5 probe — either redundant work or a misplaced fix that should be a migration.

### Things this design missed

- **The `LanguagePack` retrofit asymmetry.** The security design never engages with how TypeScript becomes pack #1. It says "LanguagePack #1 = TypeScript (retrofit)" in one ASCII box and never returns to it. The best-practices design correctly identifies this as "the single sharpest retrofit seam" (its Q1) — Phase 1 probes already self-register, so the TypeScript pack either double-registers (loud crash) or only *references* probes (asymmetric proof). Security is blind to this; its "no-shadow guarantee" Goal 2 would in fact *fire on the TypeScript pack itself* if the retrofit re-registers Phase 1 probes.
- **Conformance tier CI cost.** Security adds "5–10 extra fixture repos and goldens" of adversarial fixtures to conformance and calls it "a few seconds of CI." The performance design's entire thesis is that conformance must not become a tentpole; security cheerfully inflates the exact tier performance warns about, with no budget analysis.
- **`tsx` and `javascript` are separate grammar `Literal` members.** Security (like the others) treats "TypeScript" as one language. The grammar kernel has three Node-side members (`typescript`, `tsx`, `javascript`). Whether one `LanguagePack` covers all three, or there are three packs, is undefined — and it bears directly on the no-shadow check (one pack claiming three grammar keys).

## Attacks on the best-practices design

### Concrete problems

1. **Problem:** The design's own central decision — Q1, "the single most important decision in the phase" — is left *unresolved*, and the resolution it leans toward is self-defeating. **Why it matters:** the design admits the TypeScript retrofit either (a) routes Phase 1 probe registration through `register_language()`, requiring an edit to the shipped `codegenie/probes/__init__.py` collection point, or (b) keeps probes self-registering and the pack merely *references* them — "an asymmetry with Python." It picks (b), then states in Risk #3 that this means "Python only validates *half* of [the abstraction]." The phase's exit criterion and entire reason for existing is "Python is `LanguagePack` #2, which validates the abstraction." A best-practices design that ships a known half-validated abstraction has failed its own lens — and it knows it, marking the seam "the critic should attack this hardest." It is attacked: the design does not solve the problem it was written to solve. **Where:** TypeScript pack component "Internal design"; Risk #2 and #3; Open Question Q1.

2. **Problem:** `register_language()` is specified as a flat fan-out that calls `register_probe(probe_cls)` for each probe in the pack — which, for the TypeScript pack, *will* double-register every Phase 1 probe and raise `ProbeError`. **Why it matters:** the design's own code block (component "`LanguageRegistry` + `register_language()`") is `for probe_cls in pack.layer_a_probes: register_probe(probe_cls)`. The TypeScript pack's `layer_a_probes` lists `LanguageDetectionProbe`, `NodeBuildSystemProbe`, etc. — classes whose modules are *already* imported by `codegenie/probes/__init__.py`, which *already* fired `@register_probe`. Running `register_language(TS_PACK)` then calls `register_probe` a second time on each → the registry "raises on duplicates" (the design says so itself in its Failure-modes table). So the design's own `register_language()` body crashes on its own pack #1. The Failure-modes row "Duplicate probe registration ... See Open Question Q1" is the design admitting its primary function does not run on its primary input. **Where:** `register_language()` code block; Failure modes table row 4.

3. **Problem:** The design reuses the existing `Language = NewType("Language", str)` for `LanguagePack.language` and then builds the `LanguagePack` field set on six capabilities — but `LanguagePack.grammar_name: str` is a *raw `str`*, not the `SupportedLanguage` `Literal` or a newtype. **Why it matters:** the design's "Conventions honored" section claims "Domain-modeling discipline (ADR-0033) — never raw `str` for domain IDs," and the `register_language()` body relies on `pack.grammar_name in grammars.lock.supported_languages()` to fail loud. But `grammar_name: str` means a typo (`"pyhton"`) passes `mypy` and is caught only at *runtime registration* — and only if `supported_languages()` is consulted, which is a runtime assert, not a type. The design had `SupportedLanguage` available (a closed `Literal`) and chose raw `str` for the one field that keys into a `Literal`-typed kernel. That is primitive obsession on a domain ID, in a design whose headline is domain-modeling discipline. **Where:** `LanguagePack` interface code block (`grammar_name: str`); `register_language()` code block.

4. **Problem:** The "category-based extension-by-addition fence" the roadmap and ADR-0043 ask for is silently downgraded to a single-contract snapshot test, and the design declares the roadmap's planted-silent-edit requirement satisfied by a test that only catches `LanguagePack`-field changes. **Why it matters:** the roadmap exit criterion is "the category-based fence rejects a planted silent edit"; the roadmap §"test-architecture evolution" row 7.5 says the fence is "exercised against a planted silent edit." The best-practices design's fence is `test_language_pack_contract.py` — a snapshot of the `LanguagePack` field set. Its own "Tradeoffs accepted" admits "A snapshot test catches a *contract* change, not an arbitrary silent edit anywhere." So a planted silent edit to a *Node probe body* (the canonical silent edit ADR-0043 exists to stop) is **not** caught by this fence — it is caught, the design says, "by the regression suite + review." The design has redefined the deliverable to match what it wants to build. ADR-0043 *does* defer the general category fence — but then the roadmap exit criterion "the category-based fence rejects a planted silent edit" is itself unsatisfiable as written, and the best-practices design papers over that contradiction instead of surfacing it. **Where:** "Category-based extension-by-addition fence" component; Test plan "Fence"; roadmap Phase 7.5 exit criteria.

5. **Problem:** The design accepts a `ProjectDetector` that "duplicates marker knowledge that `LanguageDetectionProbe` also has" and calls it "the design's accepted-duplication point" — then in Open Question Q4 admits a `catalogs/language_markers.yaml` both read "*would* be addition-only and might be cleaner." **Why it matters:** ADR-0043's Consequences explicitly names *duplication* as one of the "two problems in this space [that] have no mechanical fence" and a standing review criterion the design-patterns critic must flag. The best-practices design — the lens whose entire job is idiomatic, maintainable, conventional code — knowingly ships the anti-pattern its governing ADR singles out, with a cleaner addition-only alternative *identified in the same document*, and defers the choice to the synthesizer. A best-practices design that finds the better option and ships the worse one has inverted its lens. **Where:** `ProjectDetector` component "Tradeoffs accepted"; Open Question Q4.

### Hidden assumptions

1. **Assumption:** Two `LanguagePack` instances (TypeScript, Python) is "the minimum that proves the abstraction without freezing it on one example." **What breaks if it's wrong:** TypeScript and Python are both dynamically-typed-or-gradually-typed, lockfile-based, single-file-module ecosystems with near-identical capability shapes. They are *similar*, so the abstraction passing on both proves little. Phase 8's likely next language (Java/Maven — ADR-0032's running example) has a *classpath*, *compiled artifacts*, and *POM inheritance* — capabilities the six `LanguagePack` fields cannot express. The design's own Risk #1 admits this. "Two instances proves the abstraction" is the assumption; two *similar* instances proves only that the abstraction fits similar things — and the design freezes the contract on that thin evidence anyway (it does ship the freeze ADR, merely "Provisional").

2. **Assumption:** Parameterizing `tests/conformance/` over the live `default_language_registry.all()` is "the idiomatic pytest answer" and its import-side-effect coupling is acceptable ("the same coupling the coordinator already lives with"). **What breaks if it's wrong:** a registry-driven parametrization means pytest *collection* depends on import side effects firing in the right order. If a pack module fails to import (a broken `tree-sitter-python` wheel, an import-order bug — which the design's own blind spot #5 admits is "managed but not enforced"), the conformance suite does not *fail* for that language — it *silently collects fewer parameters*. A green conformance run with one language quietly missing looks identical to a green run with all languages present. The "auto-enrollment" property the design prizes is also an auto-*disenrollment* hole with no guard.

3. **Assumption:** `register_language()` keeping cyclomatic complexity "≤ 6 (it is a fan-out loop, not a branch tree)" is evidence of good design. **What breaks if it's wrong:** low cyclomatic complexity here is achieved precisely *because* the function ducks the hard problem — it does not handle the TypeScript double-registration case (problem 2), it does not handle partial-failure rollback (which the security design at least attempts), it does not validate adapter import paths resolve. A function is simple because it is *incomplete*. The metric (`C901 ≤ 6`) is being cited as a virtue of a function whose simplicity is a symptom of missing logic.

### Things this design missed

- **Atomicity / partial-failure of `register_language()`.** The best-practices design's fan-out has no rollback and no two-phase commit. The security design caught that a mid-fan-out failure leaves registries half-written. The best-practices "Failure modes" table lists duplicate-registration and un-wired-grammar failures but never "the 3rd of 5 fan-out steps raised" — the kernel is left corrupt and no test covers it.
- **Adversarial / hostile-input fixtures in conformance.** The best-practices conformance tier tests "detector detects, probe produces non-empty slice, golden matches" — all happy-path. The security design correctly makes hostile `requirements.txt` / oversized lockfile / hostile `setup.py` *part of passing conformance*. The best-practices design's conformance suite would pass a Python pack that OOMs on a 200 MB `poetry.lock`.
- **`requirements.txt` is a directive language, not data.** Best-practices says the pip strategy "reads `requirements.txt`" as if it were a manifest. It is a directive DSL (`-e`, `-r`, `--index-url`, VCS URLs, env markers). The security design caught this; best-practices' "three concrete lockfile parsers, no premature abstraction" framing treats `requirements.txt` as just another lockfile format and will under-parse it.

### Which disagreement matters most for *this* phase?

The **`register_language()` failure semantics** disagreement, because it exposes a fact none of the three confronted: the registries `register_language()` fans into are *append-only with no unregister*. The security design *wants* two-phase-commit-with-rollback and cannot have it without editing shipped registries; the performance and best-practices designs *don't even want* rollback and so ship a function that can leave the kernel half-corrupted — and the best-practices design additionally ships a `register_language()` that *crashes on its own first input* (the TypeScript pack) because the fan-out double-registers Phase 1 probes. This single disagreement is where the phase is least buildable as specified by any of the three: one design wants a capability the substrate doesn't offer, the other two ship a known-broken or known-incomplete function. The synthesizer cannot average these — it must first decide whether `register_language()` is a *pure addition* (Python-only fan-out; TypeScript is retrofitted differently or not fanned-out at all) or a *symmetric registrar* (which forces a shipped-code edit and a real staging mechanism). That decision precedes everything else in the phase.

### Where do all three quietly agree on something questionable?

1. **All three treat "TypeScript/JavaScript" as one language.** The grammar kernel has *three* Node-side `SupportedLanguage` members (`typescript`, `tsx`, `javascript`) and no `"node"`. None of the three designs says whether `LanguagePack` #1 carries one grammar key or three, how `tsx`/`javascript` map to one pack, or what `LanguagePack.language` (or "node" the ecosystem) even *is* relative to the grammar `Literal`. The whole phase's identifier model rests on a conflation all three inherited.

2. **All three assume the existing decomposed registries (`@register_probe`, `@register_dep_graph_strategy`, grammar `_DISPATCH`) compose cleanly under a `register_language()` facade with no edits.** None checked that `register_probe` has no `unregister`, that `@register_probe` already fires at probe-module import (making a second registrar-path a double-registration), or that `_DISPATCH` is a `Final` dict edited textually (a "loud edit") rather than written by `register_language()` at runtime. The "fan-out into existing seams" story is repeated by all three and verified by none.

3. **All three accept that two *similar* language packs (TypeScript, Python) "validate the abstraction" and that the `LanguagePack` contract should be frozen now.** TypeScript and Python are structurally alike; the next language (Java/Maven) is not. Freezing a six-field contract on two near-isomorphic examples is the "freeze-too-early" judgement-error ADR-0043 explicitly names — and all three either freeze it (best-practices, "Provisional") or treat the six fields as settled (performance's 7-field worry, security's "total frozen value"). None argues for *not* freezing it this phase.

## Roadmap-level critiques

1. **Does this phase set up problems for later phases (8+)?** Yes. All three freeze a six-field `LanguagePack` shaped entirely by TypeScript+Python. Phase 8 introduces the Hierarchical Planner and, per ADR-0032's own running example, the next target language is Java/Maven — which needs classpath resolution, compiled-artifact handling, and POM-inheritance capabilities the six fields do not name. ADR-0043's freeze discipline says freeze only *earned* contracts ("survived ~3 phases"); `LanguagePack` will have survived *zero* phases when frozen. The phase hands Phase 8 a contract that will break on its first real new language — the designs call that breakage "desired" (compiler-policed), but a contract that breaks on the very next use was frozen too early, which is the precise judgement-error ADR-0043 flags as having "no mechanical fence."

2. **Does it rely on something an earlier phase (0–7) didn't establish?** Yes, in two places. (a) The performance design's `LanguageDetectionPrepass` reads `enriched_snapshot.detected_languages` — a `RepoSnapshot` field that does not exist; `LanguageDetection` is a probe whose output is a `schema_slice`, available only *after* the wave runs, not before wave construction. (b) The security design's "two-phase commit with rollback" relies on the probe/depgraph registries having an unregister/staging capability they do not have (`src/codegenie/depgraph/registry.py` is append-only, duplicate-loud). Both designs assume Phase 0–3 substrate affordances that were never built.

3. **Does it violate any load-bearing commitment from `production/design.md` §2 or `CLAUDE.md`?** Yes. (a) **Commitment 3 (honest confidence / silent staleness is the worst failure mode):** the performance design's `register_language`-manifest-vs-`@register_probe`-decorator dual path can silently drop a probe from the dispatched wave — a registered-but-never-run probe is silent under-analysis, caught only by a CI conformance assertion, not at gather time. (b) **Commitment 5 / ADR-0043 (no *silent* edits):** the security design's claimed "ADR-0033 amendment to ADR-0032's `confidence() -> float`" would change the ADR-0032 adapter Protocol that every shipped adapter implements — a cross-cutting behavior change to frozen pre-Phase-7 surface, presented as a settled fact rather than a scoped migration. (c) The best-practices design's "category-based fence" downgrade leaves the roadmap's own Phase 7.5 exit criterion ("the category-based fence rejects a planted silent edit") unmet, and the design conceals rather than surfaces that contradiction (a Rule 7 / Rule 12 violation — surface conflicts, fail loud).

## Design-pattern critiques (cross-cutting)

### Misapplied patterns (with concrete victim)

- **"Command pattern + two-phase commit" (security design, `register_language()`).** A two-phase commit pattern requires a substrate with a prepare/commit/abort protocol. The victims — `ProbeRegistry`, `DepGraphRegistry`, the grammar `_DISPATCH` — are append-only dicts with no abort. The pattern is named to claim atomicity the components cannot deliver; it is pattern-as-decoration.
- **"Facade over existing `@register_*` seams" (best-practices design, `register_language()`).** A Facade *simplifies* access to subsystems without changing their semantics. This "facade" *changes* semantics: routing TypeScript's already-registered probes through it triggers a double-registration crash. A facade that breaks one of the two subsystems it fronts is not a facade; it is a leaky re-registrar.
- **"Specification pattern" (performance design, `LanguageDetectionPrepass`).** The design tags the pre-pass as "Functional core / Specification pattern," but a Specification is a composable boolean predicate object; the pre-pass is a single marker-glob scan returning a `frozenset`. Calling a one-shot filter a Specification is pattern-name inflation.

### Missed patterns (with concrete location)

- **A tagged sum type for the "language identifier vs grammar key vs ecosystem" tangle.** All three need to relate `LanguagePack.language`, the grammar `SupportedLanguage` `Literal` (`typescript`/`tsx`/`javascript`), and the implicit "node" ecosystem. None models the *one-language-to-many-grammars* relationship. A `LanguagePack` carrying `grammars: tuple[SupportedLanguage, ...]` (a real modeled relation) is the obvious missed structure; best-practices instead uses a raw `grammar_name: str`.
- **A staging/builder for `register_language()` partial-failure** — *if* atomicity is wanted. The security design wants atomicity and names "two-phase commit" but the buildable pattern over append-only registries is a *staging registry constructed complete then swapped in* (build-then-publish), which none of the three describes. (Note: the best-practices design correctly rejects a `LanguagePackBuilder` — a builder for the *pack value* would reintroduce partial state — but that is a different object from a staging mechanism for the *registration act*; the two were not distinguished.)

### Pattern claims that don't survive scrutiny

- **Performance: "Flyweight (the memoized shared `Language`)."** The memoized `Language` is just `functools.lru_cache` memoization — the grammar kernel already does this (`lock.py:92`). Flyweight is a pattern for sharing fine-grained immutable objects to save memory across *many* instances; one cached `Language` per process is plain memoization. Pattern-name inflation.
- **Security: "Hexagonal ports & adapters ... isolating `scip-python` behind the jailed wrapper."** The deterministic core already does not import `subprocess`/`requests` — that is enforced by `import-linter`, which predates this phase. The design claims hexagonal architecture as a *new* contribution; it is restating an existing structural invariant.
- **Best-practices: "Make illegal states unrepresentable" for `LanguagePack`.** Partially true — a *missing field* is unrepresentable. But `grammar_name: str` makes an *invalid grammar key* fully representable (`"pyhton"` type-checks). The design claims the pattern while leaving the most error-prone field unprotected by the type system.

### Anti-patterns from the toolkit's "flag on sight" list

- **Primitive obsession (best-practices, `LanguagePack.grammar_name: str`).** A raw `str` keying into a closed `Literal`-typed kernel, in the design that names domain-modeling discipline as a "convention honored."
- **Premature freeze (all three).** Freezing the `LanguagePack` contract on two near-isomorphic examples — ADR-0043's explicitly-named "freeze-too-early" judgement error.
- **Stringly-typed dispatch / dual source of truth (performance).** The pack's `layer_a_probes` manifest and the `@register_probe` decorator are two registration paths that "must agree," reconciled only by a CI test — a dual source of truth for which probes are dispatched.
- **Pattern soup / pattern-name inflation (all three "Design patterns applied" tables).** Performance's row claims five patterns for one component table; "Flyweight," "Specification," "Chain of responsibility" are stretched. Security claims "Command + two-phase commit," "Hexagonal," "tagged union" — at least two restate existing invariants. The tables read as pattern-credentialing rather than load-bearing design.
- **Solving a problem the phase does not have (security).** An elaborate TB-4 jail, env-scrub, degrade-ladder, and cgroup-memory-cap proposal for `scip-python` — a component the same design recommends *deferring out of the phase* (its Open Q3). Machinery built for a deferred component.
