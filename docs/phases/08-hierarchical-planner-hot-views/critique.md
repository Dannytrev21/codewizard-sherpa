# Phase 08 — Hierarchical Planner + pre-rendered hot views: Devil's-advocate critique

**Reviewed by:** Devil's-advocate critic subagent
**Date:** 2026-05-21

## Method
I read all three designs and attacked each on its own terms. I do not propose alternatives. My job is to surface what the synthesizer needs to see before it merges.

I also read the named ADRs (0013, 0023, 0029, 0030, 0031, 0032) and ADR-0042, production/design.md §2, the sibling final-designs (06, 07, 07.5), and — critically — the *actual* shipped code under `src/codegenie/plugins/`, `src/codegenie/tccm/`, and `src/codegenie/adapters/`. Several attacks below depend on what the codebase already contains versus what the designs assume it contains.

## Attacks on the performance-first design

### Concrete problems

1. **The two "performance-derived slices" (`plugin_resolution`, `context_bundle_skeleton`) are a unilateral ADR-0013 amendment that the design then admits it cannot make.** ADR-0013 §Consequences is explicit: "Adding a new slice to the pre-render list requires a deliberate ADR amendment." The design caches *six* slices, names ADR-0013's exact four, and openly says in Open Question 1 "they technically need an ADR amendment." So the entire load-bearing throughput mechanism — the thing the lens summary calls "the load-bearing move" — is, by the design's own admission, **not yet sanctioned**. A design whose central optimization is contingent on an ADR amendment that has not been written, and whose author flags it as an open question rather than producing the amendment, has not actually designed Phase 8 — it has designed a Phase 8 that requires a Phase-8 ADR it did not write.

2. **`context_bundle_skeleton` re-derives an artifact the resolver already produces.** `src/codegenie/plugins/resolver.py` already returns `ConcreteResolution.composed_tccm` and `composed_adapters` — the `extends`-chain is *already walked* and the TCCM *already merged left-to-right* (resolver.py lines 137–163, `compose_extends_chain`, `_merge_tccm`). The performance design's "context_bundle_skeleton = the union of `must_read` entries across the active plugins' TCCMs, already composed down the `extends` chain" is computing a thing the resolver hands back for free. The design talks as if TCCM composition is an expensive step worth pre-rendering ("resolve + compose-TCCM + union-slices on every workflow costs 25–50 ms") — but the composition is already done inside `resolve()`, which the design itself budgets at ~5 ms. The 25–50 ms figure is invented; the design never benchmarks the thing it claims is slow.

3. **`route()`'s recipe-existence check claims to be a free lookup but depends on a recipe index whose freshness is unmodeled.** The design asserts `route()` is "Rule 5 applied — recipe existence is a lookup, not a judgment." But Risk 2 then concedes "if recipe indexes are frequently stale, recipe-routes descend to RAG/LLM and the pre-selection saved nothing." The design has it both ways: routing is deterministic-and-free in the lens summary, and a mispredicting heuristic in the risk section. A stale recipe index that says "recipe exists" when it does not is not a deterministic lookup — it is a cache that can be wrong, and the design has no invalidation story for it. `route()` reads `RepoContext.recipe_index` (component §routing) but never says when that index is built, by whom, or how a probe re-run touches it.

4. **The 1,200 workflows/hour and <5 ms p95 numbers are asserted against infrastructure that does not exist this phase.** The throughput goal is "≥ 1,200 wph steady-state per worker pool (8 workers)." Phase 8 has no worker pool — Temporal and worker processes arrive in **Phase 9** (roadmap, explicit). The design even concedes this in §MCP ("per-agent identity is Phase 9+"). A workflows-per-hour number for an 8-worker pool is a Phase-9 metric smuggled into a Phase-8 design; it cannot be tested at Phase 8's exit because the substrate that would produce it is a phase away.

5. **The cold-path "≤ 350 ms" budget hand-waves the `RepoContext` disk read.** §Resource profile: "the bulk is reading `RepoContext` from disk/object store." `RepoContext` for a large monorepo is not a small file. The design gives one number (350 ms p95) for "inline `resolve()` ~5 ms + bundle skeleton assembly 20–40 ms + synchronous render 5–20 ms + Redis backfill" — that sums to ~70 ms, leaving ~280 ms unexplained and attributed to "reading `RepoContext`." A cold path whose dominant cost is un-budgeted is not a bounded cold path. And the cold path is the *every-first-workflow* path and the *every-schema-bump* path — Risk 4 admits a schema bump "cold-paths the entire portfolio once."

### Hidden assumptions

1. **Assumption:** Pre-rendering at the gather tail means the hot views are always at most one gather cycle stale. **What breaks if it's wrong:** The design's debounce (250 ms per `repo_id`) plus a detached `asyncio.create_task` render means a workflow can fire *between* a probe re-run and the render completing. The design calls this "bounded staleness ≤ one gather cycle" — but it is actually "bounded staleness ≤ one gather cycle *plus the render latency plus the debounce window*," and the workflow in flight reads the *stale* view with no signal that it is stale (the `confidence_summary` slice carries `IndexHealthProbe` output, not "this hot view lagged the last gather"). The design conflates "the gather is fresh" with "the views are fresh."

2. **Assumption:** A misprediction by `route()` costs "one wasted recipe-match attempt (~milliseconds)." **What breaks if it's wrong:** If `route()` says `RouteRecipe` and the recipe is stale/inapplicable, the design says `FallbackTier` descends. But descending means the workflow now pays the recipe-match attempt *and* the RAG round-trip *and* possibly the LLM call — strictly *more* than entering at the chain head. The design's own claim "never worse than not pre-selecting" is false for the mispredict case: a workflow that should have gone straight to RAG instead does recipe-then-RAG. The "net-positive in expectation" hinges entirely on the unmeasured misprediction rate from problem 3.

3. **Assumption:** Redis as a no-AOF, single-instance cache is fine because "an empty Redis after a restart is a portfolio-wide cold path that self-heals." **What breaks if it's wrong:** Risk 3 admits "a portfolio-wide cold-path storm after a Redis restart is a real thundering-herd risk." The design's mitigation is "the 250 ms render debounce" — but the debounce is on the *render* path, not the *Supervisor cold path*. After a Redis flush, every workflow on every repo simultaneously takes the ≤350 ms cold path *and* triggers a synchronous render *and* a backfill. The debounce does nothing for a workflow-driven cold-path storm; it only coalesces gather-driven renders. The thundering herd is unmitigated.

### Things this design missed that a different lens caught

- **Redis is treated as trusted on read.** The performance design reads `HGETALL repo:{id}:hotviews` and parses "the pre-serialized `plugin_resolution` blob" with zero integrity check. The security design's entire TB-4 — a writable Redis is a write primitive into every planner's context — is absent. The performance design's degraded path handles Redis *unavailable*; it has no path for Redis *lying*.
- **Multi-plugin `Both`-workflow coordination (ADR-0042) is not mentioned once.** See Roadmap critique 1.
- **The MCP server has no authorization** — the design acknowledges this as a blind spot, but a security lens would call it a Phase-8 deliverable gap, not a deferral, because the roadmap puts the Skills server *in* Phase 8.

## Attacks on the security-first design

### Concrete problems

1. **The design invents an entire credential and KMS apparatus the roadmap never names, in a phase with no LLM call to protect yet.** The `LlmCapability` (per-workflow minted, secrets-broker-fetched, TTL'd, `revoke()`d), the KMS-held audit-chain signing key, the secrets broker, the mTLS-private Redis network segment, Redis 6+ ACLs — none of this is in the Phase 8 roadmap entry ("`redis` in docker-compose. `redis-py`. The `mcp` Python SDK"). The roadmap's Phase 8 tooling list is three lines. The security design ships a secrets-management subsystem, a KMS integration, and a network-segmentation story as if they were Phase 8 scope. This is the security-lens version of pattern soup: it is *architecture by threat enumeration*, and it front-runs Phase 9 (Temporal, identity) and Phase 13 (cost ledger, OTel) wholesale. The roadmap is explicit that identity is not yet a thing; ADR-0023 §"Evidence needed to resolve" names "are we adopting a per-agent identity model" as an *open question*. The security design answers that open question unilaterally and builds on the answer.

2. **The `PlannerDecisionLog` directly contradicts the roadmap and ADR-0034's stated phasing.** Roadmap Phase 9: "Phase 9 is where ADR-0034 (event sourcing as canonical primitive) lands operationally... Existing append-only structures — attempt logs, draft cost ledgers, **plugin-resolution records** — migrate to event-stream projections from this point." The security design builds, *in Phase 8*, a hash-chained, BLAKE3-linked, KMS-signed event-sourced store for exactly "plugin-resolution and routing decisions." That is the Phase 9 canonical event log, built a phase early, under a different name. Open Question 5 even asks "should Phase 8 defer the log to Phase 9 entirely" — and then answers "no" on the strength of the exit criterion. But the exit criterion ("the chosen path is logged on every workflow") is satisfied by *any* audit emission; it does not require event sourcing, hash chaining, or KMS signing. The design has manufactured a Phase-9 deliverable and justified it with a Phase-8 exit criterion that does not demand it.

3. **The `BundleBuilder` "does not re-read raw repo bytes" claim is asserted, then quietly broken.** §BundleBuilder Isolation: "It operates only on already-gathered, already-sanitized artifacts — it does **not** re-read raw repo bytes." But the *whole point* of ADR-0030 derived queries is to select files the agent then *reads* — `scip.refs` returns `file:line:col` call sites, and the bundle's job (ADR-0029) is to load those files' content into the worker's context window. If the bundle only ever holds the sanitized `RepoContext` and never the actual source of the affected call sites, the LLM-fallback node has nothing to plan against. Either the bundle includes repo source (and the no-raw-bytes claim is false) or it does not (and the bundle is useless for the recipe/RAG/LLM routing the phase exists to do). The design's `contains_unverified_repo_content` flag and "fence repo content as untrusted data" prose presuppose repo content *is* in the bundle — contradicting the isolation claim two paragraphs up.

4. **The manifest-poisoning defenses are mostly already covered by ADR-0031, and the design does not cleanly distinguish its additions.** Open Question 4 honestly flags this: "ADR-0031 already mandates Pydantic validation and import-path resolution at startup... I *add* the import-path *allowlist*, the scope-claim guard, the `extends` cycle/depth bound, and the budget clamp." But ADR-0031 §"Discovery and resolution" and §"Inheritance and override" already specify cycle-safe `extends` walking implicitly (the resolver in `resolver.py` already has a `walk()` with a `seen` set — line 397+), and the universal `(*,*,*)` plugin is already the *only* wildcard-all plugin by ADR-0031 §No-match fallback. The design presents as novel hardening several things the shipped resolver already does. The genuinely new bits (import-path *allowlist* by module prefix, `MAX_EXTENDS_DEPTH=8`, budget clamp) are buried inside a six-step list that mostly re-states ADR-0031.

5. **"Fail-closed to cold storage" on HMAC failure is a denial-of-service amplifier the design celebrates as a feature.** §Redis Integrity defense: an attacker who poisons Redis "can only force a slower cold read." But the security design's own cold path is the *cold storage* path through Postgres + object store. An attacker with Redis write access can flip *every* hot-view read to a cold read by corrupting HMAC tags — turning a <5 ms read into a tens-of-ms Postgres round-trip across the entire portfolio, indefinitely, until someone notices. The design calls this "a latency problem, not an integrity problem" — but a portfolio-wide, attacker-sustained latency multiplier *is* an availability attack, and the design ships no rate limit, no circuit breaker, and no alert threshold beyond "an `integrity_ok: false` is a security event, alerted" (which, under a sustained attack, is an alert storm). Blind spot 5's own list — "cost attribution of the security controls... I flagged but did not specify" — is this exact hole.

### Hidden assumptions

1. **Assumption:** A secrets broker and a KMS exist in the Phase 8 deployment. **What breaks if it's wrong:** The roadmap's Phase 8 infrastructure is `redis` + `redis-py` + `mcp` SDK. There is no secrets broker, no KMS, no mTLS PKI in any phase before Phase 8, and the roadmap does not introduce one in Phase 8. Every credential-lifecycle claim, every "KMS-signed chain head," every "minted from the secrets broker" depends on infrastructure the design assumes into existence. If it is not there, the entire credential design is undeployable and the audit-chain signing is undeployable.

2. **Assumption:** `seccomp-bpf`, `no_new_privileges`, and a read-only bind-mount can be applied to the Skills MCP stdio child process within Phase 8's scope. **What breaks if it's wrong:** Phase 8 runs as a local dev process (the roadmap: "the Skills server runs as a local MCP stdio process"). seccomp profiles, bind-mounts, and unprivileged-user confinement are container/host-orchestration concerns — they require the deployment substrate Phase 9 (Temporal workers, separate processes) introduces. Applying a seccomp-bpf profile to a stdio subprocess spawned by a local `codegenie` CLI on a developer's macOS machine (the documented dev environment — `Darwin` in the env block) is not even possible: seccomp is Linux-only. The design's signature isolation control does not run on the platform the project develops on.

3. **Assumption:** The `LlmCapability` just-in-time mint fits the latency budget. **What breaks if it's wrong:** Open Question 1 is the design admitting it does not know. A secrets-broker round-trip per LLM-fallback workflow is ~10–30 ms by the design's own §Resource profile. The design says this is "off the hot path" because the hot path is the <50ms hot-view *read* — but the LLM-fallback route is precisely the *slow, expensive* route, and adding a mandatory broker round-trip in front of every LLM call at portfolio scale is a contention point the design's own Blind Spot 1 concedes is unmodeled.

### Things this design missed

- **It said almost nothing about the actual planning logic.** Blind Spot 2 admits it: "I have said little about how recipe-match and RAG retrieval actually score — that is the substance of the planner." A security design for a *Planner* phase that secures the boundary around the router and never designs the router has secured a perimeter around an empty room. The exit criterion is "the planner makes the recipe/RAG/LLM decision" — the security design's `PlannerSubgraph` section is four sentences of routing and twelve of audit.
- **It missed the `ComposedTccm` placeholder problem entirely** (see Roadmap critique 2) — it assumes a finished, validated `TCCM` model with `must_read`/`should_read`/`may_read`/`budget` fields, when the shipped `ComposedTccm` is an explicitly-documented stub.
- **Multi-plugin `Both` coordination** — Blind Spot 3 gestures at it ("if `Both` coordination is in Phase 8 scope, the `LlmCapability` and decision-log model need a parent/child extension I have not drawn") but does not design it. It *is* in scope — see Roadmap critique 1.

## Attacks on the best-practices design

### Concrete problems

1. **The design's central reuse claim is built on a package that is a documented placeholder, and the design never read the code.** Best-practices repeatedly asserts "`codegenie.tccm` already models manifests and the five derived queries" and places its `BundleBuilder` in `codegenie.tccm` because "it consumes `TCCM` and the five `DerivedQuery` variants already modeled in `codegenie/tccm/queries.py`." But the resolver's composition output is `ComposedTccm` (`src/codegenie/plugins/resolver.py` line 120), whose own docstring says: *"Minimal `TCCM` placeholder for Step 2. Step 3 (S3-01) replaces this with the real `TCCM` Pydantic per Phase-3 ADR-0004... only the field set on the underlying model widens."* The design assumes a finished TCCM substrate with `must_read`/`should_read`/`may_read`/`budget` bands and five typed `DerivedQuery` variants. Whether `codegenie/tccm/queries.py` actually contains five discriminated-union query variants today is something the design asserts without verifying — and the resolver, the *actual* composition path, does not use `codegenie.tccm.TCCM` at all; it uses its own `ComposedTccm`. The "Phase 8 just wires existing seams" thesis rests on seams the design did not confirm are finished.

2. **`BundleBuilder` is given an `AdapterDispatcher` "from the resolver result" that the resolver does not return.** §BundleBuilder: "Adapter routing is delegated to an `AdapterDispatcher` that walks the resolved `extends` chain and picks the last-registered adapter per primitive." But `ConcreteResolution` already exposes `composed_adapters: dict[PrimitiveName, Adapter]` (resolver.py line 163) — the per-primitive last-wins merge is *already done* by `_merge_adapters` (line 466). There is no `AdapterDispatcher` to inject and no chain left to walk; the resolver flattened it. The design invents a collaborator (`AdapterDispatcher`) and a behavior ("walks the resolved `extends` chain") that duplicate shipped resolver internals. The Open Question 1 ("Bundle Builder home") is moot for the wrong reason: the design mis-modeled what the resolver hands it.

3. **The `NullRagPort` makes the three-step chain a two-step chain wearing a costume, and the phase's exit criterion is "the planner makes the recipe/RAG/LLM decision."** §PlannerNode: "`SolvedExampleRagPort` is stubbed in Phase 8... returns 'no hit' — honestly, a `NullRagPort`." Risk 2 concedes "every non-recipe workflow routes to LLM in Phase 8." So in Phase 8, the system makes a *recipe-or-LLM* decision; RAG is structurally unreachable with real data. The exit criterion says "the planner makes the recipe/RAG/LLM decision and the chosen path is logged." A planner that can never choose RAG (because the only RAG port always returns empty) does not "make the recipe/RAG/LLM decision" — it makes two-thirds of it. Calling the stub "honest" does not make the exit criterion met; it makes the gap *documented*. The design has confused disclosing a gap with closing it.

4. **The three-node Supervisor LangGraph is justified by a Phase-9 need and a `design.md §1` citation that the design treats as load-bearing without quoting it.** §Supervisor Tradeoffs: a three-node graph "is arguably overkill versus a plain async function. I keep it a graph because (a) Phase 9 wraps each LangGraph step in a Temporal Activity... and (b) `design.md §1` is explicit that the Supervisor is a LangGraph node." Open Question 3 then re-opens it ("Should the Supervisor be a LangGraph graph or a plain async function"). The design simultaneously commits to the graph *and* lists the commitment as unresolved. Worse: building the graph "for the Phase 9 Temporal seam" is speculative generality — the toolkit's "premature pluggability" sin applied to graph topology. Phase 9 will *wrap* whatever Phase 8 ships; it does not need Phase 8 to pre-shape itself into three nodes. A plain function is wrappable too.

5. **`HotViewKey.schema_version` is an `int`, and the design relies on it for shape-eviction — but a slice's *shape* is not versioned by a single global integer.** §HotViewStore: "the schema version is *in* the key so a slice-shape change evicts on read per ADR-0013." A single `schema_version: int` across all four slices means changing the shape of `risk_flags` alone forces a version bump that cold-evicts `available_skills`, `entrypoint`, and `confidence_summary` too — every slice for every repo. ADR-0013 says "when the slice shape changes, the version bumps and stale entries are evicted on read" — but a per-*store* integer cannot express per-*slice* shape evolution. The design picked the coarsest possible versioning granularity and called it ADR-0013 compliance.

### Hidden assumptions

1. **Assumption:** `codegenie.plugins.resolver.resolve(...)` has the signature `resolve(task, languages, build_systems)` and returns something the Supervisor can wrap as `PluginResolution(primary, chain, matched_by)`. **What breaks if it's wrong:** The actual signature is `resolve(registry: PluginRegistry, scope: PluginScope) -> PluginResolution` (resolver.py line 485), and `PluginResolution` is *already* the public discriminated-union return type (`ConcreteResolution | UniversalFallbackResolution`). The design re-defines a `PluginResolution` Pydantic model with fields `primary`, `chain`, `matched_by` — a *name collision* with the existing public type, which already has `kind`, `plugin`, `extends_chain`, `matched_scope`, `composed_tccm`, `composed_adapters`. The design's "delegate entirely to the shipped resolver" is undermined by the design not knowing the shipped resolver's types — and shipping a second type with the same name is exactly the silent-edit / convention-fork the project forbids (CLAUDE.md Rule 11, "surface conflicts, don't average them").

2. **Assumption:** A single Redis `GET` over a "local-network socket" is ~0.3–1 ms and clears the 50ms SLO "by 25×." **What breaks if it's wrong:** The 50ms p95 exit criterion is end-to-end "hot views serve agent context" — not "one `redis-py` GET." Risk 1 even concedes reviewers may read it as a wider SLO. If "serve agent context" includes `get_all` (4 keys) + Pydantic deserialization of four slices + the planner consuming them, and if Phase 9's eventual worker pool puts Redis on a *different host* (not a local socket), the 25× headroom is a single-developer-laptop number. The design's own Blind Spot ("Concurrency under portfolio scale... this design does not model connection pooling") concedes the number does not survive contact with the deployment the metric is actually for.

3. **Assumption:** Putting `BundleBuilder` in `codegenie.tccm` is "cohesion" because the builder consumes TCCM models. **What breaks if it's wrong:** The builder *also* consumes `RepoContext`, the resolver's output, language search adapters, the `ContextStore`, and `IndexHealthProbe` confidence. It is the resolver's *downstream consumer*, not the TCCM model's sibling. Placing a multi-input orchestration component inside the data-model package it happens to read one of its inputs from is cohesion-by-coincidence. The design's Open Question 1 admits "the cohesion argument is strong but not absolute" — it is in fact weak.

### Things this design missed

- **Multi-plugin `Both` coordination (ADR-0042)** — not mentioned. See Roadmap critique 1. For a "best-practices, traces-to-the-ADRs" design, missing an `Accepted` ADR that says "Phase 8 must model parent workflow plus plugin work items" is a coverage failure.
- **Redis integrity / tampering** — the design's failure table handles "Redis unreachable" but not "Redis returns wrong bytes." A best-practices design that prides itself on `mypy --strict` and typed everything still trusts an out-of-process cache's contents unconditionally.
- **It missed that the resolver already composes the TCCM and adapters** — so the `BundleBuilder`'s "union TCCMs over resolved chain" step (§architecture diagram, step 2) is re-doing the resolver's `compose_extends_chain`. The design's whole "wire existing seams" virtue is undercut by re-implementing one.

## Cross-design observations

### Where do the three disagree?

| Dimension | Performance picks | Security picks | Best-practices picks | What's at stake |
|---|---|---|---|---|
| Hot-view slice set | Six slices (4 ADR-0013 + 2 derived: `plugin_resolution`, `context_bundle_skeleton`) | Four ADR-0013 slices, each HMAC-tagged | Four ADR-0013 slices, plain | Whether ADR-0013 gets amended; whether resolution is cached at all |
| Redis trust posture | Trusted on read; degrade only on *unavailable* | Untrusted on read; HMAC-verify every value; fail closed to cold storage | Trusted on read; fallback only on *unreachable* | A writable-Redis compromise: latency cost vs. context-poisoning |
| Routing-decision log | Typed `RoutingDecided`/`RoutingDescended` events on the existing event log | Event-sourced, BLAKE3-chained, KMS-signed `PlannerDecisionLog` — a new store | `planner.route.decided` into the existing audit sink; Phase 9 makes it a projection | Whether Phase 8 front-runs Phase 9 / ADR-0034 |
| Supervisor shape | Functional core + thin shell (`dispatch`) | "Trusted core," smallest code surface, contract-fenced | Three-node LangGraph (resolve → build_bundle → dispatch) | Speculative Phase-9 generality vs. a plain function |
| LLM credential | Not addressed (Phase 8 adds `$0.00`, no key) | Per-workflow `LlmCapability`, secrets-broker-minted, KMS-adjacent, TTL'd, `revoke()`d | `LeafLlmPort` Protocol; key handling unspecified | Whether Phase 8 builds a secrets subsystem |
| MCP server hardening | Stdio, no auth, in-memory index; ADR-0023 deferred | seccomp-bpf + read-only bind-mount + `no_new_privileges` + zero-net | Stdio, no auth, transport-agnostic core class; ADR-0023 deferred | Whether OS-level confinement is in Phase 8 scope (and runnable on macOS dev) |
| `route()` placement | A pre-selector in the Supervisor in front of Phase 4's `FallbackTier` | Inside the plugin subgraph; routing on structural signals only | One `PlannerNode` inside each plugin subgraph | Whether routing is Supervisor-level or subgraph-level — a real architectural fork |

### Which disagreement matters most for this phase?

**The routing-decision log: does Phase 8 build the event-sourced store, or emit into the existing audit sink and let Phase 9 project it?** This is the disagreement most likely to produce a wrong final design, because the security design's position is *seductive* — "log on every workflow by construction" sounds like exactly what the exit criterion wants — but it directly contradicts an explicit roadmap commitment. Roadmap Phase 9 names "plugin-resolution records" as one of the structures that "migrate to event-stream projections from this point [Phase 9]." If the synthesizer adopts security's `PlannerDecisionLog`, Phase 8 builds the canonical event log a phase early, and Phase 9's "lands operationally" sentence becomes a lie — Phase 9 would be *re-pointing* an already-built store, not landing it. The synthesizer must rule: Phase 8 emits a typed audit event (best-practices/performance position) and Phase 9 owns event sourcing, OR the roadmap's Phase 9 boundary is wrong and needs an explicit amendment. It cannot quietly average the two — an event log that is "sort of event-sourced but not the canonical one" is the worst outcome.

### Where do all three quietly agree on something questionable?

1. **All three treat multi-plugin `Both`-workflow coordination as out of scope or barely mention it — but ADR-0042 (`Accepted`) says "Phase 8 must model parent workflow plus plugin work items."** Performance never mentions it. Security flags it in Blind Spot 3 and does not design it. Best-practices does not mention it at all. The roadmap's own Phase 10 entry says the `Both` case "escalates as a multi-plugin coordination candidate to Phase 8's Planner." Three designs, one omitted `Accepted` ADR. This is the single most dangerous shared blind spot — the synthesizer cannot fix by merging, because none of the three has the material.

2. **All three assume the plugin/TCCM/adapter substrate is finished and stable.** Performance pre-renders `composed_tccm` as a slice; security validates a fully-fielded `TCCM` with `budget` clamps; best-practices wires `codegenie.tccm`'s "five `DerivedQuery` variants." But the resolver's actual composition output, `ComposedTccm`, is an explicitly-documented placeholder ("Step 3 (S3-01) replaces this with the real `TCCM` Pydantic per Phase-3 ADR-0004"). None of the three checked whether the real `TCCM` model and the five derived-query variants have actually shipped. If they have not, every design's Bundle Builder is building on sand.

3. **All three accept "<50ms p95" as a hot-view *read* SLO and design the routing decision to sit outside it — but none questions whether that is what the roadmap means.** The roadmap exit criterion: "Hot views serve agent context in <50ms p95." Best-practices explicitly narrows this to a `HotViewStore.get_all` read SLO and flags the narrowing as Risk 1. Performance budgets "Supervisor + context-bundle assembly ≤ 60 ms" — *separately* from the 50ms. Security spends "~0.3ms" of the budget on HMAC. All three quietly agree the 50ms covers only the Redis read and not the resolution, bundle hydration, or routing. That may be right — but three designs converging on the *convenient* reading of an ambiguous exit criterion, each citing the others' framing, is not verification. If a reviewer reads "serve agent context" as "from workflow trigger to context-in-hand," all three miss the bar.

## Roadmap-level critiques

1. **Does this phase set up problems for later phases?** Yes, two. **(a)** By omitting ADR-0042 multi-plugin coordination, all three designs ship a Supervisor / `SupervisorDecision` / `PlannerDecisionLog` modeled for *single-plugin* dispatch only. ADR-0042 §Consequences: "Phase 8 must model parent workflow plus plugin work items." A Phase 8 that ships single-plugin-only forces Phase 10 (which surfaces `Both` as "a coordination candidate to Phase 8's Planner") to either retrofit parent/child workflow modeling into a shipped Supervisor — a non-additive edit — or stall. **(b)** The security design's premature `PlannerDecisionLog` would make Phase 9's "ADR-0034 lands operationally" a no-op or a contradiction; Phase 13 (cost ledger) and Phase 11 (Stage 7 Learning) are roadmap-committed to be *projections* of the Phase 9 canonical log — if Phase 8 builds a *different* event-sourced log, those projections have two sources of truth.

2. **Does it rely on something an earlier phase didn't actually establish?** Yes. All three rely on a finished `TCCM` model with priority bands and `budget` and five typed `DerivedQuery` variants, and on a resolver that hands back a composable bundle skeleton. The shipped `resolver.py` returns `ComposedTccm` — a placeholder whose docstring defers the real model to Phase-3 story S3-01 / ADR-0004. Phase 6's final-design confirms Phase 3's plugin (`vulnerability-remediation--node--npm`) exists, but Phase 8's designs assume the *TCCM-with-derived-queries* layer (ADR-0029/0030) is production-ready. The synthesizer must verify S3-01 actually shipped the real `TCCM`; if it did not, Phase 8 cannot build a `BundleBuilder` at all. Additionally, the security design relies on a secrets broker, a KMS, and mTLS PKI that *no* phase 0–7.5 establishes and Phase 8's roadmap entry does not introduce.

3. **Does it violate any load-bearing commitment from production/design.md §2 or CLAUDE.md?** Three concerns. **(a)** Commitment §5 ("Extension by addition — no *silent* edits"): the best-practices design ships a new `PluginResolution` Pydantic model that *collides by name* with the existing public `PluginResolution` discriminated union in `resolver.py`. That is not a loud, compiler-policed additive edit — it is a silent semantic fork of a public type, exactly what §5 and CLAUDE.md Rule 11 forbid. **(b)** Commitment §5 again: the performance design's two extra hot-view slices require an ADR-0013 amendment the design did not write — "a bounded additive core primitive is allowed only under explicit ADR control"; the design ships the primitive and *defers* the ADR to an open question. **(c)** Commitment §1 ("No LLM in the gather pipeline"): the performance design fires `HotViewRenderer` as "the gather's final step" / "the gather pipeline's tail" and gives it pure render functions — fine — but the design also says the renderer is "triggered off probe re-runs" *and* is "part of the gather pipeline." If the renderer is genuinely *inside* the gather pipeline's import closure, every dependency it pulls (and any future LLM-adjacent dep) is now fence-policed by `test_pyproject_fence.py`. None of the three designs checks whether their new packages (`codegenie.hotviews`, `codegenie.supervisor`, `codegenie.mcp`) land inside or outside the gather-pipeline runtime closure the fence locks. Best-practices adds `import-linter` contracts for *LLM SDKs* but not for the gather-closure boundary.

## Design-pattern critiques (cross-cutting)

### Misapplied patterns (with concrete victim)

- **Security — "Command pattern" for the routing decision.** Security's pattern table claims each routing decision is "a `Command` whose `execute()` is the append + transition." Best-practices' "Patterns deliberately avoided" section names this exact move and rejects it correctly: "`RouteDecision` is *data* (a logged record), not a deferred-execution object; making it a `Command` with an `execute()` would be ceremony." A `Command` exists to defer, queue, undo, or parameterize an invocation. A routing decision that is computed and immediately acted on is not deferred execution — it is a function call. Security dressed "append then transition" in GoF vocabulary to make atomicity sound like a pattern. The victim is the reader who now thinks there is a command bus.
- **Performance / Best-practices — "Chain of responsibility (preserved)."** Both claim the recipe→RAG→LLM chain *is* chain-of-responsibility. It is a fixed three-step pipeline with a fallthrough. Chain of responsibility is about a *runtime-variable, decoupled* set of handlers where the sender does not know which handler responds. Three hardcoded steps in a fixed order, where the caller knows exactly the three and their order, is a pipeline / an `if-elif-else`. Best-practices is at least honest enough to also call it "Pipeline" and reject a registry — but labeling a fixed pipeline "Chain of responsibility" inflates it.
- **Security — "Hexagonal / ports & adapters" with the Skills server as a Port.** The claim: "every trust-boundary crossing is a Port." But the security design then has the Skills *adapter* "spawn the seccomp'd process" and the Redis adapter "do HMAC verify." A Port/Adapter's job is to translate between the core's domain language and an external technology. Loading a seccomp-bpf profile and spawning an OS process with bind-mounts is *infrastructure provisioning*, not adapter translation. Smuggling process-supervision and kernel-security-policy into an "adapter" is the hexagonal claim that "smuggles I/O into the core" inverted — it smuggles ops into the adapter and calls it ports-and-adapters cleanliness.

### Missed patterns (with concrete location)

- **All three: no design models the `Both` / multi-plugin case as a sum type at the Supervisor's output.** The performance design's `SupervisorDecision = Dispatched | EscalatedToHITL` is a two-variant union. ADR-0042 demands a third state: a parent workflow with multiple plugin work items. The obvious missed pattern is *making the multi-plugin state a first-class variant of the dispatch sum type* — `Dispatched | MultiPluginDispatch | EscalatedToHITL`. All three reached for tagged unions everywhere else and then modeled the dispatch outcome as if `Both` did not exist.
- **Best-practices: `HotViewKey` with a single `schema_version: int` misses per-slice versioning.** The location is `HotViewKey.schema_version`. A slice's shape is a per-slice contract; the natural model is a version *per slice name* (a `Mapping[HotViewSliceName, int]` or a version baked into each slice's own Pydantic model). The design picked a scalar where a small map belonged — the inverse of primitive obsession, call it scalar-where-a-map-belongs.

### Pattern claims that don't survive scrutiny

- **Performance: "Pre-computed read model / event-sourced projection (off the gather as the 'event')."** Calling the gather "the event" and the hot views "a projection" is event-sourcing cosplay. There is no event *log*; there is a gather that overwrites Redis. A projection is rebuilt by replaying an event stream. The performance design explicitly has *no* AOF, *no* persistence, and reconstructs Redis from "the next gather." That is a cache with gather-driven invalidation — which is fine and is what ADR-0013 says — but it is not an event-sourced projection, and the label imports correctness guarantees (replayability, an immutable log) the design does not provide.
- **Security: "Smart constructor" for `ContextBundle` — claimed unforgeable, but the design never shows the raw Pydantic constructor is actually suppressed.** §BundleBuilder: "the raw Pydantic constructor is not part of the public surface." A Pydantic model's `__init__` is *always* callable — `ContextBundle(**anything)` works unless the design adds real enforcement (a private model with a module-private name, a `__init_subclass__` guard, or a separate frozen value type the constructor returns). "Not part of the public surface" is a docstring convention, not a type-system guarantee. The design's own pattern table says "an unvalidated `dict` reaching a prompt is a compile-time error" — but nothing shown makes `ContextBundle.model_construct()` or a direct call a compile-time error. The smart-constructor claim is asserted, not demonstrated.
- **Best-practices: "Composition over inheritance: the Supervisor holds a `PluginRegistry` and a `BundleBuilder`; it subclasses nothing."** Nobody proposed subclassing. Claiming "composition over inheritance" as an applied pattern when inheritance was never on the table is pattern-table padding — it is a non-decision dressed as a decision.

### Anti-patterns from the toolkit's "flag on sight" list

- **Premature pluggability — best-practices' three-node LangGraph Supervisor.** A three-node graph (`resolve → build_bundle → dispatch`) for a strictly sequential, never-branching flow is graph machinery for a function. The justification is "the Phase 9 Temporal seam" — speculative generality for a phase away. The design itself calls it "arguably overkill."
- **Stringly-typed-adjacent — performance's `plugin_resolution` "pre-serialized blob."** The performance design stores resolution as "a pre-serialized `ConcreteResolution`/`UniversalFallbackResolution`" JSON blob in a Redis hash field and re-parses it on the warm path. Serializing a typed discriminated union to an opaque blob and re-hydrating it on every workflow read is a typed contract laundered through a `str` — the type safety the resolver's discriminated union buys is dropped at the Redis boundary and reconstructed on faith.
- **Name collision as a silent fork — best-practices' second `PluginResolution`.** Already covered in Roadmap critique 3(a). The toolkit's "flag on sight" spirit: a new public type that shadows an existing public type of the same name in the same project is a latent import-ambiguity and review-confusion bug.
- **Speculative subsystem — security's secrets broker / KMS / mTLS apparatus.** Building a credential-management subsystem, a KMS integration, and a network-segmentation model in a phase whose roadmap tooling list is three lines and whose only LLM call is a leaf node is the security-lens form of gold-plating. The toolkit flags "abstraction for single-use code"; this is infrastructure for zero-current-use threats whose enabling phase (9, identity) has not arrived.
