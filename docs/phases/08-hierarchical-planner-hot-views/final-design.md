# Phase 08 — Hierarchical Planner + pre-rendered hot views: Final design

**Status:** Design of record (synthesized from three competing designs + critique).
**Synthesized by:** Graph-of-Thought synthesizer subagent
**Date:** 2026-05-21
**Sources:** `design-performance.md` · `design-security.md` · `design-best-practices.md` · `critique.md`

## Lens summary

Phase 8 adds the **Supervisor** (the planning layer that sits above every workflow), a **Bundle Builder seam** that turns a resolved plugin's TCCM into the worker subgraph's initial context, a **Planner node** that makes the recipe/RAG/LLM routing decision, the four **Redis hot views**, and one **MCP Skills stdio server**. The synthesis is deliberately *thin*: it `wires` shipped seams rather than rebuilding them. The critic's most important finding is decisive — `codegenie.plugins.resolver` *already* returns a public `PluginResolution` discriminated union with `composed_tccm` and `composed_adapters` pre-merged, a `BundleBuilder` + `Bundle` *already* ship (Phase 3 S3-04), and `codegenie.plugins.events` *already* provides a hash-chained append-only event log with `PluginResolved`/`BundleBuilt` variants. So Phase 8 builds **four genuinely new packages** (`codegenie.supervisor`, `codegenie.planner`, `codegenie.hotviews`, `codegenie.mcp`), reuses every plugin/TCCM/adapter/event seam through its public surface, and explicitly rejects the heavy speculative apparatus (a secrets-broker/KMS subsystem, seccomp confinement, an event-sourced store that front-runs Phase 9). It takes the **performance lens's hot-path discipline** (functional core, gather-tail rendering, branchless warm path), the **security lens's trust posture at the one boundary that is real this phase** (untrusted-on-read Redis, sealed `ContextBundle`, manifest validation as fail-closed registry load), and the **best-practices lens's shape** (flat packages, reuse, table-driven dispatch) — and adds one thing none of the three did: it models the ADR-0042 `Both`/multi-plugin case as a first-class variant of the Supervisor's output sum type, because ADR-0042 is `Accepted` and names Phase 8 as the phase that must model it.

## Goals (concrete, measurable)

- **The Supervisor never becomes the throughput ceiling.** [P] Warm-path Supervisor overhead (Redis read + parse + `route()`) is budgeted at **< 5 ms p95**; the exit-criterion `<50ms p95` is satisfied with wide margin (see "Exit-criterion scope" below). [synth]
- **`<50ms p95` exit criterion — scope pinned.** [synth] The criterion measures **hot-view serving**: from the planner asking for a slice to the typed slice in hand — i.e. `HotViewStore.get_all(repo)` (one Redis pipeline of the four ADR-0013 slices) + Pydantic deserialization. It does **not** cover plugin resolution, Bundle building, or the routing decision — those are upstream of the hot-view read and bounded separately (resolution <5 ms; Bundle building is dominated by ADR-0030 graph queries and is explicitly outside any 50 ms budget). This is the reading all three designs converged on; the synthesis makes it the *definition*, not a convenient assumption, and an e2e test measures exactly `get_all`. [B]/[P]
- **Phase 8 adds `$0.00` of LLM spend.** [P]/[B] The Supervisor, Bundle Builder, hot views, routing decision, and MCP server are 100% deterministic. The only LLM call in Phase 8 is the Planner's `llm_fallback` leaf node behind a `LeafLlmPort` — and only on a recipe-and-RAG miss. `route()` *saves* tokens: every recipe-route avoids an LLM call. [synth]
- **The routing decision is logged on every workflow — by construction.** [S]/[B] Every workflow emits exactly one `RouteDecided` event into the **existing** `codegenie.plugins.events` hash-chained log before the routing transition completes. A static test asserts no routing code path can reach a transition without the append. [synth]
- **Public API surface ≤ 24 exported names** across the four new packages; **≥ 90% line coverage** on the new packages (above the 85% gate); **100% branch coverage** on the two exit-criteria-bearing functions (`PlannerNode.route` and the hot-view `invalidates` matcher); **cyclomatic complexity ≤ 8** per function (`ruff` `C901`). [B]
- **One new runtime service** (`redis:7-alpine` in `docker-compose.yml`) and **two new runtime deps** (`redis-py`, `mcp` SDK). No KMS, no secrets broker, no Postgres (Phase 9 owns Postgres). [B]/[synth]
- **Redis is untrusted on read.** [S] Every hot-view read is integrity-checked against the gather identity that produced it; a failed check falls through to cold storage (correct, slower) — a writable-Redis compromise is a *latency* cost, never a *context-poisoning* cost. The mechanism is scoped to be deployable on the project's actual dev substrate (no KMS dependency) — see HotViewStore. [synth]
- **Multi-plugin `Both` coordination is modeled, not deferred.** [synth] The Supervisor's output is a three-variant sum type `Dispatched | MultiPluginDispatch | EscalatedToHITL`; `MultiPluginDispatch` carries a parent workflow id and an ordered tuple of plugin work items, satisfying ADR-0042's "Phase 8 must model parent workflow plus plugin work items." Phase 8 *models and dispatches* the parent/child shape; the deep sequencing logic across PRs is exercised in Phase 10 when Assessment first produces `Both` candidates.

The shape: a Supervisor LangGraph with three nodes (resolve, build_bundle, route), a Planner that is one node, a hot-view layer that is one store + one renderer, and one MCP process with two read-only tools. The load-bearing move is **reuse**: resolution, TCCM composition, adapter composition, Bundle building, and the event-log substrate already ship — Phase 8 wires them and adds only what is genuinely new.

## Components

### Supervisor — `codegenie.supervisor`

- **Provenance.** [B] shape (three-node LangGraph) + [P] hot-path discipline (functional core) + [synth] `MultiPluginDispatch` variant.
- **Purpose.** The planning layer above the state machines: resolve the matching plugin, build the Context Bundle, make and log the routing decision, and dispatch into the plugin subgraph. The per-workflow tollbooth — so it must be a fast, small, audited toll.
- **Interface.**
  - `build_supervisor_graph(*, plugin_registry, bundle_builder, planner_node, checkpointer=None) -> CompiledStateGraph`.
  - `SupervisorState` — frozen Pydantic LangGraph state: `workflow_id: WorkflowId`, `task_class: TaskClassId`, `repo_id: RepoId`, `resolution: PluginResolution | None`, `bundle: ContextBundle | None`, `decision: SupervisorDecision | None`.
  - **Output is a closed sum type** `SupervisorDecision = Dispatched(plugin, version, bundle, route) | MultiPluginDispatch(parent_workflow_id, work_items: tuple[PluginWorkItem, ...]) | EscalatedToHITL(reason, evidence)`. `match` + `assert_never` forces every dispatch site to handle all three. `EscalatedToHITL` and `MultiPluginDispatch` are *variants*, never `None` or a boolean flag.
- **Internal design.**
  - **Plugin resolution is delegated entirely** to the shipped `codegenie.plugins.resolver.resolve(registry, scope) -> PluginResolution`. Phase 8 does **not** re-implement matching, wildcard precedence, or `extends`-chain walking, and does **not** define a new `PluginResolution` type — it consumes the existing public discriminated union (`ConcreteResolution | UniversalFallbackResolution`). The `UniversalFallbackResolution` variant becomes a logged `EscalatedToHITL`; a `ConcreteResolution` proceeds to bundle building.
  - **`Both`/multi-plugin dispatch.** When the trigger carries a `vuln.provenance` of kind `both` (ADR-0038/0042 — the trigger field is set by Phase 10 Assessment, or by the CLI for a manual `Both` run), the Supervisor resolves *each* implicated task class, and emits `MultiPluginDispatch` with one `PluginWorkItem(plugin, bundle, route)` per resolved plugin under a shared `parent_workflow_id`. Phase 8 owns the *modeling and parent/child dispatch*; the Planner sequences the work items and tracks cross-PR status. The deep coordination logic is exercised once Phase 10 produces real `Both` candidates — Phase 8 ships the typed shape so Phase 10 is an additive consumer, not a non-additive retrofit (ADR-0042 §Consequences).
  - **Functional core / imperative shell.** `decide(trigger, resolution, bundle, route_decision) -> SupervisorDecision` is pure and exhaustively unit-testable with no Redis and no I/O. The shell is the three LangGraph nodes; the impure surface is the resolver call, the `BundleBuilder.build` call, and the subgraph handoff.
  - **Three-node LangGraph, not a plain function.** A flat `resolve → build_bundle → route` graph. This is deliberately the *Phase-9 Temporal-Activity seam*: Phase 9 wraps each LangGraph node in a Temporal Activity, and `design.md §1` frames the Supervisor as a graph node. The cost is ~30 lines of builder boilerplate — see the conflict table for why this beats "plain function now, refactor in Phase 9."
- **Why this choice over the alternatives.** Conflict-resolution row "Supervisor shape" — the three-node graph ([B]) wins over [P]'s thin functional shell and [S]'s "smallest trusted core" because the graph *is* the Phase-9 seam and `design.md §1` mandates it; the functional-core discipline is folded in (`decide()` is pure) so the [P] benchability win is kept without the [P] shape. The critic calls the graph "premature pluggability"; the synthesis accepts the graph anyway because LangGraph is already a runtime dep since Phase 6 and the node boundary is exactly what Phase 9 needs — this is *forward-compat with a named consumer one phase away*, not speculative generality.
- **Tradeoffs accepted.** ~1–2 ms of LangGraph framework overhead per workflow; ~30 lines of builder boilerplate. The Supervisor is a single point of trust — paid for with the smallest possible code surface and a contract-snapshot test on `SupervisorDecision`.

### BundleBuilder reuse + `ContextBundle` sealing — `codegenie.plugins` (existing) + `codegenie.supervisor`

- **Provenance.** [B] "reuse the shipped seam" (decisive — `BundleBuilder` ships) + [S] sealing discipline, scoped down.
- **Purpose.** Turn the resolved plugin chain's composed TCCM into the worker subgraph's initial `ContextBundle` by dispatching `must_read`/`should_read`/`may_read` derived queries through the plugin's language search adapters.
- **Interface.** Phase 8 **reuses the shipped `codegenie.plugins.BundleBuilder`** (S3-04 — GREEN): `build(resolution, repo_ctx, vuln, vuln_index) -> Bundle`. Phase 8 does **not** create a new Bundle Builder, does **not** create an `AdapterDispatcher` (the resolver already returns `composed_adapters` / `composed_dispatch` — pre-merged, last-wins per ADR-0031), and does **not** re-walk the `extends` chain. The Supervisor's `build_bundle` node is a *thin call* into the shipped builder.
- **Internal design.**
  - The shipped `BundleBuilder` already: iterates `must_read`/`should_read`/`may_read`; dispatches through the typed `AdapterDispatch` seam; applies declarative serial fallback on `AdapterConfidence` `Degraded`/`Unavailable` (ADR-0008/0030/0032); and emits `BundleBuilt` into the hash-chained event log.
  - **`ContextBundle` sealing.** Phase 8's one *additive* contribution at this boundary: the worker-subgraph entry signature accepts only a `ContextBundle` value — never a `dict`. `ContextBundle` (the shipped `Bundle`, re-exported as the subgraph contract type) is `frozen=True` and carries `BundleProvenance` (which queries fed it, downgrades, truncations). The "the LLM only ever sees typed, validated context" property is a **type-system fact** at the subgraph boundary, not a code-review hope.
  - **What the synthesis explicitly does NOT do.** Security's "BundleBuilder never re-reads raw repo bytes" claim is *rejected as self-contradictory* (the critic's attack #3 on the security design is correct — derived queries exist precisely to select repo files the agent then reads). The honest framing: the Bundle *does* carry repo-derived content, the gather sanitizer already scrubbed absolute paths and secret-shaped fields at gather time, and the Bundle Builder's `Bundle`/`BundleEntry` types carry that content typed and provenance-stamped. There is no second secret-rejection pass invented in Phase 8 — the shipped sanitizer is the boundary. A `contains_repo_content` provenance flag on `ContextBundle` lets a downstream LLM-fallback node fence repo text as untrusted data; Phase 8 does not own output-side injection defense (Phases 4/5 gates do).
- **Why this choice over the alternatives.** Conflict-resolution row "Bundle Builder ownership" — reuse the shipped `codegenie.plugins.BundleBuilder` ([B] thesis, corrected) beats best-practices' *own* proposal of a new `BundleBuilder` in `codegenie.tccm` (the critic showed that proposal mis-modeled the resolver output) and beats security's invented re-read-free builder. Commitment §5 ("no silent edits / no convention forks") vetoes building a *second* Bundle Builder when one ships.
- **Tradeoffs accepted.** Phase 8 inherits whatever `Bundle`-shape limitations S3-04 shipped; if the subgraph needs a field the shipped `Bundle` lacks, that is a loud, ADR-controlled additive field on the existing model — not a fork. The `ComposedTccm` placeholder in `resolver.py` is a *resolver-internal* concern: the shipped `BundleBuilder.build` consumes `resolution.composed_tccm` with the real `must_read`/`should_read`/`may_read` bands (`codegenie.plugins.tccm.TCCM`), so Phase 8's Bundle path is not blocked by the placeholder. See Open Questions for the one verification the implementer must do.

### PlannerNode — recipe / RAG / LLM routing — `codegenie.planner`

- **Provenance.** [B] (ports, `StrEnum` route, fixed pipeline) + [P] (pure, deterministic, cost-ascending tier order) + [S] (route on structural signals only).
- **Purpose.** Inside the dispatched plugin's subgraph, decide whether this workflow enters at the recipe tier, the RAG tier, or the LLM tier — and **log the decision on every workflow** (exit criterion 1).
- **Interface.**
  - `PlanningRoute(StrEnum)` — `RECIPE | RAG | LLM`.
  - `RouteDecision` — frozen Pydantic: `route: PlanningRoute`, `reason: str`, `confidence: Confidence`, `candidates_considered: tuple[str, ...]`.
  - `PlannerNode(*, recipe_port: RecipeMatchPort, rag_port: SolvedExampleRagPort, llm_port: LeafLlmPort)`; `async route(bundle: ContextBundle, hot_views: HotViewStore) -> RouteDecision`.
- **Internal design.**
  - **A fixed three-step pipeline** (not "chain of responsibility" — see Design patterns): try recipe, then RAG, then LLM; first hit wins; fallthrough is LLM. Implemented as an ordered `tuple` of `(PlanningRoute, port-callable)` iterated in order — not a class hierarchy, not a registry (exactly three steps, fixed by ADR-0011; a registry here is premature pluggability).
  - **The decision is deterministic and structural.** Recipe existence is a key-membership test against the plugin's recipe registry (`codegenie.plugins.recipe_registry` — content-addressed). RAG non-emptiness for the fingerprint is a cheap count query. **Neither consults an LLM** — Rule 5 applied: a recipe-existence check is plain code, not a judgment. An LLM "router" would cost a token call per workflow and is rejected outright.
  - **`route()` picks the ENTRY tier; Phase 4's `FallbackTier` still owns descent.** The Planner pre-selects the cheapest tier that can succeed so a recipe-eligible workflow does not pay the RAG round-trip just to discover a recipe existed. On a recipe *miss at apply time*, `FallbackTier` descends recipe→RAG→LLM exactly as Phase 4 designed — Phase 4 is untouched (extension by addition). The exit criterion is satisfied by the `RouteDecided` event *plus* any `RouteDescended` events: the audit shows prediction and outcome.
  - **The three collaborators are Ports** (`Protocol` classes — hexagonal): `RecipeMatchPort`, `SolvedExampleRagPort`, `LeafLlmPort`. `LeafLlmPort` is the *only* LLM seam in Phase 8; its concrete adapter (Agents SDK, ADR-0020) is injected so the routing logic itself is LLM-free and `fence`-clean. `import-linter` forbids any LLM SDK from `codegenie.planner.routing`.
  - **Phase 8's RAG port is a documented `NullRagPort`.** The Knowledge Graph arrives in Phase 11; in Phase 8 `SolvedExampleRagPort` returns "no hit". The three-step *shape* is correct from day one and the RAG-hit branch is exercised by a fake port in tests. This is disclosed honestly — see Risks; the exit criterion is met because the *router makes and logs a recipe/RAG/LLM decision on every workflow* (the machinery, the routing logic, and the audit are all real and tested), and the RAG branch is structurally present and unit-covered — Phase 11 swaps the null adapter for the KG-backed one with zero routing-code change.
- **Why this choice over the alternatives.** Conflict-resolution row "route() placement" — the Planner as one node *inside the plugin subgraph* ([B]/[S]) beats [P]'s "pre-selector in the Supervisor in front of FallbackTier." Routing reads recipe applicability that depends on the resolved plugin chain, and Phase 4's `FallbackTier` lives in the subgraph — keeping the Planner in the subgraph keeps routing next to the chain it pre-selects and avoids splitting routing knowledge across two layers. [P]'s throughput point (skip the RAG round-trip on a recipe-route) is *kept*: the node still pre-selects the entry tier.
- **Tradeoffs accepted.** The RAG branch is fake-port-tested until Phase 11. `route()` can mispredict (recipe in the index but stale) — the cost is one wasted recipe-match attempt, and the `RouteDecided`/`RouteDescended` event pair makes the misprediction rate a measured number Stage 7 can tune.

### HotViewStore + HotViewRenderer — `codegenie.hotviews`

- **Provenance.** [B] (thin redis-py wrapper, `HotViewKey`, pure renderer, `invalidates` matcher) + [P] (gather-tail rendering, branchless read, no TTL) + [S] (untrusted-on-read, fail-closed to cold storage) + [synth] (per-slice versioning; gather-id integrity instead of HMAC/KMS).
- **Purpose.** Serve the four ADR-0013 agent-context slices from Redis in `<50ms p95` (exit criterion 2); re-render them as a background task when a probe re-run changes the underlying `RepoContext`.
- **Interface.**
  - `HotViewKey` — frozen Pydantic: `repo_id`, `slice_name: HotViewSliceName` (a closed `Literal` of the four slices), `slice_schema_version: int`; `.redis_key() -> "hotview:{repo}:{slice}:v{n}"`.
  - `HotViewStore(*, redis, slice_schema_versions: Mapping[HotViewSliceName, int])`; `async get(repo, slice_name) -> HotViewSlice | None`; `async get_all(repo) -> Mapping[HotViewSliceName, HotViewSlice]` (one pipelined round-trip).
  - `render_hot_views(repo, repo_context, active_tccms, store) -> RenderReport` — the background-task entry point.
  - `invalidates(probe_outputs) -> set[HotViewSliceName]` — the pure matcher under the cache-invalidation tests.
- **Internal design.**
  - **The FOUR ADR-0013 slices ONLY** — `available_skills`, `entrypoint`, `risk_flags`, `confidence_summary`. The synthesis **rejects** performance's two extra derived slices (`plugin_resolution`, `context_bundle_skeleton`). The critic's attack is decisive: ADR-0013 §Consequences says "adding a slice requires a deliberate ADR amendment," and `context_bundle_skeleton` re-derives what `resolver.resolve()` *already returns for free* (`composed_tccm`/`composed_adapters` — pre-merged). There is nothing slow to pre-render: resolution is `<5 ms` and TCCM composition is *inside* `resolve()`. Caching resolution would be a second invalidation surface for no measured win. If a future phase proves a resolution-cache need, that is a *separate* ADR-0013 amendment with benchmark evidence — Phase 8 does not ship it.
  - **The renderer is a pure function.** `render_hot_views` computes the four slice values from `RepoContext` + the union of `must_read` across `active_tccms` (ADR-0029) — "which slices to render" is *derived from TCCM aggregation*, not a hand-curated list. The shell does one `HSET`.
  - **Per-slice versioning** [synth] — `HotViewKey.slice_schema_version` is resolved per `slice_name` from a `Mapping[HotViewSliceName, int]`, not a single global `int`. The critic's attack on best-practices is correct: one global integer cold-evicts all four slices for all repos when only one slice's shape changes. Per-slice versions let `risk_flags` evolve without touching `available_skills`. A version mismatch on read is treated as a miss → cold path → re-render at the current version (ADR-0013 "evicted on read", made precise).
  - **Gather-driven invalidation, no TTL** (ADR-0013). Each render overwrites; a probe re-run re-renders exactly the slices `invalidates(probe_outputs)` names. Every slice is one atomic Redis write — no torn read.
  - **Untrusted-on-read, fail-closed — but deployable.** [synth, departing from both [P] and [S]] Every value the renderer writes is stamped with the `gather_id` (a content hash of the `RepoContext` it was rendered from — already a first-class identity in the gather/audit layer) and its `slice_schema_version`. On read, the planner checks the `(repo, slice, gather_id, slice_schema_version)` binding; on any mismatch it **discards the Redis value and falls through to cold storage** (the ADR-0013 documented fall-through). This gives security's fail-closed property — a tampered or stale Redis value cannot reach a planner's context — **without** the KMS/HMAC-key/secrets-broker apparatus the critic correctly flagged as undeployable on the project's actual substrate (Phase 8 is local; no KMS, no secrets broker, no mTLS PKI exists before Phase 9). A `gather_id` mismatch is detectable with zero new infrastructure: it is data integrity by content-addressing, the same discipline the cache layer already uses (`cache/keys.py`). A genuine *cryptographic* tamper-evidence story for Redis is correctly Phase 9+ work (when identity and secrets management land) and is recorded as an implied ADR, not built here.
- **Why this choice over the alternatives.** Conflict-resolution rows "hot-view slice set" and "Redis trust posture." Slice set: four slices ([S]/[B]) beats six ([P]) — commitment §5 veto on the un-amended ADR-0013 extension, plus the critic's proof the two slices re-derive resolver output. Trust posture: untrusted-on-read with `gather_id` integrity ([synth]) beats [P]'s trusted-on-read (it has *no* path for Redis *lying*, only Redis *unavailable* — a real gap) and beats [S]'s HMAC/KMS scheme (undeployable this phase; the critic's hidden-assumption #1 on the security design). The synthesis takes security's *property* (fail-closed) via performance's *substrate-honest* mechanism (content-addressed identity).
- **Tradeoffs accepted.** `gather_id` verification adds ~microseconds per read. After a Redis flush every repo takes the cold path once — bounded and self-healing (the cold path backfills Redis); the renderer's gather-tail trigger re-warms repos as they next gather. The cold-path-storm risk is real (see Risks) and is mitigated by, not eliminated by, the self-healing backfill — Phase 9's process supervision is where a warm-up-on-start story belongs.

### SkillsMcpServer — `codegenie.mcp`

- **Provenance.** [B] (transport-agnostic core class, contract snapshot, reuse the skills loader) + [P] (long-lived process, in-memory index built once) — security's seccomp/bind-mount confinement is **rejected** for Phase 8.
- **Purpose.** Serve Skill manifests to the planner over MCP stdio — the first concrete piece of the eventual MCP topology (ADR-0023, `Deferred`).
- **Interface.**
  - `serve_skills_stdio(*, skills_registry) -> None` — the thin MCP-protocol shell.
  - `SkillsMcpServer(*, skills_registry)` — the testable, transport-agnostic core: `list_skills(repo: RepoId) -> list[SkillManifest]`, `get_skill(skill_id: SkillId) -> SkillManifest`.
  - `MCP_SKILLS_CONTRACT: Final[McpServerContract]` — the pinned public tool surface; a snapshot test asserts the live server's advertised tools byte-match it.
- **Internal design.**
  - **Two read-only MCP tools** — `list_skills`, `get_skill` — on an `mcp` SDK `Server` running the stdio transport. **No write tool, no exec tool, no filesystem-path tool.** Skill/plugin IDs are newtypes validated by a regex smart constructor; a traversal-shaped ID (`../../etc/passwd`) fails the newtype before any filesystem touch (this is security's one *cheap, in-scope, substrate-portable* hardening — kept).
  - **Long-lived process, in-memory index built once at startup** ([P]) — walk `plugins/*/skills/`, parse YAML-frontmatter Skills once, build an index keyed by `(task_class, language, build_tool)`. `list_skills` becomes a dict lookup. A scan-per-call server re-pays filesystem+YAML cost on every request.
  - **Progressive disclosure** (commitment §7): tools return *manifests* (id, frontmatter, path), never inlined skill bodies.
  - **Reuses the existing `codegenie.skills` loader** — Phase 8 does not re-implement skill loading.
  - **No OS-level confinement.** seccomp-bpf, `no_new_privileges`, and read-only bind-mounts are **rejected** for Phase 8: seccomp is Linux-only and the documented dev substrate is macOS (the critic's hidden-assumption #2 on the security design — the signature security control does not run on the project's own machines). The process boundary itself is the Phase-8 security gain (it forces the Skills interface to be an explicit, contract-tested port now); OS-level confinement is Phase 9+ deployment-substrate work and is recorded as an implied ADR.
- **Why this choice over the alternatives.** Conflict-resolution row "MCP server hardening" — stdio + in-memory index + contract snapshot + newtype-ID validation ([B]/[P] + one [S] control) beats [S]'s full seccomp/mount confinement (undeployable on macOS dev; out of Phase-8 scope per the roadmap's three-line tooling list) and beats a naive [B] server with no ID validation. ADR-0023 is `Deferred`; Phase 8 ships exactly one MCP server and treats it as the worked example, committing to no topology.
- **Tradeoffs accepted.** An in-memory index means a Skills change needs an MCP-server restart (plugins are in-tree and change at deploy time — ADR-0031 — so this is fine). A long-lived stdio process that dies silently strands leaf nodes — the degradation path is a direct `codegenie.skills` loader read (same data); proper process supervision is Phase 9's Temporal envelope.

### Routing/resolution event emission — `codegenie.plugins.events` (existing, reused)

- **Provenance.** [B]/[P] (emit a typed event into the existing log; let Phase 9 own event sourcing) — security's standalone event-sourced `PlannerDecisionLog` is **rejected**.
- **Purpose.** Make the exit criterion "the chosen path is logged on every workflow" true by construction.
- **Interface.** Phase 8 **reuses the shipped `codegenie.plugins.events`** hash-chained append-only log. It *adds two event variants* to the existing discriminated union: `RouteDecided(workflow_id, route: PlanningRoute, reason, bundle_hash, recipe_match?, rag_top_score?)` and `RouteDescended(workflow_id, from_route, to_route, reason)`. Resolution already emits the shipped `PluginResolved` event. Adding a `Literal`-tagged variant to an existing discriminated union is exactly the loud, compiler-policed additive edit commitment §5 sanctions — not a fork.
- **Internal design.**
  - The `RouteDecided` append is a **precondition of the routing transition**, not a fire-and-forget side effect: the Planner appends the event, then transitions. A static test asserts no routing code path reaches a transition without the append.
  - **Phase 8 does NOT build a new event store.** The critic's attack on the security design is decisive and confirmed against the codebase: `codegenie.plugins.events` *already* ships a hash-chained log with `canonical_json_bytes` + `_chain_step` + `ChainTamperDetected`, and ADR-0034 *explicitly* names `PluginResolved` as a canonical event variant and states event sourcing "lands operationally in Phase 9" with "plugin-resolution records [migrating] to event-stream projections from this point [Phase 9]." A Phase-8 standalone `PlannerDecisionLog` would build the Phase-9 canonical log a phase early under a different name, give Phase 13 (cost ledger) and Phase 11 (Stage 7 Learning) two sources of truth, and make Phase 9's "lands operationally" sentence a contradiction. The exit criterion ("logged on every workflow") is satisfied by *any* typed audit emission with the append-before-transition guarantee — it does not require a KMS-signed standalone store.
- **Why this choice over the alternatives.** Conflict-resolution row "routing-decision log" — emit `RouteDecided`/`RouteDescended` into the existing hash-chained log ([B]/[P]) beats security's standalone event-sourced KMS-signed `PlannerDecisionLog`. This is the critic's "disagreement that matters most"; the roadmap (Phase 9) and ADR-0034 are explicit, and the synthesis follows them rather than averaging.
- **Tradeoffs accepted.** Phase 8's log is workflow/plugin-scoped (the existing `codegenie.plugins.events` shape); Phase 9 re-points it as a projection of the canonical Postgres event log. Building it event-sourced *as a separate store* now is rejected; emitting into the *existing* chained log is the cheap-correct choice and is already the shape Phase 9 adopts.

## Data flow

One representative warm run — `vulnerability-remediation` on a previously-gathered Node/npm repo.

1. **Trigger.** The CLI (Temporal in Phase 9) fires a workflow with `task_class="vulnerability-remediation"`, `repo_id`, an optional `cve_id`, and an optional `provenance` field (set by Phase 10 Assessment). The Supervisor builds `SupervisorState`.
2. **resolve node.** `codegenie.plugins.resolver.resolve(registry, scope)` — *[lens crossing: trust]* the scope derives from a repo the system does not own; the resolver matches `vulnerability-remediation--node--npm`, walks its already-validated `extends` chain, and returns a `ConcreteResolution` with `composed_tccm` + `composed_adapters` pre-merged. A `PluginResolved` event is appended. If `resolve` returned `UniversalFallbackResolution`, the Supervisor would emit `EscalatedToHITL` — a typed variant, logged, never silent. If `provenance` is `both`, the Supervisor resolves each implicated task class and the run becomes a `MultiPluginDispatch`.
3. **build_bundle node.** The Supervisor calls the shipped `codegenie.plugins.BundleBuilder.build(resolution, repo_ctx, vuln, vuln_index)`. The builder iterates `must_read`/`should_read`/`may_read`, dispatches derived queries through the composed adapter table, applies declarative serial fallback on low `AdapterConfidence` (ADR-0008/0030/0032), and emits `BundleBuilt`. The result is sealed as a frozen `ContextBundle` with `BundleProvenance`.
4. **route node (`PlannerNode.route`).** *[lens crossing: hot path]* `route` reads `available_skills` and `risk_flags` via `HotViewStore.get_all(repo)` — one pipelined Redis round-trip, `gather_id`-verified, `<50ms p95` with wide margin. It runs the fixed pipeline: `RecipeMatchPort.match(bundle)` finds a `lodash` bump recipe → **hit**. `RouteDecided(route=RECIPE, reason="recipe lodash-bump matched", ...)` is appended to the hash-chained log **before** the transition (exit criterion 1 satisfied by construction). The LLM port is never touched.
5. **dispatch.** The Supervisor emits `Dispatched(plugin, version, bundle, route=RECIPE)`; the `ContextBundle` becomes the Phase 6 SHERPA subgraph's initial state, with Phase 4's `FallbackTier` entered at the recipe tier.
6. **Subgraph runs** — Phase 6 SHERPA loop, Phase 4 `FallbackTier`, Phase 5 gates — unchanged by Phase 8. If the recipe mismatches at apply time, `FallbackTier` descends and a `RouteDescended` event is appended.
7. **Gather tail (asynchronous, decoupled).** Earlier, when a probe re-ran for this repo, the gather's final step fired `HotViewRenderer` as a detached `asyncio` task: it recomputed exactly the slices `invalidates(probe_outputs)` named and one `HSET` updated Redis, `gather_id`-stamped. The next workflow reads fresh views; the in-flight workflow is never blocked.

## Resource & cost profile

- **Tokens/run added by Phase 8:** **0.** The Supervisor, Bundle Builder, hot views, routing decision, and MCP server are fully deterministic. The only LLM call is the Planner's `llm_fallback` leaf — and only on a recipe-and-RAG miss. With the Phase-8 `NullRagPort`, every non-recipe workflow reaches the LLM (the Phase-6 cost shape, unchanged — Phase 8 adds routing, not new LLM calls).
- **Hot-view read latency (exit criterion 2):** a single `redis-py` `GET` over a local socket ≈ 0.3–1 ms; `get_all` (4 keys, one pipeline) ≈ 1–2 ms; `gather_id` verification ≈ microseconds; Pydantic deserialization of four slices ≈ 0.1–0.4 ms. **`<50ms p95` is met with ~25× headroom** on the project's dev substrate. When Phase 9 puts Redis on a different host, the budget still holds comfortably; the e2e latency test measures `get_all` specifically and is re-run under Phase 9's topology.
- **Warm-path Supervisor overhead:** resolution `<5 ms` (in-memory dict + cycle-bounded `extends` walk — already shipped); `route()` `<1 ms` (index lookups); LangGraph framework overhead ~1–2 ms. Total Supervisor overhead `<5 ms p95` warm.
- **Bundle building:** dominated by ADR-0030 graph queries (dep-graph pennies, tree-sitter ~100 ms, SCIP single-digit-seconds for a hot query) — *upstream* of the hot-view read, outside the 50 ms SLO. This is the shipped `BundleBuilder`'s cost, unchanged.
- **Hot-view memory:** four slices × watched repos, each slice ~1–10 KB → ~10–40 MB Redis at 1,000 repos; linear in watched-repo count, independent of workflow volume. `maxmemory-policy allkeys-lru` is the one-line scale concession if a portfolio ever dwarfs single-node RAM. No AOF (the cache is reconstructable from the next gather).
- **MCP Skills server:** one long-lived stdio process, ~30–80 MB RSS, near-zero idle CPU.
- **New runtime deps:** `redis` (client + `redis:7-alpine` service) and `mcp` (SDK). `langgraph`/`pydantic` already present. No KMS, no secrets broker, no Postgres.
- **Storage growth:** Phase 8 adds no durable storage — Redis is a reconstructable cache; routing events ride the existing `codegenie.plugins.events` log (~200 bytes/workflow).

## Test plan

"Passes its tests" for Phase 8 means:

- **Supervisor routing tests** (roadmap-mandated). Fixture `RepoContext` + skill manifest + recipe index → assert `PlannerNode.route` returns the expected `RouteDecision` variant. Parametrized: recipe-present, recipe-absent-RAG-warm (fake RAG port returns a hit), recipe-absent-RAG-cold→LLM. A `RouteDecided` event is asserted present on **every** path — exit criterion 1 is a test, encoding *why* it matters (global Rule 9), not a hope.
- **100% branch coverage** on `PlannerNode.route` and on the hot-view `invalidates` matcher — the two exit-criteria-bearing functions.
- **Hot-view cache-invalidation tests** (roadmap-mandated). Re-run a probe → assert `invalidates(probe_outputs)` returns exactly the affected slices → assert only those slices change in Redis → assert the next planner read is warm and reflects the new data. A **per-slice** version-bump test asserts an old-version field is a miss and re-renders, and that bumping `risk_flags`'s version does *not* evict `available_skills`.
- **MCP server contract tests** (roadmap-mandated). A snapshot test pins `list_skills`/`get_skill` request/response shapes; the live server's advertised tools must byte-match `MCP_SKILLS_CONTRACT`. Breaking the contract fails CI. One integration test exercises the real stdio roundtrip; the rest exercise the transport-agnostic `SkillsMcpServer` core directly.
- **`Both`/multi-plugin dispatch test** [synth]. A fixture trigger with `provenance == both` → assert the Supervisor emits `MultiPluginDispatch` with one `PluginWorkItem` per resolved plugin under a shared `parent_workflow_id`, and that `match` over `SupervisorDecision` is exhaustive (`assert_never` would fire if a variant were unhandled).
- **Warm/cold path equivalence.** Property test (Hypothesis): for the same inputs, a hot-view-served read and a cold-storage read produce the **identical** planner context. The cache must never change the answer — only the latency.
- **Redis-tamper / fail-closed test.** Write a value to Redis with a wrong `gather_id`; assert the planner discards it, falls through to cold storage, returns the correct value, and emits the mismatch signal. A second test feeds attacker-controlled bytes for `risk_flags` and asserts the planner context is byte-identical to the no-tamper run.
- **Skills-ID traversal test.** `get_skill("../../etc/passwd")` → the `SkillId` newtype smart constructor rejects it before any filesystem touch.
- **Decision-log completeness test.** Run N fixture workflows across recipe/LLM routes; assert exactly N `RouteDecided` events, the existing hash chain verifies end-to-end, and a deliberately-introduced chain gap is caught by the shipped `ChainTamperDetected` path. A static test asserts no routing edge is reachable on a code path that skips the append.
- **Functional-core purity fence.** AST source-scan asserting `decide()` (Supervisor core), `route()` selection logic, `render_hot_views`, and `invalidates` import no I/O modules (mirrors the existing `tests/unit/plugins/test_resolver_purity.py`).
- **Fence — gather-closure + LLM-SDK + wiring.** `import-linter` contracts: `codegenie.hotviews`, `codegenie.mcp`, `codegenie.supervisor`, `codegenie.planner.routing` may not import an LLM SDK. A Phase-8 `tests/fence/` entry enumerates the wiring-line allowlist (new package imports, the `docker-compose.yml` redis service, the `pyproject.toml` `redis`/`mcp` rows). **A fence check confirms the four new packages are NOT inside the gather-pipeline runtime closure that `test_pyproject_fence.py` locks** — the `HotViewRenderer` is *triggered by* the gather tail but its package is not imported into the gather closure (the gather fires a detached task referencing it by a thin callback; the renderer's deps stay outside the fenced closure).
- **Golden tests.** `tests/golden/hotviews/{repo}/` — a gathered `RepoContext` + the expected four rendered slices; the renderer is deterministic, so a golden diff catches accidental shape change.
- **Performance regression canary** (`@pytest.mark.bench`, advisory, CI-tracked). A benchmark of `HotViewStore.get_all` against a real local Redis asserting **p95 < 50 ms** (exit criterion 2, made a test); a second canary asserts warm-path Supervisor overhead p95 < 5 ms. A >20% regression on either fails the advisory gate and surfaces a CI annotation.
- **e2e** (`@pytest.mark.phase08_e2e`, two tests). A fixture vuln-remediation workflow through the full Supervisor → Planner path asserting the `RouteDecided` event is in the log; a hot-view latency e2e running 200 sequential `get_all` calls after a real render, asserting p95 < 50 ms (measured, not asserted-by-faith — global Rule 12).

### Patterns considered and deliberately rejected

- **Event sourcing as a Phase-8 standalone store** — rejected: ADR-0034 lands event sourcing operationally in Phase 9; building it now gives downstream projections two sources of truth. Phase 8 emits into the existing chained log.
- **Command pattern for the routing decision** — rejected: a `RouteDecision` is *data* (a logged record), not a deferred/undoable/queued invocation. A `Command` here is ceremony.
- **Strategy registry / `@register_planning_step` for the three routing tiers** — rejected: exactly three steps fixed by ADR-0011; a registry for three known steps is premature pluggability. An ordered `tuple` iterated in order is the honest shape.
- **Specification pattern for plugin matching** — rejected: the `(task × lang × build)` match with wildcard precedence already ships in `resolver.py`; re-expressing it as composable `Specification` objects re-implements a tested seam for zero gain.
- **A second in-process LRU in front of `HotViewStore`** — rejected: one Redis `GET` already clears the SLO ~25×; a process-local cache is a second invalidation surface for no measurable win.
- **A new Bundle Builder / a new `PluginResolution` type** — rejected: both already ship; a new one is a silent fork of a public surface (commitment §5, Rule 11).

### Anti-patterns avoided

- **Pattern soup** — components are named for what they do (`Supervisor`, `HotViewStore`, `SkillsMcpServer`), not for patterns.
- **Premature pluggability** — no registry for the three fixed routing tiers; no per-stage MCP topology (ADR-0023 `Deferred`); no resolution cache without benchmark evidence and an ADR.
- **Stringly-typed identifiers** — every domain ID is a newtype; `HotViewKey` is a typed key, never an f-string at a call site.
- **Untyped `dict[str, Any]` interfaces** — `ContextBundle`, `RouteDecision`, `HotViewSlice`, all events are Pydantic models.
- **Tag-and-dispatch without a tagged union** — `SupervisorDecision`, `PluginResolution`, `PlanningRoute`, the event union are all discriminated unions handled by `match` + `assert_never`.
- **Boolean flags on public methods** — the Supervisor's three outcomes are a sum type, not `is_hitl`/`is_multi` flags.
- **Side effects in constructors / import time** — the MCP in-memory index is built in an explicit startup call, not at import; the Supervisor's resolver/builder are injected.
- **Speculative subsystem** — no KMS, no secrets broker, no mTLS PKI, no seccomp profile (none deployable on the Phase-8 substrate; the enabling phase for identity is Phase 9).

## Risks (top 3–5)

1. **The `NullRagPort` leaves the RAG branch un-exercised by real data until Phase 11.** Every non-recipe Phase-8 workflow routes recipe-or-LLM; RAG is structurally present and fake-port-tested but unreachable with real data. *Mitigation:* the three-step pipeline shape is correct from day one, the RAG-hit branch is unit-covered via a fake port, and Phase 11 swaps `NullRagPort` for the KG-backed adapter with zero routing-code change. Disclosed honestly — the exit criterion ("the planner makes the recipe/RAG/LLM decision and logs it") is met by the routing machinery, logic, and audit all being real; the RAG *data path* maturing is a Phase-11 dependency, not a Phase-8 gap.
2. **Portfolio-wide cold-path storm after a Redis flush.** An empty Redis means every repo takes the cold-storage path once. *Mitigation:* the cold path is correct and self-heals (it backfills Redis), and the gather-tail renderer re-warms repos as they next gather — but a synchronized re-warm under load is a real spike. Phase 9's Temporal process supervision is where a warm-up-on-start story belongs; Phase 8 ships the self-healing fallback and records the gap.
3. **The `ComposedTccm` placeholder in `resolver.py`.** The resolver's *internal* composition output is documented as a placeholder (real `TCCM` per S3-01). The shipped `BundleBuilder.build` consumes `resolution.composed_tccm` with the real `must_read`/`should_read`/`may_read` bands (`codegenie.plugins.tccm.TCCM`), so the Bundle path is not blocked — but the implementer must verify the resolver hands the *real* composed TCCM to `BundleBuilder` (not the placeholder) before relying on derived-query expansion. See Open Questions.
4. **`<50ms p95` under Phase 9's eventual remote-Redis topology.** The ~25× headroom is a local-socket number. When Phase 9 puts Redis on a different host the latency rises; the budget should still hold, but the e2e latency canary must be re-run under Phase 9's topology and the criterion re-verified.
5. **The Supervisor is a single trusted layer.** A bug in the resolve/build/route wiring affects every workflow. *Mitigation:* the smallest-possible code surface, a contract-snapshot test on `SupervisorDecision`, the functional-core purity fence, and reuse of already-tested seams (resolver, `BundleBuilder`, the event log) rather than new code.

Modeling it now keeps Phase 10 an additive consumer, not a non-additive retrofit.
- **The plugin/TCCM/adapter substrate maturity.** All three assumed it finished. **Carried forward, corrected.** Verified the codebase: `resolver.resolve` returns a real public `PluginResolution` union with `composed_tccm`/`composed_adapters` pre-merged; a real `BundleBuilder` + `Bundle` ship (S3-04); `codegenie.plugins.tccm.TCCM` has the real `must_read`/`should_read`/`may_read` bands; `codegenie.tccm` has `TCCM` + 5 `DerivedQuery` variants. - **`<50ms p95` scope ambiguity.** All three converged on "hot-view read SLO" each citing the others. **Carried forward, pinned as a definition** (Goals §"scope pinned"): it measures `HotViewStore.get_all` + deserialization, and the e2e test measures exactly that. ### Departures from all three inputs

1. **`MultiPluginDispatch` as a first-class `SupervisorDecision` variant.** None of the three modeled the ADR-0042 `Both` case as a sum-type variant — performance and best-practices omitted it; security gestured at it as a blind spot. The synthesis makes it the third variant, because ADR-0042 is `Accepted` and names Phase 8.
2. **Gather-id content-addressed hot-view integrity.** Performance trusts Redis on read (no path for Redis lying); security HMAC-tags with a KMS/secrets-broker apparatus that is undeployable on the Phase-8 substrate. The synthesis takes security's *fail-closed property* via *content-addressing* — the `gather_id` is already a first-class identity in the gather/cache layer; verifying the `(repo, slice, gather_id, slice_schema_version)` binding needs zero new infrastructure.
3. **Per-slice hot-view versioning.** All three either used a single global version ([B], explicitly) or did not specify the granularity ([P], [S]). A single global `int` cold-evicts all four slices when one changes shape; the synthesis versions each slice independently.
4. **Reuse the shipped `BundleBuilder` rather than build one.** Best-practices proposed a *new* `BundleBuilder` in `codegenie.tccm`; security proposed a *new* re-read-free builder; performance left it implicit. The critic proved a `BundleBuilder` + `Bundle` already ship (S3-04). The synthesis reuses the shipped component — none of the three did.

## Load-bearing commitments check

- **§1 No LLM in the gather pipeline.** The Supervisor, Bundle Builder, hot views, routing decision, and MCP server are deterministic; the only LLM call is the `llm_fallback` leaf behind `LeafLlmPort`. `import-linter` forbids LLM SDKs from the four new packages; a fence test confirms the new packages are outside the `test_pyproject_fence.py` gather-runtime closure (the `HotViewRenderer` is triggered by a thin detached-task callback, not imported into the closure).
- **§2 Facts, not judgments.** Hot views pre-render *evidence slices* (`available_skills`, `risk_flags`, …). The routing decision is a logged *judgment*, correctly placed in the Planner (not the gather layer).
- **§3 Honest confidence.** The shipped `BundleBuilder` reads `IndexHealthProbe`/`AdapterConfidence` and degrades SCIP→tree-sitter with a logged `AdapterDegraded`; `RouteDecision` carries the confidence band it routed on; the `confidence_summary` hot view carries `IndexHealthProbe` output.
- **§4 Determinism over probabilism.** Plugin resolution, TCCM composition, Bundle building, hot-view rendering, and recipe matching are all deterministic; the LLM is reached only on a recipe-and-RAG miss.
- **§5 Extension by addition — no silent edits.** Four new packages; the only edits to shipped code are loud, fence-enumerated wiring lines (new imports, the `docker-compose.yml` redis row, the `pyproject.toml` `redis`/`mcp` rows). Two `Literal`-tagged variants are *added* to the existing event union — the compiler-policed additive edit §5 sanctions. No new `PluginResolution` type (the existing public one is consumed); no new `BundleBuilder` (the shipped one is reused). The performance design's two un-amended hot-view slices are rejected because §5 requires a bounded additive core primitive to be under explicit ADR control.
- **§7 Progressive disclosure.** Hot views index `must_read` slices; the Bundle Builder reads originals at decision time; the MCP server serves manifests, not skill bodies.
- **§8 Humans always merge.** `EscalatedToHITL` and the universal-fallback path are typed variants the Supervisor cannot drop; `MultiPluginDispatch` keeps multi-PR remediation auditable.
- **§9 Cost observable and bounded per workflow.** Phase 8 adds `$0.00`; routing events ride the existing log; the `LeafLlmPort` seam is where Phase 9's per-workflow budget cap (ADR-0024/0025) attaches. Phase 8 does *not* build the cost ledger (Phase 13) — it emits the events a later projection reads.

## Open questions deferred to implementation

1. **Resolver → BundleBuilder TCCM handoff.** The implementer must verify that `resolver.resolve` passes the *real* composed `codegenie.plugins.tccm.TCCM` (with `must_read`/`should_read`/`may_read` bands) to `BundleBuilder.build` — the `ComposedTccm` in `resolver.py` is a documented resolver-internal placeholder. If the resolver still hands the placeholder, the resolver-internal substitution (its S3-01 follow-up) is a Phase-8 prerequisite, not a Phase-8 deliverable — surface it loudly.
2. **`MultiPluginDispatch` sequencing depth.** Phase 8 ships the typed parent/child *shape* and dispatch. How much cross-PR *sequencing* logic (ordering, shared evidence, status rollup) Phase 8 implements vs. defers to Phase 10 is a scoping call for the phase-architect — Phase 8 must at minimum make the shape non-additively-extensible by Phase 10.
3. **`NullRagPort` vs. a two-step chain.** The synthesis keeps the three-step pipeline with a null RAG adapter (the shape is right from day one). If the executor finds the null branch creates dead-test maintenance burden, a two-step chain that grows the RAG step in Phase 11 is the fallback — but the three-step shape is preferred for ADR-0011 fidelity.
4. **Hot-view debounce under churn.** Whether the renderer needs a per-`repo_id` debounce (performance proposed 250 ms) to cap render amplification under a hot monorepo's push burst — a tuning parameter to validate against real push-frequency data, not a Phase-8 blocker.
5. **Cold-storage read path identity.** The fail-closed fallback reads "cold storage"; in Phase 8 (pre-Postgres) that is the `RepoContext` on disk / the existing context store. The implementer should confirm the cold-read path is the same artifact the renderer rendered from, so warm/cold equivalence (a property test) holds.
