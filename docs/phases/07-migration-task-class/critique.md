**Reviewed by:** Devil's-advocate critic subagent
**Date:** 2026-05-19

## Method

I read each design end-to-end, the Phase 7 roadmap section (scope + exit criteria + Tooling & setup), production/design.md §2's nine commitments, ADR-0029 (TCCM), ADR-0031 (plugin architecture: scope tuple + `extends`), ADR-0033 (domain modeling: newtypes, smart constructors, tagged unions), ADR-0034 (event sourcing canonical primitive), ADR-0038 (`vuln.provenance` shape + deferred chain-assembly question), ADR-0039 (bounded additive core primitives), ADR-0042 (`Both` = one parent + plugin work items, **Planner owns sequencing — Phase 8**), and ADR-0011 (recipe-first ordering applies to *planning order within a workflow*, not to PR-open order across plugins). ## Attacks on the performance-first design

### Concrete problems

1. **Problem:** `MultiPluginCoordinator` is invented in Phase 7 and ships ordering policy, partial-success semantics, child-workflow fan-out, and pre-Phase-9 `asyncio.gather` plumbing.
   **Why it matters:** ADR-0042 is explicit: "**The Planner owns sequencing, shared evidence, and cross-PR status**." The Planner is **Phase 8**. Performance-first puts a coordinator *above* both Phase 3's `RemediationOrchestrator` and the still-unwritten Phase 8 Planner, with a typed `CoordinatedOutcome` sum, a YAML policy file (`multi_plugin_coordinator.yaml`), and a Temporal-future swap claim. That isn't extension by addition — it's **inventing Phase 8's load-bearing component one phase early**, and it does so without an ADR amendment to ADR-0042. The §2.5 commitment is violated on contact.
   **Where:** Components §1 (`MultiPluginCoordinator`); Architecture diagram (parent box above both orchestrators); Data flow §"One Both-variant run"; Open question §1 (where it lives).

2. **Problem:** Phase 7 ships zero real PRs (per roadmap: Phase 11 is "first PR at scale"). Yet the design specifies PR-ordering policy, recipe-first PR sequence, and `MultiPluginCoordinated(parent_workflow_id, vuln_child_id, migration_child_id)` events containing PR IDs.
   **Why it matters:** There is no PR to order in Phase 7. Recipe-first per ADR-0011 governs **in-workflow planning order** (recipe → RAG → LLM), not the order of two GitHub PRs. The design is conflating "which transform applies first inside a single workflow" with "which PR opens first across two workflows," and budgeting wall-clock against PR-opening behavior that doesn't exist yet.
   **Where:** Components §1 "vuln-remediation PR opens first; migration PR opens second"; Open question §4; Risks §1.

3. **Problem:** The `vuln.provenance` cache lives in a *new* `src/codegenie/vuln_provenance/cache.py` with SQLite-backed cross-process warm reuse, LRU, TTL=24h, and a five-tuple key including `repo_snapshot_sha` and `vuln_index_digest`.
   **Why it matters:** ADR-0038 §Tradeoffs explicitly defers `vuln_provenance_cache` to Phase 14: "the provenance join is recomputed every time it's called, with no inter-workflow caching. […] Phase 14 may add a `vuln_provenance_cache` keyed on `(sbom_digest, vuln_index_digest)` if the lookup volume justifies it." Performance-first contradicts the deferral on its first page and motivates it with "Stage 1 Assessment N_repos × N_open_cves" — but Stage 1 Assessment doesn't exist until Phase 10. The cache is built for a load that no phase before 10 can produce.
   **Where:** Lens summary point (1); Components §2; Architecture diagram box `cache.py`; Resource & cost profile table.

4. **Problem:** The "additive migration alembic 003" to `chainguard_image_catalog` and the new `recommend_distroless(upstream_repo)` query method add columns + an index to `VulnIndex`.
   **Why it matters:** This is an edit to Phase 3 infrastructure, dressed as "additive." `VulnIndex` is Phase 3's SQLite schema; bolting a new domain (Chainguard catalog) into a CVE index conflates two things (vulnerability-feed snapshots vs. base-image recommendations) that have nothing in common except both being lookup tables. §2.5 extension-by-addition is being elastic-stretched to cover "any new row added to any existing table." If the catalog belongs anywhere it's a new artifact (a separate file/store) — not under `vuln_index/`.
   **Where:** Architecture diagram `src/codegenie/vuln_index/` "[Phase 3 — EXTENDED, additive]"; Components §8.

5. **Problem:** The `VulnProvenanceChainAssembler` is a class with policy ("static ordering driven by adapters' `confidence() × cost_band × applies_when` declaration") that hard-codes "App-layer adapters first; base adapter always tried; emit `Both` when both succeed." It also introduces a `cost_band` attribute on adapters that ADR-0038's adapter Protocol does not have.
   **Why it matters:** The design **extends the adapter contract** to add `cost_band` and `applies_when` declarations — that's an edit to the just-promoted-to-kernel `VulnProvenanceAdapter` Protocol, which is the literal contract surface ADR-0039 says becomes part of the next stable contract. The performance argument ("the cost of static ordering is that adding a new adapter family requires touching `VulnProvenanceChainAssembler`") is then explicitly accepted in the same paragraph — i.e., the design admits its chain is not open/closed and then ships it anyway. Adding `RhelVulnProvenanceAdapter` requires editing the kernel chain assembler.
   **Where:** Components §3 entire section; "Adding a new adapter family requires touching `VulnProvenanceChainAssembler`."

### Hidden assumptions

1. **Assumption:** Pre-Phase-9 `asyncio.gather` of two child workflows shares zero contended resources.
   **What breaks if it's wrong:** Both children run against the *same* `repo` working tree (`SandboxedPath`) and the *same* `.codegenie/cache/` directory. The vuln child mutates `package-lock.json`; the migration child mutates `Dockerfile`. They share the buildx cache (8 GB ceiling), they share the same `SubprocessJail` token pool, and they share the same `vuln_provenance.sqlite` for writes. The "different sandbox runs, different output paths" line in §1 is wrong on its face for a single repo's working tree.

2. **Assumption:** `BaseImageProbe` runs at gather time on the cold path, costing p99 ≤ 60 ms because it only does `crane manifest`.
   **What breaks if it's wrong:** A repo with N Dockerfiles × M `FROM` stages can have dozens of `crane manifest` calls. The probe also says it "resolves to immutable digest (already-cached Phase 2 ADR-0004 token)" — but Phase 2 ADR-0004 is a *token*, not a cache fill. The first run still pays the registry call. Stage 0 Discovery scanning thousands of repos at 60 ms each is *minutes* of latency that the performance design budgets as "negligible."

3. **Assumption:** OpenRewrite Dockerfile support is immature and JVM startup is 2 s, so `dockerfile-parse` is the right call.
   **What breaks if it's wrong:** Phase 3's `OpenRewriteRecipeEngine` stub is the established recipe engine; Phase 7 picks a *different* engine for a *different* file type, which Phase 8/12/15 will inherit as "two engines is fine." The convention-drift cost is borne by every later phase. Performance-first acknowledges no precedent obligation here.

### Things this design missed that a different lens caught

- **No threat model for the Chainguard catalog ingest.** Security caught the poisoned-table attack; performance treats it as "operator-curated, weekly refresh, table lookup, done." A poisoned row routes every consumer to a malicious image and the design pipeline trusts the catalog at face value.
- **No Sigstore / signature verification on the catalog.** Security mandates digest pinning + Sigstore bundle; performance refuses any verification cost.
- **The promotion of `NpmVulnProvenanceAdapter` from Phase 3's "refuse-mode shape" is treated as a re-export.** Best-practices caught that this is an additive new file under the *Phase 3 plugin's* `adapters/` directory — performance-first invents a story where the adapter "ships in `plugins/distroless-migration--node--npm/adapters/` and is re-exported" by Phase 3, which inverts the dependency direction. The Phase 3 plugin would have to import from the Phase 7 plugin to re-export it; that's a layering violation neither plugin should accept.
- **Missed the `ShellInvocationTraceProbe` code-execution threat surface entirely.** Performance-first calls the trace probe "a thin reducer that produces a per-stage shell-invocation count" — i.e., it assumes Phase 2 has already executed the build and the probe just reads the trace. Security correctly identifies this as the *first* probe to run target-repo code as part of gather, and isolates it in a microVM. Performance has no isolation story.

## Attacks on the security-first design

### Concrete problems

1. **Problem:** Security ships its own `multiplugin/coordinator.py` with `CoordinationState` sum (`NotStarted | InProgress | Coordinated | PartiallyApplied | Aborted`), `MultiPluginCoordinationStarted` events, `PartiallyApplied` watchdog at 24h, and "Phase 11 merge gate refuses to mark either PR as 'done'."
   **Why it matters:** Same violation as performance-first, but compounded — security depends on a Phase 11 merge-gate consumer that doesn't exist yet, and silently amends ADR-0042's "Planner owns sequencing" to "Phase 7's `multiplugin/coordinator.py` owns sequencing **and** Phase 11 owns enforcement." Phase 7 ships zero PRs (roadmap §"Phase 11 — first PR at scale"), so a `PartiallyApplied` watchdog firing on PR close events in Phase 7 is observing an empty set. The risk table (Risks §5) admits "Phase 11 ships the events; without Phase 11's merge-gate consumer, a determined human can still merge one and close the other" — that's an admission the entire atomicity story is decorative until Phase 11.
   **Where:** Components §"Multi-plugin coordinator"; Goals §6; Risks §5.

2. **Problem:** Security cites `[ADR-0042](../../production/adrs/0042-multi-plugin-coordination-for-both-workflows.md)` repeatedly as if it specifies Phase 7 behavior, including "atomic-or-nothing PR linking" and 24h half-merge thresholds.
   **Why it matters:** ADR-0042 is **24 lines long**, says "Planner owns sequencing," and explicitly lists Phase 8 (not Phase 7) as the consequence. Security is putting words in ADR-0042's mouth that ADR-0042 does not say. "Atomic-or-nothing across PRs" is the security lens's *invention*, not ADR-0042's decision. The cite-to-justify pattern recurs ≥ 6 times in this design.
   **Where:** Architecture diagram "ADR-0042 multi-plugin coordinator"; Components §"Multi-plugin coordinator"; Goals §6.

3. **Problem:** The CVE-to-image lookup is upgraded from "Tooling & setup → a CVE-to-image-recommendation lookup table" (roadmap, one line) to a Sigstore-bundled, digest-pinned, CODEOWNERS-reviewed signed artifact with quarantine tier, publish CLI, and operator-side GPG identity flow.
   **Why it matters:** Security says "my position is non-negotiable" and announces an upgrade of the roadmap line item without an ADR. This is **architectural decree without ADR amendment**. The roadmap says "lookup table." Security expands that into ~7 components (`lookup.py`, `publish.py`, `quarantine.py`, Sigstore verifier, CODEOWNERS workflow, ADR-anchored content-addressed dataset, operator GPG identity) and treats the expansion as already-decided. Per CLAUDE.md "load-bearing architectural commitments […] do not violate without surfacing the tradeoff via an ADR amendment" — security wants the discipline applied to others but not itself.
   **Where:** Lens summary "Contradiction-to-roadmap surfaced" §; Components §"CVE-to-image lookup"; entire `src/codegenie/cveimage/` package.

4. **Problem:** `ChainguardPullToken` ships as `SecretStr`-wrapped newtype with `__str__` raising, a process-boot logger filter, an STS/OIDC mint flow with ≤ 10-min TTL, an egress pull-proxy that injects the token at the outer egress, IP allowlist, audit events per mint and per use, and "rotation is automated via Chainguard's STS-style OIDC flow."
   **Why it matters:** None of this is required to ship the migration task class. Chainguard's `cgr.dev/chainguard/*` distroless images are *public* and pullable without authentication (that's the entire pitch of the catalog). The security design invents an auth requirement that doesn't exist, then builds a multi-component subsystem (`src/codegenie/registry/chainguard/sts_client.py`, `pull_proxy.py`, `token.py`) around it. The "credential class" the threat model loops on (`ChainguardPullToken`) has no production justification documented; the design pretends pulling Chainguard's public distroless image requires bearer tokens, IP allowlisting, and a sidecar process. This is **threat-model-driven over-engineering** — a defense against a credential that needn't exist.
   **Where:** Threat model §"Adversaries assumed" §"Chainguard-credential-theft adversary"; Architecture diagram `src/codegenie/registry/chainguard/`; Components §"Chainguard pull-proxy + token client"; Goals §2, §11, §13.

5. **Problem:** Security ships a *new* `probe-control` process that boots probe microVMs, separate from Phase 5's `gate-control` process — and asserts that "the Phase 5 microVM stack is reused (no new isolation tech, only a new caller)."
   **Why it matters:** "New caller" understates a major topology change: Phase 5 has one privileged process spawning microVMs (`gate-control`); Phase 7 adds a second (`probe-control`). That's two long-running processes with microVM CP creds, two HMAC keys, two TLS endpoints. The "no new isolation tech" framing is correct only in the literal sense; everything else (the operational surface, the supervision tree, the credential boundary count) doubles.
   **Where:** Trust boundaries diagram (two parallel CONTROL PROCESS boxes); Components implied by `ShellInvocationTraceProbe`.

### Hidden assumptions

1. **Assumption:** `ShellInvocationTraceProbe` is a gather-time probe that "runs target-repo build commands."
   **What breaks if it's wrong:** The performance design treats `ShellInvocationTraceProbe` as a *reducer over a pre-existing runtime trace artifact* ("Phase 2's runtime trace already captures shell invocations"). Best-practices makes the probe responsible for booting a container and running `strace`. Security commits to the "this probe executes the build" interpretation and builds an entire microVM `probe-control` subsystem around it. If Phase 2 already produces the trace (performance-first's assumption), the entire `probe-control` apparatus is unnecessary. The three designs literally do not agree on what the probe is.

2. **Assumption:** A Sigstore verifier failing at orchestrator start should *refuse to start the workflow*.
   **What breaks if it's wrong:** Hard-fail at orchestrator boot for any Sigstore-availability issue (outage, network blip, transient verifier crash) takes down the entire system over data that may be hours old anyway. There's no degraded-mode story; "Sigstore verifier offline at orchestrator start → loader refuses to start the workflow" treats availability of a signing service as a hard precondition on workflow execution. Operationally fragile.

3. **Assumption:** The Phase 5 microVM stack supports a `probe` role today.
   **What breaks if it's wrong:** Phase 5's `SandboxClient.spawn(...)` was designed for gates, not probes. The "Trust level" of a probe (semi-trusted gather, not gate) is different from a Phase 5 gate's trust class. Reusing the spawn API for a new role is fine in principle but assumes the API shape is role-parametric. The security design asserts it is without citing Phase 5's contract.

### Things this design missed that a different lens caught

- **No `Both` provenance variant performance budget.** Performance gets ≤ 110 s warm wall-clock for `Both`; security never quantifies what `Both` costs. The design says "atomic-or-nothing" without modeling the cost of serialization the atomicity implies.
- **No discussion of `dict[str, Any]` boundary at the syft schema layer.** Best-practices flags this: `SyftSbom` Pydantic model with `extra="allow"` (because syft's schema is out of our control). Security treats SBOM-as-evidence as if it has a fixed shape and validates against poisoned `locations[].layerID` — but `extra="allow"` means an attacker can add arbitrary fields the verifier won't see. The threat model is incomplete.
- **No mention of the `Layer`/`Ecosystem` enum question.** Best-practices makes them `Enum`s with exhaustiveness checks; security doesn't engage with adapter-key typing at all.
- **No `assemble_provenance` LOC budget or complexity ceiling.** Best-practices caps the chain at 60–80 LOC plain function; security ships `chain.py` as a class with policy and confidence checks and never says how big it is.

## Attacks on the best-practices design

### Concrete problems

1. **Problem:** `assemble_provenance(...)` decides the deferred ADR-0038 question by picking "declared registration order, app-layer first then base-image, plain `for` loop" — and the implementation in §4 walks `registry.items()` which **assumes Python `dict` insertion order is the registration order**.
   **Why it matters:** Best-practices then acknowledges this in Acknowledged blind spots §5 ("'declared order' semantics depend on `dict` insertion order"). That is **a load-bearing global-state ordering invariant smuggled in via implementation detail.** The order an adapter registers is the order plugins import — which depends on plugin-loader iteration order, which depends on filesystem ordering or `sorted()` discipline neither of which is specified. The mitigation ("a unit test asserts the order of `registry.items()` matches registration order") tests the symptom on a fixture and pins nothing about production. Same module imported twice with a different loader order silently changes routing. This is *exactly* the kind of "looks orthogonal to me" coupling Rule 8 warns against.
   **Where:** Component §4 internal design; Acknowledged blind spots §5.

2. **Problem:** The Phase 3 plugin's `vulnerability-remediation--node--npm/` directory gains a new file (`adapters/npm_provenance.py`) **and** a new line in its `tccm.yaml requires:` block — and best-practices repeatedly claims "zero edits to Phase 3 plugin."
   **Why it matters:** G1 says "Zero edits to Phase 3–6.5 plugin code or stable existing behavior" but G4 says "ships in `plugins/vulnerability-remediation--node--npm/adapters/` (additive — does not edit Phase 3's existing adapters)" and Conventions honored §3 says "The Phase 3 plugin […] is touched exactly once: a new TCCM `requires:` line." Adding a file *inside* a plugin's directory **is** an edit to the plugin (its `PLUGINS.lock` `sha256(dir_tree)` changes; its scope tuple now contributes to a new primitive; the `extends` chain consumers see a new contributed adapter). Best-practices wants both "extension by addition" credit and "edits-allowed for the additive parts" relaxation. The CI fence pattern "extends its allowlist to permit Phase 7's exact additions" then **redefines the fence** every time additive shipping happens, which makes the fence non-load-bearing. Conventions §3 even says "Even that edit is gated by ADR-0039's bounded-primitive exception" — but ADR-0039 is about *bounded core primitives*, not about giving free edits to existing plugins. This is the §2.5 commitment being elastic-stretched.
   **Where:** Goals G1; Goals G4; Conventions honored §3; Architecture diagram bottom box; Risks §1.

3. **Problem:** `@register_provenance_adapter` does `cls()` to construct an instance for the `isinstance(cls(), VulnProvenanceAdapter)` runtime check at import time.
   **Why it matters:** Constructing an instance at decorator-application time forces every adapter to have a no-arg constructor and forbids constructor injection — but ADR-0032 / ADR-0031 want adapters to receive dependencies (e.g., `SyftSbom` reader, a logger, an image-manifest cache). The decorator's `cls()` smuggles a hidden constraint: adapters cannot use DI; their state must be lazy-loaded from globals. That's anaemic-by-default. The decorator also stores the *instance* (`_REGISTRY[key] = cls()`) rather than the class, which means the registry is full of pre-constructed singletons created during import — the worst time to do work. Module import ordering becomes load-bearing.
   **Where:** Component §3 code block; "duplicate adapter for {key!r}" path.

4. **Problem:** `Both` is modeled as a flat tagged variant with two sub-discriminated unions (`app_record: AppKind`, `base_record: BaseKind`), but `assemble_provenance` collects only the **first** non-`Unknown` app result and the **first** non-`Unknown` base result. There is no story for what happens when there is a *second* app-layer adapter that also resolves the CVE (e.g., npm and yarn-berry both resolving the same package).
   **Why it matters:** Best-practices Tradeoffs §"Component §4" admits this — "doesn't handle 'two app-layer adapters both resolve' (e.g., npm + yarn-berry on a polyglot repo)." The chosen fallback ("the function takes an optional `registry` param so an explicit selector can be passed when needed") **defers polyglot detection to the caller** — but ADR-0038's Decision says `Both` represents "a CVE in both app and base layers," not "the first app-layer adapter wins, mute the others." A polyglot repo with both npm and yarn-berry where only one of the two has a real fix path becomes a silent mis-route. The "premature DSL averted" framing is hiding a correctness bug under a simplicity claim.
   **Where:** Component §4 tradeoffs; G5 wording "calls each adapter in declared order […] composes the `Both` variant when both return non-`Unknown`."

5. **Problem:** `BaseImageProbe` is placed at `src/codegenie/probes/layer_c/` and `ShellInvocationTraceProbe` at `src/codegenie/probes/layer_d/`, but applies `applies_to_tasks=["distroless-migration"]`.
   **Why it matters:** The probe contract (`localv2.md §4`, frozen by Phase 0 ADR-0007) prescribes probes live in core `src/codegenie/probes/` and are layer-coded. But ADR-0031 says **plugins contribute probes** (the whole plugin pitch is that adding a task class adds new probes inside the plugin directory). Performance-first and security both put the new probes under `plugins/distroless-migration--node--npm/probes/`. Best-practices puts them under `src/codegenie/probes/` — adding them to the *core* probe directory tree. That's an edit to the core; it elevates a task-class-specific probe (only `applies_to_tasks=["distroless-migration"]`) into the core layer-C/D namespace where every other phase's probe lives. Future task classes ("opentelemetry-migration") then need to know whether their probes go in core or in the plugin — and best-practices establishes a precedent that probes go in core. ADR-0031 disagrees.
   **Where:** Architecture diagram `src/codegenie/probes/` box; Components §5, §6.

### Hidden assumptions

1. **Assumption:** A 1-line `tccm.yaml requires:` edit to Phase 3's plugin is "the one allowed extra surface" under ADR-0039.
   **What breaks if it's wrong:** ADR-0039 admits a bounded *core primitive*, not free edits to plugins. Best-practices treats "primitive becomes part of the next stable contract surface" as license to amend the Phase 3 plugin's TCCM. The fence test gets weaker by one row, and the next phase claims its own "one row" relaxation, and the fence becomes a Ship of Theseus.

2. **Assumption:** `dive`, `strace`, `docker buildx` will all live happily in `ALLOWED_BINARIES` with one ADR amendment row each.
   **What breaks if it's wrong:** `strace` requires `CAP_SYS_PTRACE`; running it inside Phase 5's microVM constraints is non-trivial. The design says "the last already present on Linux" as if presence implies usability. CI runners with `--privileged` aren't free; the design admits this in Risks §5 then mitigates with a marker (`@pytest.mark.phase07_e2e`) — which means the e2e doesn't run by default and the headline "End-to-end migration test passes" claim is gated behind a marker most contributors won't trigger.

3. **Assumption:** A `--task-class=distroless-migration` CLI flag is a "tiny CLI surface change" gated by an ADR amendment.
   **What breaks if it's wrong:** Open question §5 punts the decision. If the flag is required (best-practices's preferred branch), it's an edit to Phase 3's CLI — making `cli/remediate.py` task-class-aware contradicts G1 "Zero edits to Phase 3–6.5." If the flag isn't required and the orchestrator infers the task class from the resolved plugin, then plugin-resolution becomes the sole signal — but plugin resolution depends on TCCM matching, which depends on `vuln.provenance`, which is the thing being computed. The design hand-waves which way it falls.

### Things this design missed that a different lens caught

- **No story for what `assemble_provenance` does when an adapter raises an unexpected exception inside the loop.** Failure modes §"A registered adapter raises an unexpected exception" says "the chain-assembly function catches `ProvenanceError` […] *All other exceptions propagate*." Performance-first builds an explicit retry envelope and event-log path for adapter failures; best-practices catches typed exceptions and lets everything else nuke the workflow. That's a §"fail loud" / §"surface uncertainty" trade-off the design picks without engaging the other side.
- **No discussion of `vuln.provenance` cost at portfolio scale.** Best-practices treats "the lookup is fast enough at Phase 7 scale" as the position; never models what Phase 10 Assessment (N_repos × N_open_cves) would cost. ADR-0038 explicitly notes this is "wasteful" for hundreds of CVEs — best-practices marks it "premature optimization" and moves on.
- **No threat model for SBOM tampering.** Security catches the `layerID` poisoning attack via `sbom_verifier.py`; best-practices treats the SBOM as Phase 2-trusted-evidence and reads it as-is. The `Unknown(reason="sbom_layer_attribution_absent")` variant is exercised in tests but the *adversarial* generator of such SBOMs is not.
- **No reasoning about the `runtime_bundled` variant.** ADR-0038 has 7 variants including `RuntimeBundled`; assembly.py special-cases `Layer.RUNTIME` checking `base_result is None`, which collapses `BaseImage` and `RuntimeBundled` into the same slot — but `Both` is `app_record + base_record` where `base_record: BaseImage | RuntimeBundled`. The implementation silently lets `RuntimeBundled` overwrite a real `BaseImage` if the iteration order puts the runtime adapter first. Best-practices doesn't notice.

### Which disagreement matters most for this phase?

**The coordination-ownership disagreement.** Both performance-first and security ship a Phase 7 `MultiPluginCoordinator` (under different names: `transforms/multi_plugin_coordinator.py` vs `src/codegenie/multiplugin/coordinator.py`) with overlapping responsibility for resolving the `Both` provenance variant, sequencing PRs (or planning to), watchdog-ing partial application, and emitting `MultiPluginCoordinated`/`PartiallyApplied` events. ADR-0042 explicitly assigns that responsibility to the Phase 8 Planner. Both designs justify the early-shipping with "we need the seam" or "the events are the spec" — but **two ADR-conflicting Phase-7 designs out of three is a signal that the phase scope is being expanded silently**. Best-practices is the only design that correctly defers: emit `Both` provenance + `RequiresCoordination` event, let Phase 8 own composition. If the synthesizer merges performance and security's "ship the coordinator in Phase 7" framing, Phase 7 ends up doing Phase 8's job, Phase 8 inherits a fait accompli, and the roadmap's phase boundaries dissolve.

### Where do all three quietly agree on something questionable?

1. **All three add net-new top-level packages to `src/codegenie/`** (`vuln_provenance/`, `cveimage/`, `registry/chainguard/`, `multiplugin/`, `primitives/vuln_provenance/`). Each design treats its own additions as "additive, not edits." But every new top-level submodule **must** be wired into the explicit-import collection at `src/codegenie/__init__.py` or `codegenie.probes.__init__.py` or `codegenie.plugins.loader.py` — and those wiring lines **are edits** to existing files. CLAUDE.md is explicit: "Adding a probe = new module + one additive import line." That one line is still a touch to the existing kernel. None of the three designs counts those wiring lines against §2.5 or against the kernel-frozen fence. They all treat "I didn't change the body of the file" as "I didn't edit the file."
2. **All three treat `applies_to_tasks=["distroless-migration"]` as enough to gate probe execution cost.** Stage 0 Discovery (Phase 10) doesn't know what task class will eventually apply to a repo, so it gathers everything that might be relevant. None of the three designs engages with the fact that `applies_to_tasks` is a *filter at dispatch time*, not at *gather time*. Probe Coordinator dispatch may end up running the heavy `ShellInvocationTraceProbe` against every gathered repo in Phase 10 even when distroless migration is never selected. Cost modeling assumes probe-runs-only-when-relevant; coordinator semantics may not deliver it.
3. **All three trust the syft SBOM at the byte level for layer attribution.** ADR-0038's `Unknown(reason="sbom_layer_attribution_absent")` is the typed escape valve, but every design uses `locations[].layerID` as authoritative when present. Phase 2 ADR explicitly marked syft output `extra="allow"` because the schema evolves. A future syft version that semantically changes layer-attribution rules will route differently without any code change in Phase 7. The "evidence" trust boundary the three designs draw is sharp at the orchestrator/sandbox line but soft at the syft/sandbox-output line.

## Roadmap-level critiques

1. **Phase 7 as designed encroaches on Phase 8.** ADR-0042 assigns multi-plugin sequencing to the Planner (Phase 8). Two of three designs ship a `MultiPluginCoordinator` in Phase 7, complete with PR-ordering policy and partial-application watchdogs. Phase 8's design pipeline will arrive to a problem already half-solved by Phase 7 code that no Phase 8 ADR sanctioned. The Phase 8 "Planner routes work between recipe lookup, solved-example RAG, and LLM-fallback" pitch in the roadmap presumes Phase 7 didn't already build a router. Best-practices is the only design that respects the boundary.

2. **Phase 7 depends on a Phase 11 capability it cannot validate.** Security's atomicity guarantee ("the Phase 11 merge gate refuses to mark either PR as 'done'") names a consumer that won't exist for four phases. The roadmap says Phase 11 is "first PR at scale" — Phase 7 ships no real PRs, so the entire `PartiallyApplied`/`Coordinated`/24h-watchdog apparatus runs against synthetic fixtures only. The "evidence is shipped, enforcement deferred" pattern is the same one the ADR-0015 calibration was praised for refusing in Phase 6.5 — but here it's adopted without comment.

3. **Phase 7 relies on a Phase 5 sandbox-stack capability that may not exist as designed.** Security asserts `SandboxClient.spawn(...)` accepts a `role="probe"` parameter. Phase 5's design ships `gate-control` and a `gate` role; the `probe` role + `probe-control` process is invented for Phase 7. If Phase 5's `SandboxClient` doesn't already parametrize role, Phase 7 needs to edit Phase 5 code — which violates §2.5 the security design names ten times.

4. **`§2.5 Extension by addition` is being treated as "additive to the body of files."** All three designs add wiring imports, schema `$ref` insertions, `ALLOWED_BINARIES` rows, `PLUGINS.lock` updates, fence-test allowlist amendments, and `tccm.yaml requires:` lines to existing files — and count them as "additive" because the file *grows* rather than *mutates*. The commitment's force was "no edits to existing plugins or stable existing behavior"; the designs read it as "no semantic edits to existing behavior, but byte-edits to existing files are fine." That's drift the synthesizer should pin down.

5. **`§2.4 Determinism over probabilism for structural changes`** is met by all three (deterministic recipes), but only best-practices reasons about it explicitly. Performance and security pick `dockerfile-parse` AST manipulation without engaging the precedent that Phase 3 already shipped `OpenRewriteRecipeEngine` (a stub). The phase ends up with two recipe engines and no ADR explaining the split.

6. **`§2.7 Progressive disclosure`** — TCCMs are supposed to index evidence, not inline it. Best-practices's TCCM declares `must_read: [dockerfile, base_image, sbom, language_detection]`; security's TCCM adds `vuln.provenance(cve_id, package_id, image_ref)` as a `must_read` derived query. Embedding a *function call* as a `must_read` entry conflates "the evidence to load" with "the computation to invoke" — the progressive-disclosure commitment is about the former, not the latter. ADR-0029's TCCM shape should be re-read to confirm this is allowed.

## Design-pattern critiques (cross-cutting)

### Misapplied patterns (with concrete victim)

- **Performance-first: Chain of Responsibility with extended Protocol.** `VulnProvenanceChainAssembler` is labeled CoR; its consequence is that adding a new adapter family edits the kernel chain assembler. CoR's whole point is open/closed extension at the chain's edges. This design admits in its tradeoffs that adding `RhelVulnProvenanceAdapter` requires editing the chain — i.e., it is **CoR claim, Strategy reality**.
- **Performance-first: Composite for `MultiPluginCoordinator`.** "Parent workflow composing children" is given the Composite label, but children are not Composite components (they don't share the parent's interface and aren't recursively composable). It's a **Mediator-with-fan-out**, which the design then explicitly *denies*: "Not Mediator: children don't talk to each other." Mediator's defining property is centralization, not whether children also talk to each other. Mislabel.
- **Performance-first: Memoization with content-addressed key, "event-sourced through the cache log."** The cache is the source of truth; the event log mirrors it. But the design says "the cache table itself can be reconstructed by replaying the event log." Event sourcing requires the *event log* to be the source of truth and the cache to be a projection. This design has it reversed — the cache writes, then emits events. That's **write-ahead-cache-with-mirror**, not event sourcing. ADR-0034 compliance is claimed by name only.
- **Best-practices: Protocol as runtime-typed registry key.** `@register_provenance_adapter` does `isinstance(cls(), VulnProvenanceAdapter)` at decorator time — but `@runtime_checkable` Protocols in Python only check method *names*, not signatures. The "runtime structural check" gives a false sense of safety; an adapter with the right method names but wrong signatures will register cleanly and break at call time. **Protocol misused as a contract guard.**
- **Security-first: Capability tokens claim.** `ChainguardPullToken` is called a capability token, but capability tokens are unforgeable references to specific actions on specific resources. `ChainguardPullToken` is a bearer credential with a TTL and a scope string. **Bearer token mislabeled as capability token.** The pattern claim sells properties the implementation doesn't have.

### Missed patterns (with concrete location)

- **Best-practices: Missed Open/Closed at the chain-assembly layer.** `assemble_provenance` matches on `Layer.APP | Layer.BASE_IMAGE | Layer.RUNTIME` with hard-coded branch logic. Adding `Layer.SIDECAR` (next task class might need it) requires editing the function. A registration-time policy table keyed on `Layer` (lookup, not branch) would be open/closed. The design ships branching code.
- **Performance-first: Missed Specification pattern for adapter applicability.** Every design has `applies_when=manifest_present(<lang>)` shape. None makes the predicate first-class; it lives in adapter code, not as a typed `AdapterApplicability` value the chain can introspect. The result is the chain has to *call* each adapter to find out if it applies, paying the full cost on every probe even for non-matching adapters.
- **Security-first: Missed Strategy for sandbox role.** Phase 5's microVM stack is reused by adding a second control process (`probe-control`) parallel to `gate-control`. A `SandboxRole` Strategy (gate / probe / future) parametrizing one control process would be the canonical pattern; security ships two copies of the privileged process instead.
- **All three: Missed Builder for the seven-variant `Provenance` construction.** Adapters return `AppDirect(...)`, `BaseImage(...)`, etc. directly. The chain assembler then composes `Both`. A `ProvenanceBuilder` that progressively accumulates evidence and finalizes into one of the seven variants would make the "first-app, first-base, then compose-Both, else Unknown" logic explicit and testable in one place — instead of distributed across three designs in three different shapes. Pure-data builder; not premature pluggability.
- **Best-practices: Missed Discriminator-aware `match` on `Layer` enum.** `assemble_provenance` does `if layer is Layer.APP and app_result is None` — Python's `match` statement with `Layer.APP | Layer.BASE_IMAGE` arms is the convention. Manual `if/elif` chains are the anti-shape the codebase's `match`/`assert_never` discipline explicitly avoids.

### Pattern claims that don't survive scrutiny

- **Performance-first: "Pluggability cost in latency terms: zero — chain assembly is a static list comprehension."** The cost claim is about the loop body; the *registry* construction is at import time and pays the cost of every plugin's module load, every adapter's `__init__`, every `_REGISTRY` dict write. Zero is wrong.
- **Performance-first: "Hot path is fully memoizable: the shared `Bundle` is built once and frozen-referenced into both children."** "Frozen-referenced" implies immutability — but a `Bundle` carries `SandboxedPath` handles that point to a *mutable* working tree. The vuln child mutates the lockfile, the migration child mutates the Dockerfile; the references are frozen but what they point to is not.
- **Security-first: "Strict-AND objective-signal gate."** `DockerfilePolicyGate` is listed alongside `ShellInvocationDeltaGate` and `DistrolessBuildGate` as strict-AND gates — but the design doesn't say what happens when all three pass and the *fourth* gate (a future migration-coverage gate) is missing. Strict-AND over an extensible set means new gates are *required to be at least permissive* by default, which the design doesn't guarantee.
- **Best-practices: "Protocol over inheritance (mirrors ADR-0032 exactly)."** ADR-0032 specifies a protocol; the design's `VulnProvenanceAdapter` adds `confidence()` returning `AdapterConfidence`, which ADR-0032 does not require. The "mirrors exactly" claim is decorative.

### Anti-patterns from the toolkit's "flag on sight" list

- **Stringly-typed identifiers (performance-first):** "`Provenance` returned `Both(app_record=AppTransitive(...), base_record=BaseImage(...))`" — `app_record` and `base_record` field names are fine, but the `kind: Literal[...]` discriminator strings appear in code paths as raw string comparisons (`if r.kind in {"app_direct", "app_transitive", "app_vendored"}` in best-practices assembly.py). The codebase pattern is **enum-or-newtype** for these — string sets are footguns when adding `app_vendored_via_shaded_jar` etc.
- **Premature pluggability (performance-first):** "Adapter registration via plugin manifest's `contributes.adapters` map" — Phase 7 ships *two* adapters (one app, one base). Building the manifest-driven contribution surface with `cost_band` + `applies_when` declarations for N=2 is **Strategy with one impl** territory. The pattern is justified by appeals to Phase 8+ that haven't happened yet.
- **Boolean flag where sum type belongs (security-first):** `is_distroless: bool` in `base_image.json` collapses what BasImageProbe's other field already encodes (`os_family`, plus best-practices's `base_image_kind: Literal["distroless", "alpine", "debian-slim", "debian", "ubuntu", "scratch", "unknown"]`). The bool is redundant with the tagged enum and creates illegal states (`kind="alpine"` + `is_distroless=true`).
- **Smart constructor bypassed by `model_construct()` risk (best-practices):** `Provenance.parse_from_adapter_result(...)` is named as the smart constructor, but adapters return typed variants directly (`return BaseImage(image_digest=..., ...)`). Pydantic's `BaseModel(...)` invokes validation, but `model_construct()` doesn't. Any future refactor that adds `model_construct()` in a hot path (for perf) silently bypasses the smart constructor. The design doesn't add a CI fence asserting no `model_construct()` call sites in the `vuln_provenance/` tree.
- **Anaemic model (best-practices):** `class Both(BaseModel): app_record, base_record` with no behavior. Composition with the rest of the system asks "which PR opens first?" — `Both` could carry `recipe_first_ordering()` or `coordination_summary_for_pr_body()` methods. It carries data only. Behavior lives in `assemble_provenance` and `MigrationOrchestrator`. Classic anaemic-model split.
- **Primitive obsession (performance-first):** `upstream_repo TEXT PRIMARY KEY` in the `chainguard_image_catalog` SQL schema — should be `ImageRef` newtype validated at SQL-load time, not raw `TEXT`. The design relies on string-equality joins where typed comparison would catch normalization bugs.
- **Hexagonal claim smuggling I/O into the core (performance-first):** `vuln.provenance` is positioned as a kernel primitive (per ADR-0039) but its `cache.py` does SQLite I/O at the call site (`.codegenie/cache/vuln_provenance.sqlite`). The "core" is now read/writing a database. The ports/adapters discipline ADR-0032 / ADR-0033 establishes wants the kernel pure; the cache should be an adapter the kernel composes, not a module the kernel writes.
- **"Hexagonal" claim that doesn't hold (security-first):** `Hexagonal Port+Adapter for isolation` is given as a pattern justification, but `vuln.provenance` primitive is described as running "in the orchestrator process (not sandboxed)" — i.e., in the same address space as the privileged orchestrator. That's not hexagonal isolation; that's a function call. The boundary the design names as hex is the microVM, which is a *separate* pattern.
