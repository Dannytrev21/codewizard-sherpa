### What didn't work the first time

1. **Async test functions trip `asyncio.run()`.** With `asyncio_mode = "auto"` (pyproject), the integration tests started as `async def`. Calling `rebuild(...)` from inside the asyncio test loop raised `RuntimeError: asyncio.run() cannot be called from a running event loop`. Fix: make the rebuild integration tests **sync** and bracket their async setup with `asyncio.run(_seed_three_records_async(root))`. Notes §2 anticipated this — "the integration tests above call the sync entry-point and `asyncio.run` inside" — but the validator-prescribed test code in the story used `async def` + `await store.add`. Honored Notes §2 over the literal code sample.

2. **`OperationalError: no such table: collections` after `rmtree`.** chromadb's `PersistentClient` keys a process-wide `SharedSystemClient` system by on-disk path; after `shutil.rmtree(<root>/chroma)` the cached system still held handles to the now-deleted sqlite. The first `collection.add` on a freshly-constructed client at the same path raised. Fix: call `SharedSystemClient.clear_system_cache()` between `rmtree` and re-construction. Lives in `codegenie.rag.store._reset_process_wide_client_cache` (not `cli.py`) so the ADR-0003 chromadb path-scoped fence's `ignore_imports` list stays minimal — only `codegenie.rag.store -> chromadb`.

3. **Doubled records in the rebuilt manifest.** The fresh `ChromaPersistentStore(root_dir=root)` constructor's `_load_existing_record_ids()` reads `manifest.yaml` into `_record_ids` even after `rmtree(chroma/)`. Then `store.add(example)` for each parsed record `_record_ids.append(...)`'d on top — the rebuilt manifest carried `[ex-000, ex-001, ex-002, ex-000, ex-001, ex-002]` and the chain head shifted. Fix: also `manifest.yaml.unlink()` immediately after `rmtree` so the fresh store opens against records-on-disk-but-no-manifest and starts with empty `_record_ids`.

### Design-pattern refactor decisions

- **Module-level seam pattern** — `_seam_build_reembed_embedder(root)` mirrors `_seam_write_lock` (S4-01). The AC-6 fake-embedder injection rides this seam via `monkeypatch.setattr`, keeping the production code chromadb/fastembed-clean.
- **Functional core / imperative shell** — `_query_text_for`, `_resolve_chroma_dir_or_raise`, `_dry_run_parse` are pure helpers; only `rebuild` + `_rebuild_async` carry I/O.
- **No new abstractions for the mint** — per AC-2 de-hedging + Notes §1, the rebuild reuses `_phase4_local_capability_mint` rather than minting a parallel `_rebuild_capability`. Adding a second mint would have meant a second boundary to police.
- **Open/Closed at the chromadb-cache-clear seam** — `_reset_process_wide_client_cache` lives in `store.py` (the lone ADR-0003-authorized chromadb importer) so the rebuild CLI can call into it without growing the contract's `ignore_imports` list.
- **Explicit allowlist over implicit guard** — `_ALLOWED_MINT_CALLSITES: Final[frozenset[str]]` is named, sorted, and grep-able. Adding a third sanctioned mint call-site is one new line in two places (fence allowlist + `pyproject.toml` `ignore_imports`).

### Out-of-story footprint surfaced (Rule 12 — fail loud)

- **Notes §5 gap acknowledged in-code.** `SolvedExample` does not persist the harvester's original `query_text` (intentional — ADR-0016 keeps workflow context out of the identity set). The `--reembed` path therefore embeds `_query_text_for(example)` — a deterministic projection over stable record fields — rather than the original text. The contract (idempotent + cross-machine-deterministic) still holds; the docstring on `_query_text_for` documents the choice. Out-of-scope §"Resume-on-failure" + Notes §3 already framed `--reembed` as idempotent-recoverable rather than perfect-parity.
