# Phase 09 — Durable workflow envelope: Temporal: Devil's-advocate critique

**Reviewed by:** Devil's-advocate critic subagent
**Date:** 2026-05-23

## Method
I read all three designs and attacked each on its own terms. I do not propose alternatives.

## Attacks on the performance-first design

### Concrete problems (3–5)

1. **The `EmitEvent` "per-workflow-batch" Activity is a determinism trap.** Section *Postgres event log → Append path → batched writer* states the writer "runs in the activity worker, not the workflow worker" and that "workflows emit events by enqueueing into a tiny `EmitEvent` Activity that lives on the `postgres-write` queue; that Activity does the batched write." The risk hits the *producer* side: events buffered to a *per-workflow* queue inside an Activity, then flushed "as one `EmitEmitEventsBatch` Activity invocation = one history record" (Risk 1). What that means concretely: the workflow body decides, on its own clock, when "enough" events have accumulated to flush — but the workflow has no clock except `workflow.now()`, and Activity invocations *are* the history records. So either the workflow makes the batching decision (which requires reading mutable per-workflow state to decide *when* to enqueue an `EmitEventsBatch` — fine but adds branchy history), or the worker process does (which means a *single* event's history record now depends on how many other workflows happened to be running in that worker at flush time — a *cross-workflow side-channel* leaking into one workflow's history-ordering decisions, the literal definition of nondeterminism on replay). Section *Risks* §1 names the symptom ("Measured ceiling: ≤ 20 history records per workflow for emission") but does not explain which side decides flush — and either answer breaks something the design separately requires.

2. **The "≥ 5,000 appends/sec" target is built on a contradiction with the synchronous-flush rule.** *Goals* names `≥ 5,000 appends/sec` for the events table. *Append path* states that `MergeOutcome`, `BudgetExhausted`, `TrustGateFailed` "flush synchronously, bypassing the batcher" and *Data flow* shows `RouteDecided` ALSO marked SYNCHRONOUS. `RouteDecided` is Phase 8's per-workflow event — emitted on *every* workflow. At 5k append/s portfolio rate, every workflow's `RouteDecided` synchronously commits to Postgres on the hot path, *defeating the entire COPY-binary fast-path argument the design hangs the throughput target on*. Either `RouteDecided` is not synchronous (in which case "every routing decision is durable before the workflow proceeds" is false), or the 5k/sec target collapses to whatever a single async `INSERT` round-trip can do per workflow (~200/sec on the same machine).

3. **`pgbouncer transaction-mode + statement_cache_size=0` makes the `COPY ... FROM STDIN BINARY` path slower than it claims.** Section *Postgres checkpointer → Connection pool* uses pgbouncer transaction-mode "100 client connections × 4 server connections per worker pod" and Risk 2 explicitly admits "pin asyncpg's `statement_cache_size=0` on the pgbouncer-fronted connections … ~3% latency cost." But `COPY ... FROM STDIN BINARY` is a *protocol-level* operation, not a prepared statement; what *is* prepared is the surrounding session state. With session-state-bound prepared statements disabled and 4 server connections shared by 100 clients, every `COPY` flush pays a fresh session warmup. The named alternative ("fallback is session-mode pooling at lower connection count") would *halve* the 100-client headroom — meaning the design's bursty `512 MiB / 50 workflow` worker can't actually open enough connections for the `COPY` it depends on.

4. **Activity-result memoization key derived from "typed inputs" silently collides across `cassette_id` boundaries.** Section *Activity workers → Activity-result memoization* says idempotent Activities declare `Idempotent=True` and a "`cache_key` derived from typed inputs"; the Phase-1 content cache "is reused as the backing store — same byte format, same eviction policy." Phase 4's cassette adapter is a typed input to `plan_with_llm_fallback`, but the *cassette identity* is per-test-run. Two concurrent workflows on the same `(bundle, route)` but different cassettes will produce byte-identical `cache_key`s if the cassette ID is not in the input's Pydantic model — and Risk 3 ("the cache will appear to hit while serving stale data — silent") names this exact failure but does not show the cassette ID is part of `cache_key.derive()`. The fence ("only allow `cache_key` to come from a `CacheKey.derive(typed_inputs)` smart constructor") doesn't help if the typed input *doesn't include* the cassette identity. The 100% cassette-replay cache hit goal makes this likely, not exceptional.

5. **Two Postgres serialization formats at the same boundary is exactly the kind of "blend" CLAUDE.md Rule 7 forbids.** Section *Postgres checkpointer → Serialization format* picks "Pydantic v2 `model_dump_json()` for the state envelope; `msgspec.msgpack` for the inner payload." The design admits "Two serialization formats at the same boundary is real cognitive cost." Rule 7 says: when two existing patterns conflict, pick one and surface the other for cleanup, not blend. This is the *worst* version of the rule's failure mode — *two* formats in *one* row, both load-bearing, plus a custom `Codec` adapter to hide it. Phase 8 ships Pydantic-only; the performance design diverges without an ADR-amendment commitment.

### Hidden assumptions (2–3)

1. **Assumption: Temporal's workflow history can hold "≤ 20 history records per workflow for emission" while still recording every Activity call.** A recipe-route workflow shows 7+ Activities in *Data flow*, sandbox-build heartbeats every 5s (each heartbeat = history record) for "2–8 min" — that's 24–96 heartbeat records *for one Activity*. The "200-event history" target in *Goals* (`Cold-replay of a 200-event history: ≤ 1.5s p95`) is already past the "≤ 20 emission records" cap. If wrong: replay latency claims do not survive a single warm-cache run.

2. **Assumption: Phase 8's "<50ms p95 hot-view read" budget passes through unchanged when the Supervisor's three LangGraph nodes each become Temporal Activities.** Section *LangGraph ↔ Temporal bridge* says "the Supervisor's `decide()` pure function from Phase 8 is exactly what we want — invoked directly, no Activity needed; only `resolve`, `build_bundle`, and `route` become Activities." But the hot-view read happens *inside* `route()` per Phase 8 final-design §"Planner." If `route` is now an Activity, the hot-view read is preceded by *one Temporal Activity invocation round-trip* (frontend gRPC + task-queue dispatch + Pydantic deserialize). On Phase 8's actual budget (50ms total, hot-view read ~5ms p95), the extra Activity hop is a 4–10x overhead — and the design promises "≥ 95% on Phase 8 hot views in steady state (no regression from Phase 8)." If wrong: Phase 8's exit criterion regresses silently.

3. **Assumption: `RetryPolicy(max_attempts=3, non_retryable=[BudgetExhausted, SchemaValidationError])` composes with Phase 4's existing `FallbackTier` descent.** Section *Workflow definitions* prescribes Activity-level retries; Phase 4 owns recipe→RAG→LLM descent semantics (Phase 8 §"Planner" makes this explicit). If a recipe Activity raises `RecipeMissError`, is it Temporal-retryable (no — same recipe will miss again) or non-retryable (yes — escalate to the `FallbackTier`)? The design's `non_retryable` list does not name *any* tier-descent triggers. If wrong: either Temporal retries a guaranteed-failing recipe three times before descent (3× wasted activity), or the descent path is silently classified `non_retryable` and the workflow fails instead of falling back.

### Things this design missed that a different lens caught

- **Workflow-history-as-PII retention.** Security design §G5 mandates 365-day retention with redaction enforcement at the type level (`RedactedWorkflowPayload`). Performance design's *Storage growth rate* says "~30 KiB per typical workflow × 1,000 workflows/day = 30 MiB/day" with no retention policy. If history is forever-by-default per Temporal, the storage projection is wrong (it grows monotonically, not 30 MiB/day-net); if it's bounded, the boundary is undefined and there is no redaction story for what does land in history.
- **Replay-determinism as a security property.** Security §F7 frames non-determinism as *audit-trail corruption*; performance §"Failure modes" frames it as "workflow is failed with that error; a `WorkflowReset` operation rewinds to the pre-change checkpoint." The performance answer presumes the *replay was wrong* (and can be reset); the security answer says *production already ran something different from what replay shows*. Performance design does not see this attack surface.
- **No mention of the per-task-class credential partitioning.** Best-practices design lumps "the worker" into one process; security explicitly demands per-task-queue workers. Performance design's *Architecture* shows a single "WORKER POOL 'activity'" with "4 task queues by class" — *one process, 4 queues, one credential set*. The security primitive (task-queue partitioning as credential-segmentation) is gone.

## Attacks on the security-first design

### Concrete problems (3–5)

1. **`pgcrypto` column encryption + BLAKE3 `prev_hash` chain on every append is incompatible with "100% of `TrustGate*`/`LlmInvoked`/`PrOpened`/`WorkflowTerminated`/`ActivityFailed` events land in event log within 5 s."** G3 sets a 5-second p100 budget; the architecture diagram shows the chain construction is `prev_hash = BLAKE3(prev_row.row_hash || canonical_payload)` — a *serial dependency* on the prior row across the *entire* `events` table. Two concurrent activities cannot append in parallel: each must read the latest `row_hash`, lock, compute, write. With 5,000 workflows on Stage 1 portfolio scans, every emission *serializes through one Postgres row lock*. Cost table item *BLAKE3 prev_hash chain* names "~5 ms write latency per event" — at 5k concurrent emitters that's a 25-second tail, blowing G3 by 5×. The design accepts this in R5 ("Phase 9 ships at Phase-6-scale throughput") but never reconciles it with G3.

2. **`RedactedWorkflowPayload.seal()` regex scrub is the wrong tool for the threat model it claims to address.** §7 lists the regex: `^(.*_)?(KEY|TOKEN|SECRET|PASSWORD|PAT|CRED|JWT)(_.*)?$` on *field names* and JWT/AWS/GitHub patterns on *values*. The Phase-6 `VulnRemediationResult` contains `evidence_digest`, `attempt_id`, `failing_signals` — none of which match the regex. The actual threat in §A1 ("a naive activity that takes `GitHubToken` as an arg writes the token into history *forever*") is *positional argument* leakage, not field-name leakage; if the activity signature is `def open_pr(token: GitHubToken, repo: RepoId, …)`, `seal()` will scrub `token: GitHubToken` *only because the field is named `token`* — not because of any security property of the type. R1 admits "the `RedactedWorkflowPayload.seal()` regex misses a new secret shape" but the regex misses *all* shapes the contributor names sensibly; the JWT/AWS/GH-PAT regexes are decorative.

3. **The "100% of … events" SLO is mathematically impossible against the design's own crash semantics.** G3 says "0 events allowed to be dropped silently — drops are detected by gap-detection in BLAKE3 chain monotonic sequence." But the design routes events through an `EventLogActivity` (§5 "the *only* sanctioned writer") which Temporal retries on failure. If Temporal *succeeds* writing an event but the worker crashes before recording success in workflow history, Temporal retries the activity → a *second* row gets appended with the same `seq` semantics → the chain forks. G3's monotonic-sequence gap detection cannot distinguish "dropped event" from "double-appended event with chain branch." F2's recovery ("Halt all projections; emit `EventChainBreak`") is then the *expected* state after every worker crash, not an exceptional one.

4. **Task-queue-per-task-class scales worse than linearly with the roadmap.** §2 enumerates Phase-9-shape examples: `worker.vuln-remediation--node--npm`, `worker.migration--node--npm`, `worker.assessment--*--*`. The roadmap shows Phase 7.5 adding Python, Phase 10 adding 5 new assessors per language, Phase 14 adding webhook-triggered continuous gather. The naming convention `(task_class, language, build_system)` already implies ≥ 12 workers for the Phase 7 roadmap alone (vuln × {node,py} × {npm,pip,poetry} + migration × …); R3 admits this ("Per-task-queue credential rotation becomes operationally unwieldy as task classes proliferate"). The mitigation ("Automate rotation via `make rotate-worker-creds`") moves the problem to "CI now has to issue and verify N×M certs per deploy" — and N×M is an integer that grows with every phase. The blast-radius math also breaks: at 30 workers, the *probability* a worker is compromised in any week may exceed 1 - (1 - p)^30; the per-worker reduction is offset by the population growth.

5. **`pgcrypto` column-level encryption + "Per-row encryption of `payload` JSONB column" defeats the projection contract.** §5 says "No `SELECT` for `application_role` on encrypted payload — workers append, but cannot read other workers' events." Projections (cost ledger, retry histogram, audit) *must* read across workflows; §5 says they run as `read_role` "which has decryption capability scoped to read-time only." But projections are *folds over the event sequence* (best-practices design §6) — they need to read every payload, in order, across every workflow, every refresh. `read_role` decrypts every row every refresh. The encryption is decorative *for the projection path*, which is the only path that actually consumes the data; an attacker who exfiltrates `read_role` creds gets the same plaintext as an attacker who exfiltrates the encryption key.

### Hidden assumptions (2–3)

1. **Assumption: `workflow.execute_activity(EventLogActivity, AppendEvent(...))` from the workflow body is safe and replay-deterministic.** §1 says workflows emit events "via the `EventLogActivity` (the *only* sanctioned writer)." Calling `execute_activity` from workflow code is allowed; *however*, the AppendEvent's `prev_hash` value depends on whatever the chain head was at execute time, which is *not* deterministic across replay (a different concurrent workflow may have appended in between). Either the workflow body sees the `prev_hash` (then replay is non-deterministic), or the Activity computes it server-side (then the workflow has no way to detect chain breaks before retry). If wrong: G7 ("replay-determinism gate") cannot pass on any workflow that emits more than one event.

2. **Assumption: temporal-ui has no auth story so loopback-only is acceptable forever.** §9 and G8 commit to "no shared dev cluster"; §F6 recovery says "Dev clusters are per-developer ephemeral; no production UI." The roadmap (Phase 13.5) explicitly names the operator portal as the production UI — but Phase 13.5 *also* says it depends on Phase 9's event log and the *Temporal workflow history* is the source of truth for in-flight workflows ("the live pipeline ribbon"). If the operator portal cannot connect to Temporal (which it can't, since the cluster has mTLS namespace isolation per §3 with cert rotation), then Phase 13.5 cannot show in-flight workflows without inventing its own Temporal client + cert provisioning. The security design has explicitly punted the auth story that Phase 13.5 has to have.

3. **Assumption: alembic CI-snapshot diff catches malicious migrations.** §6 and G9 rely on `tests/fence/test_alembic_schema_snapshot.py` to detect schema drift. But the security threat in A6 is "a poisoned migration can `CREATE EXTENSION ... LANGUAGE plpython3u` and execute arbitrary SQL." A migration that creates a function, executes it (reading `events.payload`, exfiltrating), and then drops the function leaves *zero* schema delta. The schema snapshot only catches durable DDL changes; runtime-only side effects pass clean.

### Things this design missed

- **Phase 8 ships a hash-chained event log already** (`codegenie.plugins.events`). Best-practices §"ADR-0034 event sourcing" calls out that this Phase-8 log "becomes a projection source in Phase 9 — its records are migrated to typed events on first read." Security design's §A2 lists "events table" as a brand-new asset; nothing says how the existing chain composes (or is replaced) with the new BLAKE3 chain. Either two chains coexist (an attacker forges only one), or migration breaks the existing chain (the Phase-8 audit ADR's invariant fails on cutover).
- **The Phase-6 `VulnRemediationSut` Protocol is the harness contract.** Security §1 says "All inputs are `RedactedWorkflowPayload` subtypes (smart-constructed)" — but Phase 6.5's harness consumes `VulnRemediationSut` with its own typed `VulnRemediationCase` / `VulnRemediationResult`. Wrapping those in `RedactedWorkflowPayload.seal()` either changes the public type (breaking Phase 6.5 tests) or adds a wrapper-vs-unwrapped duality. Security never touches Phase 6.5.
- **Performance budget impact of capability tokens.** G10 requires every privileged side-effect to take a typed capability token "(HMAC) at mint time and verified at use time." Per-activity HMAC verify is ~50µs; at 8+ activities per workflow × 5k events portfolio = ~2 seconds of HMAC across the warm path. Not catastrophic, but undisclosed in the cost table.

## Attacks on the best-practices design

### Concrete problems (3–5)

1. **`record_event(...)` as a `ContextVar`-backed module helper is exactly the determinism leak the design itself names as Risk 1 and then "mitigates" with a fence — but the fence is unsound.** R1: "If a future change accidentally calls `record_event` from inside workflow code, Temporal's determinism check may not flag it (the helper would no-op cleanly). Mitigation: the `import-linter` contract forbids `codegenie.events.log` from being imported by `codegenie.durable.workflows`." But `record_event` is *re-exported* via `codegenie.events` (§interface lists `record_event` in `codegenie.events` top-level). An import of `codegenie.events.EventLog` for a *type annotation* in workflow code pulls in `record_event` transitively unless `__all__` is exhaustively maintained — which Python does not enforce. The fence relies on a discipline (`import-linter` rules + `__all__`) the design does not specify in load-bearing detail; "Severity: high (silent failure); likelihood: low" understates the likelihood since *any* future code-review-only enforcement on transitive imports flips this.

2. **"`run_via_temporal` + `TemporalVulnRemediationSut`" doubles the surface to test while the design lists `≤ 18 exported names` and `~75/25 plain/framework-coupled` as KPIs.** §bridge keeps *both* execution paths: "Phase-6 LangGraph dev-mode + Phase-9 Temporal production-mode … doubles the surface to test. Mitigated by … Phase 6.5's harness fixture exercises both paths against the same test cases." But Phase 6.5 ran *one* path (in-process LangGraph); now every Phase-6.5 fixture runs N×2 = 2N tests, the `VulnRemediationSut.digest()` contract must be byte-identical across both paths (different node identities, different checkpointer, different clock source — all sources of digest drift), and the design provides *no* answer for what happens when the digests legitimately diverge. The "boring delegation" story is fundamentally a delegation to *two* substrates simultaneously.

3. **The five Phase-9 event variants are too few to satisfy the roadmap exit criterion.** Exit criterion: "Workflows survive process restarts without state loss." §payloads lists `WorkflowStarted | PatchApplied | GateOutcome | HumanReviewRequested | WorkflowCompleted`. The *retry path* is missing — there is no `ActivityRetried`, no `WorkflowResumed`, no `RecipeMissed`, no `RagMissed`. §Conventions §6 ("Honest confidence") promises "the `WorkflowResumed` and `ActivityRetried` events carry the retry count" but they are not in the variant list. The data-flow narrative names `PluginResolved`, `BundleBuilt`, `LlmFallbackInvoked` (with token counts for Phase 13's projection) — none in the variant list. Either the variant list is wrong, or the data-flow / conventions promises are wishful. Phase 13's cost ledger projection cannot ship as "additive" if the events it folds are not defined in Phase 9.

4. **"Postgres `INSERT ... RETURNING id`" + "`record_event(event)` is a module-level helper" combine to make event-log writes synchronous on the activity hot path.** §log says "Single statement per append. No event store DSL; no abstraction layer." Plus R1's no-op fallback when outside an Activity context. So in normal operation, every activity emission is one round-trip Postgres `INSERT` per event. Phase 8 final-design budgets `route()` at <5 ms p95; adding an `INSERT` (~3–5 ms even local) doubles the budget. The design admits no throughput target *because* it leans on "Phase 9 dev volume (≤100 workflows/day)" — but Phase 8's exit criterion is portfolio-shape, not dev-shape, and Phase 10 starts portfolio scans on this substrate. The "boring Postgres" choice is correct for Phase 9 *only* if Phase 10 plans the move; nothing in the design says so.

5. **The `cost_ledger_v1` stub raising `NotImplementedError("see Phase 13")` violates Open/Closed and ADR-0043 simultaneously.** §projections ships three projection modules including a *stub*: "registers the projection but leaves the fold body as `NotImplementedError` — this exists so Phase 13 lands as a single-file addition rather than a cross-cutting wiring change." (a) `@register_projection` registers an unusable projection: any caller of `replay("cost_ledger_v1", ...)` raises at *use* time, not *registration* time — the design's own pattern catalog (Registry) says "validate on use" but a `NotImplementedError` on the *only* method is failing-loud-at-the-wrong-layer. (b) ADR-0043 says "extension by addition — no *silent* edits"; a stub that *will* be edited in Phase 13 is precisely a *silent edit reserved for Phase 13* — the file is touched, not added. (c) The Phase-9 test suite cannot prove the stub's fold contract because there is no fold; the Phase-13 test author cannot tell whether the stub's signature is the right one until they write the real projection — by which point changing the signature is a Phase-9 edit. This is one of the toolkit's named anti-patterns ("Premature pluggability").

### Hidden assumptions (2–3)

1. **Assumption: `langgraph_checkpoint_postgres.PostgresSaver` exists, is stable, and uses a schema that doesn't collide with Temporal's Postgres schema or our `events` table.** §checkpointer leans entirely on the upstream package; R2 lists "PostgresSaver upstream churn" as a risk but the architecture diagram shows three schemas (`public.events`, `public.langgraph_*`, `public.temporal`) sharing one DB. The Temporal `auto-setup` image creates `temporal` and `temporal_visibility` schemas with hardcoded roles; LangGraph's `PostgresSaver` migrations install themselves at module load (per upstream docs); `alembic` owns `public.events`. The three migration paths must compose in a single Postgres instance with no convergent owner. If wrong: the dev `make migrate` story breaks on Phase 7.5 (Python checkpointer + Node checkpointer at different versions).

2. **Assumption: an "InMemorySaver" default in Phase 6 means *no* checkpointing survives across runs.** §checkpointer keeps "default = InMemorySaver" for Phase-6 backward compatibility. The roadmap exit criterion says "Workflows survive process restarts without state loss." If Phase-6 tests still run with InMemorySaver, they are *not* testing durability — and the `tests/e2e/test_temporal_durability.py` is the only durability test, marked `@pytest.mark.e2e` (excluded from `make test` by default). The exit criterion is satisfied by *one* test that runs in *one* CI mode. If wrong: durability regressions ship without warning on every PR that doesn't run `make test-e2e`.

3. **Assumption: Phase 8's `MultiPluginDispatch` (the `Both` case from ADR-0042) can be handled by a single `VulnWorkflow`.** §workflow has one `@workflow.run` method that takes one `WorkflowConfig`. Phase 8 ships `SupervisorDecision = Dispatched | MultiPluginDispatch | EscalatedToHITL` — `MultiPluginDispatch` carries multiple `PluginWorkItem`s under a `parent_workflow_id`. Best-practices design *never mentions parent/child workflows*, child-workflow signals, or how a `MultiPluginDispatch` actually fans out in Temporal (it would require `workflow.execute_child_workflow` calls — none appear in the data-flow narrative). If wrong: Phase 9 ships not implementing the Phase-8 contract for the `Both` case, and Phase 10 cannot land `Both` candidates without re-architecting the workflow class hierarchy.

### Things this design missed

- **No mention of capability-token threading.** Security's §10 (LangGraph ↔ Temporal bridge) explicitly inherits capability tokens "from the activity worker — same capability tokens injected into the LangGraph state." Best-practices has each activity holding its own credentials by default; the implicit credential pattern is "the worker process has everything." If a `apply_patch` activity also has `open_pr` permission, blast radius is unbounded.
- **No mention of payload-by-reference for large activity inputs.** Performance §Risk 5 names this ("payload-by-reference discipline — every Activity input/output larger than 8 KiB is stored as a Postgres `BYTEA` row keyed by digest"). Best-practices passes Pydantic models directly. `ContextBundle` includes resolved hot-view slices; 100KB+ is plausible. Without payload-by-reference, history grows unboundedly with bundle size.
- **No engagement with the Phase-8 hash-chained `codegenie.plugins.events` cutover.** §Q1 admits this is open: "Do both run in parallel for the duration of Phase 9, with Phase 10 freezing the old log? Or does Phase 9 backfill the old log into the new one and decommission it immediately?" Both Phase-8 and security designs treat the Phase-8 log as load-bearing; this design leaves the cutover as the synthesizer's problem.

### Which disagreement matters most for this phase?

**Workflow body composition.** Each design picks a different mapping from Phase 6/8's LangGraph world into Temporal's workflow world. Performance keeps the Phase-6 graph but moves every node into an Activity (~8 activities per workflow + bookkeeping); Security collapses the whole graph *inside one activity* and makes the workflow code an envelope that only sees opaque sealed payloads; Best-practices maps 1:1 between LangGraph nodes and Activities but treats the LangGraph compilation as dev-mode-only with a `run_via_temporal` parallel path. These three pictures produce *three different* `VulnRemediationSut.digest()` values for the same workflow, and the Phase-6 harness will fail at least two of them. The synthesizer cannot defer this; everything downstream (cost-ledger granularity, event vocabulary, replay-test shape, Phase-11 KG projection input cardinality) flows from this single choice.

### Where do all three quietly agree on something questionable?

1. **"Temporal is the only durable-execution engine we plan to use" — so no port abstracts it.** Performance §"Patterns deliberately skipped": "Did *not* introduce a `TemporalPort` — Temporal SDK is the only durable-execution engine we plan to use." Best-practices §425 "Hexagonal architecture as a Phase-9 introduction" rejects the abstraction. Security §"deliberately rejected" rejects `payload_codec`. All three accept this — but ADR-0003's *Reversibility* row names "switching the substrate" as the very kind of decision the project may need to revisit. With no Port, the Temporal SDK leaks into 30+ files (`@workflow.defn`, `@activity.defn`, `execute_activity`, `workflow.now`, etc.) and a substrate swap is a phase-sized rewrite. Premature pluggability would be wrong; *zero* abstraction with three lenses each declining to introduce one is suspicious.

2. **`PostgresSaver` (LangGraph upstream) is assumed stable.** All three designs delegate the checkpointer schema and migration story to `langgraph-checkpoint-postgres`. The package version is not pinned in the architecture diagrams (only mentioned in pyproject.toml-shape narrative). None of the three designs has a story for "PostgresSaver bumps its schema between Phase 9 and Phase 11." Phase 6's `VulnRemediationSut` digest depends on checkpoint format; an upstream schema bump silently breaks the Phase-6 harness reproducibility.

3. **"Replay-determinism is enforced by a static fence test, plus Temporal's own `Replayer`."** Performance: `tests/fence/test_workflow_imports_are_pure.py`. Security: `tests/fence/test_workflow_determinism.py`. Best-practices: `tests/fence/test_workflow_determinism.py` + `tests/workflows/test_replay_determinism.py`. All three describe AST-walking *imports/calls* in the `workflows/*.py` source set. None of the three addresses *transitive* non-determinism (a LangGraph helper imported by an activity that subsequently changes between Python versions and produces different `__hash__` for a Pydantic model used as a dict key). The fences each catch the easy version (`time.time()` literal in workflow code); none catches the realistic version (LangGraph 0.4.0 changes `compiled_graph.nodes` iteration order, Phase 8 checkpoint replay diverges).

## Roadmap-level critiques

1. **Does this phase as designed set up problems for later phases?** Yes, significantly.
   - **Phase 10 (Discovery + Assessment).** All three designs treat `VulnRemediationWorkflow` as the canonical Temporal workflow shape. Phase 10 introduces Stage 0 Discovery (a scheduled scan that emits `CandidateRepo` events spawning workflows) and Stage 1 Assessment (per-language router classifying repos into Cat 1/2/3). Neither best-practices' five-event vocabulary (`WorkflowStarted | PatchApplied | GateOutcome | HumanReviewRequested | WorkflowCompleted`) nor security's worker-per-task-class partitioning has a `CandidateRepo` or `AssessmentResult` shape. Best-practices' "extension by addition" claim — "Phase 11 adds `MergeOutcome` and the Stage-7 Learning variants" — does not name the *Discovery*/`Assessment` variants Phase 10 must add. Whichever event-sourcing primitive ships in Phase 9 is the schema Phase 10 has to *re-shape* — exactly what ADR-0034 forbids.
   - **Phase 11 (Stage 6 Handoff + Stage 7 Learning).** Roadmap says "Outcome → KG write tests assert that solved cases become retrievable for future RAG queries." Best-practices §projections names `learning_kg_writeback` as a Phase-11 projection, but the Phase-9 events the projection folds (`PatchApplied`, `GateOutcome`) do not carry the *solved-example* fingerprint, the *RAG hit/miss*, the *recipe matched*, or the *LLM cost* — all of which Phase 11 needs to write the KG entry. Phase 11 is then forced to either (a) re-shape the events (forbidden), (b) add fields to the existing variants (forbidden by frozen=True+extra=forbid + the snapshot test in best-practices R3), or (c) introduce a parallel sidecar log (defeating the canonical-primitive ADR).
   - **Phase 13 (cost ledger + ROI dashboard).** Performance ships a `cost_ledger_mv` materialized view; security adds `LlmInvoked`/`PrOpened` to G3's audit set; best-practices ships a stub. Phase 13's ROI ratio is "cost per merged PR" — needs *cost* (LLM tokens, sandbox-build minutes, gather amortization) *and* "merged" (Phase 11 webhook). None of the three Phase-9 designs ship a `CostIncurred` event variant; best-practices admits "Phase 13 adds `CostIncurred` variants." So the cost ledger does *not* fold over the Phase-9 event log alone — it requires Phase-13-specific events on top. The "projections, not separate stores" promise of ADR-0034 is dilute by the time Phase 13 lands.

2. **Does it rely on something earlier phases didn't actually establish?**
   - **Phase 6 shipped with SQLite, not Postgres.** All three designs assume the checkpointer can be swapped; none addresses *in-flight Phase-6 workflows* during the cutover. Phase 6 final-design §Open questions explicitly defers this: "Whether SQLite remains the local checkpoint backend after Phase 9 introduces Postgres." Performance §Open question §4 acknowledges this; security and best-practices do not. Whatever the synthesizer picks, the *transition* is not designed.
   - **Phase 8's `MultiPluginDispatch` parent/child shape.** Phase 8 final-design ships this variant as part of `SupervisorDecision`. None of the three Phase-9 designs has a `parent_workflow_id`-carrying workflow class, child-workflow signaling between siblings, or coordinated PR opening across N child workflows. Best-practices does not even mention multi-plugin coordination; performance mentions a "parent workflow" in passing but doesn't model it; security's worker-per-task-class shape *prevents* one worker from handling both `vuln-remediation--node--npm` and `migration--node--npm` for the same `Both` repo (different workers, different capability tokens, no shared workflow context). Phase 8 final-design §Open questions says Phase 10 will exercise the multi-plugin case — Phase 9 has to ship the shape so Phase 10 can be additive.

3. **Does it violate load-bearing commitments?**
   - **§2.8 "Humans always merge."** All three designs honor it at the *Activity* layer (workflow opens a PR; signal "human_review_decision" gates merge). But ADR-0009 is broader: "Autonomy ends at PR creation." The Temporal *workflow itself* can `workflow.execute_activity("github.open_pr", ...)` *and* `workflow.execute_activity("github.merge_pr", ...)` — nothing in any of the three designs forbids the second Activity from existing. Security best engages with this ("humans always migrate" applies to alembic) but does not say `merge_pr` is not an Activity Temporal may invoke. The fence design enforces "no retry loops" — there is no equivalent fence that says "no Activity whose name matches `merge_pr|approve_pr|...`." The commitment is preserved by *not implementing* the activity, not by *forbidding* it.
   - **§2.4 "Determinism over probabilism for structural changes."** Performance design includes an `EmitEventsBatch` Activity granularity decision that, depending on resolution, smuggles cross-workflow ordering into one workflow's history. Security design's BLAKE3 chain serializes appends — a *correctness* property, but also a *determinism* property; replay sees a different `prev_hash` than recorded (because the chain head moved between original execution and replay). Neither design explicitly addresses this; both promise "replay-determinism" without integrating it with the event-log chain.
   - **§2.5 "Extension by addition — no silent edits."** Best-practices' `cost_ledger_v1` stub is a silent-edit-reservation: the file is touched in Phase 9 but its semantics ship in Phase 13. ADR-0043 names this exact failure mode.
   - **§2.7 "Progressive disclosure" + history-by-reference.** Performance is the only design that mentions payload-by-reference (Risk 5). Security and best-practices write full `ContextBundle`-shaped Pydantic models through history. At 100KB+ per bundle × 200 events × 1k workflows/day = 20 GB/day of redundant history. The progressive-disclosure commitment from §2.7 is workflow-history-shaped exactly because of this.

## Design-pattern critiques (cross-cutting)

### Misapplied patterns (with concrete victim)

- **Performance — "Adapter pattern" for the `Codec` (Pydantic ↔ msgpack ↔ JSON).** The Adapter pattern wraps *one* incompatible interface; `Codec` wraps *two* serialization formats at *one* boundary and hides which path is taken. That's not an Adapter; it's a *Strategy without a strategy interface*. The toolkit calls this out at #54: "Strategy with a single implementation = unnecessary indirection. Wait for the second implementation before extracting." Performance ships *two* implementations on day one, neither named as a Strategy.
- **Security — "Capability pattern" for `EventLogWriteCapability(event_types: frozenset[EventType])`.** The toolkit's framing of Capability is "harder to forge than a flag" — a *non-forgeable* opaque token. Security's design says the token is "a `frozen=True` Pydantic record signed (HMAC) at mint time and verified at use time." An HMAC-signed Pydantic record with `frozen=True` is forgeable by anyone with the HMAC key (which lives on the worker — §2 "Mint capability tokens scoped to that identity"). Two workers on the same machine *share* the HMAC keymat unless explicitly isolated. The "capability" reduces to "trust the worker has the right key" — which is just "is_admin" with extra steps.
- **Best-practices — "Adapter pattern" for `PostgresCheckpointerAdapter`.** §checkpointer: `PostgresCheckpointerAdapter` exposes `def saver(self) -> PostgresSaver` — *returns the upstream class unchanged*. The toolkit's flag-on-sight: "an Adapter that re-exports the same interface unchanged. If you didn't translate, you wrote a forwarder." This is a forwarder.

### Missed patterns (with concrete location)

- **All three: Specification pattern for the `non_retryable` exception classification.** Each design has a list of "do not retry" exception classes. The Specification pattern is exactly the right shape: `IsBudgetExhausted AND IsSchemaValidationError AND IsRecipeMissed AND IsRagMissed AND ...` composable rules, each testable. None of the three uses it.
- **Performance + Best-practices: Open/Closed for the synchronous-flush event vocabulary.** Performance §"Open questions" §2: "Synchronous-flush event vocabulary — fixed or extensible?" The toolkit answers this — `@critical_event` decorator on the Pydantic class is exactly Open/Closed. Performance acknowledges this and *picks the closed (hardcoded list) version*. Best-practices has the same question with no decorator at all.
- **Security: Tagged union for the `pgcrypto`-encrypted-payload key-rotation state.** §payload section describes pgcrypto rotation with no state model. The natural shape is `KeyRotationStatus = NotStarted | InProgress(from_key, to_key, rows_remaining) | Completed`. Without it, the rotation is a boolean grid (the toolkit anti-pattern at §86).

### Pattern claims that don't survive scrutiny

- **Performance: "Hexagonal / Ports & Adapters" applied to `CheckpointerPort`, `EventLogPort`, `LeafLlmPort`.** `LeafLlmPort` is genuinely a Port (Phase 4/8). `CheckpointerPort` and `EventLogPort` are *single-implementation* Ports — the toolkit's premature-pluggability anti-pattern. Performance acknowledges this for `TemporalPort` ("did *not* introduce") but does not for the other two.
- **Security: "Hexagonal architecture — Sandbox port preserved across phases."** DP4 claims "Replacing the microVM stack (Firecracker → gVisor) or the Temporal substrate (Temporal OSS → Cloud) is an adapter swap, not a phase-9 redesign." But "Temporal OSS → Cloud" is not an adapter swap; the workflow code uses `@workflow.defn`, `workflow.execute_activity`, `workflow.now`, etc. — all SDK calls that *don't change between OSS and Cloud*. The "port" claim is true but trivial (no port needed since the SDK is the port). The claim that microVM stack is a swap is true (Phase 5 had a Port); the *Temporal* claim is decorative.
- **Best-practices: "Six explicit pattern decisions per phase."** Toolkit says 3–6 is the calibrated range. Best-practices counts six but two ("Adapter" — wraps unchanged class; "Command pattern explicitly *not* applied" — listed as a decision but is a non-application) are doing no work. Real count: four.

### Anti-patterns from the toolkit's "flag on sight" list

- **Performance: "Boolean flags on public methods."** `cache_strategy: Literal["content", "none"]` is fine (typed enum). But §Open questions §6 names `restart_workflows_on_code_change=False` (off in dev) — a Temporal SDK boolean parameter the design surfaces as a configurable flag, never explaining what the True branch would do.
- **Security: "Capability passed through ten frames as a parameter."** §Data flow shows capability tokens flowing through ~5 frames per activity (workflow → execute_activity → activity worker dispatch → `@audited_activity` decorator → activity body → side-effect call). Per the toolkit, "make it explicit (ContextVar, a small Context dataclass, or a registry)." Security explicitly *rejects* `ContextVar`-based event-log helpers (§deliberately rejected items implied) but uses parameter-passing for capabilities — the worst of both.
- **Best-practices: "Side effects in constructors / module import time."** §events.payloads registers events via discriminated union *at module import* (Pydantic builds the validator). This is fine for the data; but §projections registers projections via `@register_projection(name)` at import time and §activities via `@register_activity(name)` at import time. If two projections register the same name (a real risk with `cost_ledger_v1` being a stub Phase 13 will replace), the *import* of the Phase-13 module fails — and the workflow worker won't start. Best-practices' R3 ("JSONB schema drift across event variants") names a snapshot test for the schema; there is no analog for the registry-collision-at-import. The Phase-13 replacement of the stub is a registry-collision event by construction.
- **All three: "Untyped `dict[str, Any]` interfaces."** None of the three designs uses `dict[str, Any]` at activity boundaries (good). But all three accept the `temporalio` SDK's *internal* serialization, which payloads `dict`s through `temporalio.converter.DataConverter`. Without a project-side `payload_codec` that asserts Pydantic-typed validation on every workflow ↔ activity boundary, a runtime `dict` *can* sneak across (a contributor calls `execute_activity("foo", {"key": value})` instead of `execute_activity("foo", FooInput(key=value))`). None of the three fences against this — security's "fence test that introspects every `@activity.defn`" catches *declared* signatures but not *call sites*.
