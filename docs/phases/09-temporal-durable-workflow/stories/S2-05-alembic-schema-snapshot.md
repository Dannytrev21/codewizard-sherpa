# Story S2-05 — Alembic schema-snapshot diff fence

**Step:** Step 2 — Provision Postgres + alembic + docker-compose dev surface
**Status:** Ready
**Effort:** S
**Depends on:** S2-03 (the migration whose schema this snapshots)
**ADRs honored:** ADR-0009 (snapshot catches drift toward `pgcrypto`/`plpython3u`), ADR-0011 (snapshot catches alembic encroaching beyond `events`), ADR-0034 production (event-sourcing primitive — schema drift on `events.events` would silently change projection semantics)

## Context

The static text fences (S2-04) catch *files mutated* and *out-of-bounds references*; they cannot catch the case where a contributor *intentionally* edits a migration with subtle drift (renamed column, dropped index, missing partial-predicate) and regenerates the lock. The schema-snapshot diff is the **runtime ground truth**: migrate against a fresh Postgres, dump the resulting schema, diff against a checked-in canonical snapshot.

`phase-arch-design.md §C11` line 666 names the file pair: `tests/fence/test_alembic_schema_snapshot.py` + `tests/fence/alembic_schema.sql.snapshot`. The snapshot is the **committed, human-reviewable artifact**; any intentional schema change requires updating it in the same PR, which surfaces the change in the diff. Same secure-default + structural-enforcement pattern as ADR-0015 (`temporal-ui` loopback) — the discussion-forcing function lives in the diff.

This story complements S2-04's static fence (catches mutation/addition/disallowed references) and S2-06's runtime fences (catches role-bypass attacks). The snapshot fence catches a fourth class: *structural drift that the static fences miss* — for example, dropping a partial-index predicate is a semantic change that the static text might miss (depending on regex precision) but `pg_dump --schema-only` records faithfully.

## Goal

Ship `tests/fence/test_alembic_schema_snapshot.py` that brings up a fresh `postgres:16-alpine` container, runs `alembic upgrade head` against it, dumps `events` schema via `pg_dump`, and diffs against the checked-in `tests/fence/alembic_schema.sql.snapshot`. Ship the snapshot file itself (the canonical baseline produced by S2-03's migration). On diff, CI fails with the unified diff in the test output, instructing the contributor to either fix the migration or update the snapshot in the same PR.

## Acceptance criteria

- [ ] **AC-1 — Snapshot file exists and is the canonical baseline.** `tests/fence/alembic_schema.sql.snapshot` is the output of `pg_dump --schema-only --no-owner --no-privileges -n events` against a fresh Postgres after `alembic upgrade head`. The file is committed to the repo and human-reviewable (it is a SQL text dump). The first line is a header comment naming the source (`-- Generated by tests/fence/test_alembic_schema_snapshot.py; do not edit by hand. Regenerate via tools/regen-schema-snapshot.sh.`).
- [ ] **AC-2 — Diff fence fails on drift.** `tests/fence/test_alembic_schema_snapshot.py`:
    - Starts a `postgres:16-alpine` testcontainer (or skips with `pytest.skip("docker not available")` when not available locally — CI always has Docker).
    - Runs `alembic upgrade head` against it (using `subprocess.run` with the testcontainer's DSN in `CODEGENIE_DURABLE_POSTGRES_DSN`).
    - Runs `pg_dump --schema-only --no-owner --no-privileges -n events <dsn>` and captures stdout.
    - Compares against `tests/fence/alembic_schema.sql.snapshot` byte-for-byte (after normalizing trailing whitespace and `pg_dump`-version comment header — see Notes).
    - On mismatch, fails with the *unified diff* in the assertion message (use `difflib.unified_diff`) and a remediation hint pointing at `tools/regen-schema-snapshot.sh`.
- [ ] **AC-3 — Snapshot scope is `events` only.** The `pg_dump` invocation passes `-n events` so the dump excludes `public`, `temporal`, `langgraph_checkpoints`. A test (`test_snapshot_excludes_other_schemas`) reads the snapshot file and asserts the strings `temporal.` and `langgraph_checkpoints.` do not appear anywhere — this is the ownership boundary holding at the runtime layer.
- [ ] **AC-4 — `tools/regen-schema-snapshot.sh` exists.** A helper script that brings up a temp Postgres (via `docker run` or `testcontainers` CLI), runs the upgrade, dumps, writes the snapshot. The script is what a contributor runs after intentionally changing the migration. CI does *not* run regen (same asymmetry as S2-04's lock regen).
- [ ] **AC-5 — Snapshot is normalized.** Dropping the `pg_dump` version header comment, dropping the `SET ...` statements that vary by Postgres version, dropping empty trailing lines — the normalized dump is what's stored. The normalization function is a small helper in the test file; the same function is applied to both sides of the diff so they're comparable. The function is unit-tested with a few hand-crafted variants (different `pg_dump` versions, different whitespace).
- [ ] **AC-6 — Fence catches a planted-drift fixture.** A fixture test (inside the same fence file or a separate `test_snapshot_fence_self_check.py`) temporarily mutates a copy of the migration (e.g., drops the `events_kind_idx` index), runs upgrade + dump against the mutated copy, asserts the diff fence fires with the mutation visible in the diff output. This is the mutation-test of the fence itself — without it, a quietly-broken normalization would yield false greens.
- [ ] **AC-7 — Wall-clock under 30 seconds locally.** The full test (container start + migrate + dump + diff) completes in < 30 s on a developer laptop. Slower than that and contributors will tag it `slow` and skip it — the fence becomes decorative. The test asserts the wall-clock bound; failure messages include the elapsed time.
- [ ] **AC-8 — CI integration.** The fence runs under `make test` (not `make bench`, not behind any marker). On a contributor without Docker, the test skips cleanly with `pytest.skip("docker not available")` and CI's Docker-enabled job catches drift.

## Implementation outline

1. **Generate the initial snapshot.** Bring up Postgres via the compose (S2-01) or testcontainers; run `make migrate`; capture `pg_dump --schema-only --no-owner --no-privileges -n events <dsn>` output; apply normalization; commit as `tests/fence/alembic_schema.sql.snapshot`.
2. **Write `tools/regen-schema-snapshot.sh`** — a shell wrapper around the same steps. Outputs to `tests/fence/alembic_schema.sql.snapshot`. Self-documenting header naming the regenerate-after-intent-change discipline.
3. **Write `tests/fence/test_alembic_schema_snapshot.py`:**
   - Skip-fixture for Docker absence.
   - Container fixture (function-scoped so each test gets a fresh container, or session-scoped if the test suite has only this one test).
   - `normalize(sql_dump: str) -> str` helper.
   - `test_schema_matches_snapshot` — the main fence.
   - `test_snapshot_excludes_other_schemas` — AC-3.
   - `test_normalize_handles_pg_dump_version_drift` — unit-test the helper.
4. **Write `test_snapshot_fence_self_check.py`** — AC-6 — a controlled mutation test.

## Out of scope

- **Snapshot of `temporal` or `langgraph_checkpoints` schemas.** Those schemas are upstream-owned; we don't snapshot what we don't own.
- **Snapshot of `langgraph_checkpoints` after `PostgresSaver.setup()`.** S5-01 calls `setup()` at runtime; the schema lives in Postgres but its evolution is governed by upstream version bumps. Snapshotting it here would mean re-running on every upstream upgrade — out of scope (and the wrong scope; we'd be locking *their* schema).
- **Per-Postgres-version snapshots.** Phase 9 targets Postgres 16 only (per compose). If Phase 16 production targets a newer major, the snapshot may need a per-version variant — handled then.
- **Snapshot of *data* rows.** This is a schema-only snapshot (`--schema-only`). Data lives outside the supply-chain story.
- **Pre-commit hook.** S2-04's lock plus this snapshot already give a contributor two layers; adding a pre-commit hook is additive future work if drift becomes frequent (it won't — migrations are rare).

## Notes for the implementer

- **`pg_dump` version drift is the load-bearing normalization concern.** Different `pg_dump` versions emit different header comments (`-- Dumped from database version 16.1 ...`) and different `SET ...` boilerplate. The `normalize()` function strips comments starting with `--` from the leading 20 lines (configurable), strips `SET ` statements that appear before the first `CREATE`, and trims trailing whitespace. Don't over-normalize — if you strip `SET search_path`, you lose information that *could* indicate drift. Strip only what's unconditionally noise.
- **Container start time dominates the test budget.** `postgres:16-alpine` pulls in ~10 s cold, ~1 s warm; container init is ~3 s; `alembic upgrade head` is < 1 s; `pg_dump` is < 1 s. AC-7's 30 s budget is generous; CI's first run may be at the high end.
- **Why session-scope vs function-scope.** This story only writes one test that needs the container, so function-scope is fine. If S2-06 (adversarial role tests) shares the container, session-scope becomes attractive — handle when S2-06 lands; don't pre-optimize.
- **The diff output in failure messages.** Pytest's `assert ... == ...` truncates long strings. Use `difflib.unified_diff(expected.splitlines(keepends=True), actual.splitlines(keepends=True), fromfile="snapshot", tofile="actual")` and `pytest.fail("\n".join(diff))` to get the full diff in CI logs.
- **`--no-owner --no-privileges` matters.** Without `--no-owner`, the dump includes `ALTER TABLE ... OWNER TO postgres` (or whatever the container's superuser is — non-deterministic across CI/dev). Without `--no-privileges`, the dump includes the role grants — which are deterministic and *should* be in the snapshot. ADR-0011's role-grant intent is captured by AC-3 of S2-03 (the grants exist) + S2-06 (the grants actually constrain). The snapshot's job is structural shape, not grants.
  - However, *consider* whether you want grants in the snapshot. The story author's call: including `--no-privileges` keeps the snapshot focused on structure; including grants (drop `--no-privileges`) gives a fourth layer of defense. **Recommendation: ship with `--no-privileges` for this story; if a future drift slips through, add a separate grants-snapshot fence then.**
- **Mutation-test the fence (AC-6) is non-negotiable.** Without it, a quietly-broken `normalize()` that strips too aggressively passes every PR. The planted-drift test is the discipline.
- **Don't snapshot the `alembic_version` table contents.** The snapshot is `--schema-only`; `alembic_version`'s row data is irrelevant to schema shape. If `pg_dump` includes the table definition (it should — the table exists in the `events` schema), that's correct; if it includes the row data, your invocation flags are wrong.
- **What S2-06 reads from you.** Nothing directly. S2-06 tries adversarial migrations against a real Postgres; your snapshot of the *current* schema is unrelated to their *adversarial-migration-blocked* assertion.
- **Future migrations (Phase 10+).** Each new migration regenerates the snapshot in the same PR. The diff in the PR is the human-review artifact: a reviewer sees `+CREATE INDEX events_new_column_idx ...` in the snapshot diff and asks "is that intentional?" — exactly the discussion-forcing function. Don't regenerate without intent.
